# Visual Layout and Navigation Research

查證日期：2026-10-30。用途：供 UIUX 情境速查書選編，非市場占有率調查。研究範圍為通用 Web 與行動介面的視覺、排版及導航。所有「推論」均為原創情境應用，來源代號只指支持其設計方向的基礎，不代表官方逐條背書。

## What Do Current Official Systems Establish?

### Takeaway

【事實】成熟設計系統會依內容與平台區分層級、密度與導航方式，並非共同要求某一種外觀。以下九頁均已實際 open 讀取正文。

### Cited Findings

- V1【事實】Carbon 用 typography tokens 組合字級、字重、行高；區分偏產品操作的 productive 與偏表達的 expressive 字體配置。頁面更新 2026-09-29。[Carbon Typography](https://www.carbondesignsystem.com/building-blocks/foundations/typography/overview)
- V2【事實】Carbon spacing scale 含 2、4、8 等倍數的級距，用 token 管理 component 內外空間；這是 Carbon 系統選擇，不能推成所有產品只能使用 8px 倍數。頁面更新 2026-09-30。[Carbon Spacing](https://www.carbondesignsystem.com/building-blocks/foundations/spacing/overview)
- V3【事實】Fluent 區分 neutral、shared、brand 色；semantic 色承載狀態並搭配其他指示，不用作無意義裝飾；深色模式會調整共享色的亮度與飽和度。頁面未列更新日。[Fluent Color](https://fluent2.microsoft.design/color)
- V4【事實】GOV.UK tabs 適合同頁相關資訊的切換；比較跨區內容或依序閱讀時不宜使用。GOV.UK 本身不把此 component 當跨頁導航。頁面有歷史，最近所列為 2024-08。[GOV.UK Tabs](https://design-system.service.gov.uk/components/tabs/)
- V5【事實】Breadcrumbs 用於多層網站結構；不表示線性交易的進度，也不必出現在扁平網站。GOV.UK 建議其 breadcrumbs 結束於目前頁的父層；不能把這個細節當所有系統唯一合法形式。最近所列變更 2024-07。[GOV.UK Breadcrumbs](https://design-system.service.gov.uk/components/breadcrumbs/)
- V6【事實】Carbon filtering 區分即時套用和批次套用；多項選擇或慢查詢適合後者。收合後要顯示已套用資訊，並提供清除方式。頁面更新 2026-08-11。[Carbon Filtering](https://www.carbondesignsystem.com/building-blocks/core/patterns/filtering)
- V7【事實】Carbon 依搜尋範圍與資料集選擇搜尋模式，區分送出後前往結果頁與輸入過程中回應；active search 需考慮伺服器負荷。頁面更新 2026-08-12。[Carbon Search](https://www.carbondesignsystem.com/building-blocks/core/patterns/search)
- V8【事實】Android 指引的 navigation bar 容納同層 3–5 個目的地，大螢幕可轉 navigation rail；tabs 是次級同層內容導航，FAB 用於最重要的單一動作。數字僅屬該平台模式，非所有網站規定。頁面更新 2026-10-22。[Android Layouts and Navigation](https://developer.android.com/design/ui/mobile/guides/layout-and-content/layout-and-nav-patterns?hl=en)
- V9【事實】CSS 圓角的 padding edge 半徑是外邊框半徑減對應邊框厚度，content edge 再減 padding，負值為 0；相鄰圓角總和過大時瀏覽器會比例縮小。文件為 2024-03-11 Candidate Recommendation Draft，不應稱已定案的 W3C Recommendation。[W3C CSS Backgrounds §4.2](https://www.w3.org/TR/css-backgrounds-3/#corner-shaping)

### Inferences

【推論】本書適合把「主流」操作化為成熟設計系統反覆出現的工作方式，避免宣稱已證明的市場排名。不同平台的外觀可異，但重要性、可發現性與可預測性可以作為選擇條件。

### Gaps

- 【未查到】未取得可靠統計證明 2026 年 UI 風格市占排名；不寫「最流行一定是玻璃擬態／Bento／極簡」。
- 【未查到】Apple Layout HTML 只呈現 JavaScript 提示，Markdown 端點被 web tool 拒絕 content type；搜尋結果有內容但本研究不以其替代正文查證。
- 【未查到】沒有跨平台統一的「正文必須 16px」「所有間距只能 8px」「所有圓角都必須套同一公式」規定。

## Which Situational Rules Are Useful?

### Takeaway

以下 80 條均標【推論】，是研究者的綜合設計建議。各組末尾的 V 編號用於追溯基礎概念；具體產品例子與取捨是原創，不是來源翻譯。正式成書應保留情境與例外，不將建議寫成普遍標準。

### Cited Findings

來源代號及官方頁見上一節。以下無新增標準數值；數字如 8、16、24 是案例值，非合規門檻。

### Inferences

#### Hierarchy and Composition

1. 【推論】當一頁同時有「完成工作」與「介紹功能」時，就應該把目前工作的入口放在主視區。正例：待處理訂單在前；反例：大幅宣傳圖推走訂單。例外：首次造訪的行銷頁另訂轉換目標。基礎 V1、V3。
2. 【推論】當每個區塊都在搶注意力時，就應該先降低次要區塊的視覺強度。正例：附加說明改一般字重；反例：所有標題都加色塊與陰影。例外：多個同等緊急告警仍須完整呈現。基礎 V1、V3。
3. 【推論】當頁面只有一項主要任務時，就應該讓主要動作在局部區域中明顯突出。正例：儲存為主要按鈕、取消為次要；反例：兩者同樣醒目。例外：比較選項沒有預設推薦時不要製造虛假優先序。基礎 V3、V8。
4. 【推論】當數字需要快速比較時，就應該統一對齊、單位與小數精度。正例：同欄價格都帶幣別；反例：一格顯示元、另一格顯示千元而未標示。例外：不同精度本身有業務意義時明示差別。基礎 V1。
5. 【推論】當卡片只是把連續文章切碎時，就應該回到標題與段落的結構。正例：政策說明連續閱讀；反例：每一段都加框成卡。例外：獨立可操作的項目可用卡片。基礎 V1、V2。
6. 【推論】當圖片是理解或辨識的主要依據時，就應該給圖片足夠空間並維持可比較的比例。正例：商品列表統一預覽比例；反例：只因排版整齊而裁掉產品關鍵部位。例外：藝術作品需保留原比例。基礎 V1、V2。
7. 【推論】當使用者必須上下對照明細與總額時，就應該讓摘要接近明細，必要時固定在可見區。正例：購物車旁顯示總額；反例：總額只出現在另一個 tab。例外：窄螢幕採正常文流以免固定區擋住內容。基礎 V4。
8. 【推論】當用戶會反覆掃描相同清單時，就應該維持欄位及動作位置穩定。正例：每列狀態都在同欄；反例：依字串長短讓動作自由漂移。例外：手機可重排，但重排後仍有一致模板。基礎 V1、V2。

#### Spacing and Density

9. 【推論】當兩項資訊屬同一組時，就應該讓組內距離小於組間距離。正例：姓名與職稱靠近、不同人分開；反例：所有間距一樣。例外：分隔線與語義結構可共同補強群組。基礎 V2。
10. 【推論】當團隊一直微調孤立的 px 值時，就應該先建立少量 spacing tokens。正例：標準 gap 套同一 token；反例：每個表單都各自寫 15、17、19。例外：光學修正可記錄理由，不硬湊倍數。基礎 V2。
11. 【推論】當後台必須同時閱讀大量紀錄時，就應該提供適合資料密度的布局。正例：讓桌面表格可切 compact；反例：所有列塞入巨幅留白。例外：compact 仍需保留可辨識、可操作的目標。基礎 V1、V2。
12. 【推論】當資訊太擠時，就應該先刪除重複內容與分組，再加大所有間距。正例：欄名統一移到表頭；反例：每格重複「訂單編號」。例外：轉成手機卡片後可能需要重複標籤。基礎 V1、V2。
13. 【推論】當 icon 與文字共同構成一個動作時，就應該把它們視為同一個點擊區。正例：加號與「新增」一起可按；反例：只有圖示有效。例外：文字是說明而非動作時需明確區別。基礎 V2。
14. 【推論】當按鈕周圍容易誤觸時，就應該增加動作之間的分隔，而非只縮小圖示。正例：刪除和編輯分開；反例：兩個微型圖示緊貼。例外：工具列需要密集時可移走低頻操作。基礎 V2、V8。
15. 【推論】當版面在寬螢幕變得稀疏時，就應該限制閱讀區寬度或增加並列資訊。正例：文章保持可掃讀寬度；反例：一行文字橫跨整面大螢幕。例外：時間軸或繪圖工作區可利用全寬。基礎 V1。
16. 【推論】當容器縮窄時，就應該優先調整排列與分組。正例：水平控制列換行；反例：字體一路縮小直到塞得下。例外：極少量次要標示可使用較小樣式，但須可讀。基礎 V1、V8。

#### Typography and Content Shape

17. 【推論】當標題、內文、輔助說明無法區分時，就應該建立固定的文字角色。正例：頁標題、區塊標題、本文各用一致 style；反例：每段自行猜字級。例外：數據視覺化可另訂數字角色。基礎 V1。
18. 【推論】當頁面包含很長的說明時，就應該用可掃描的小標拆分內容。正例：依問題分「資格」「費用」；反例：整頁連續粗體。例外：需要完整法律語義的文本仍保留原段落關係。基礎 V1。
19. 【推論】當要突出一句話時，就應該只強調決策必要的部分。正例：加粗「今天到期」；反例：整段全粗全紅。例外：短警告可整句突出，但不能讓其他告警失去層級。基礎 V1、V3。
20. 【推論】當產品以長時間閱讀為主時，就應該用真實內容測試字體與行距。正例：測中文、英文與數字混排；反例：只用 Lorem ipsum 決定所有規格。例外：既有平台字體角色可作起點而非免測理由。基礎 V1。
21. 【推論】當同一欄含有編號與自然語句時，就應該分別處理截斷。正例：編號保留可複製全文；反例：重要流水號只能看到前三碼。例外：純展示縮寫需有另一個完整檢視途徑。基礎 V1。
22. 【推論】當使用者需要比較時間與金額時，就應該先固定格式。正例：同頁使用一致日期順序；反例：10/11 同時可能指月日或日月。例外：多地協作需額外顯示時區或 locale。基礎 V1。
23. 【推論】當一句標籤換行後破壞布局時，就應該允許容器長高。正例：按鈕文字完整呈現；反例：把所有譯文縮成難懂縮寫。例外：極窄 toolbar 可改含名稱的 overflow menu。基礎 V1、V8。
24. 【推論】當頁面主要供操作而非宣傳時，就應該控制大型標題的使用範圍。正例：工作台保留主要空間給工作；反例：每個區塊都像廣告 hero。例外：數據重點展示可刻意突出單一指標。基礎 V1。

#### Color and Dark Mode

25. 【推論】當顏色表示狀態時，就應該同時顯示文字或形狀。正例：紅點加「失敗」；反例：只靠紅綠區別。例外：純裝飾色不需硬塞狀態文字。基礎 V3。
26. 【推論】當品牌色也是錯誤色時，就應該分離品牌裝飾與錯誤訊息的語義。正例：錯誤另有 icon、標題及區域；反例：所有紅色區塊都看似故障。例外：品牌不必改色，須讓角色清楚。基礎 V3。
27. 【推論】當要支援 dark mode 時，就應該依 surface、text、border 等角色建立映射。正例：同一語義 token 換對應值；反例：對整頁套 invert。例外：圖片及插圖需獨立判斷。基礎 V3。
28. 【推論】當深色背景讓陰影失去區隔作用時，就應該檢查 surface 與邊界辨識。正例：浮層用可辨識底色及邊框；反例：一味加黑陰影。例外：層次不可只靠顏色，還需布局與標題。基礎 V3。
29. 【推論】當同一 badge 在多個頁面代表不同意思時，就應該統一語義或改標籤。正例：綠色「完成」全站一致；反例：另一頁綠色表示尚未開始。例外：跨產品整合需清楚的局部圖例。基礎 V3。
30. 【推論】當所有卡片都用了高飽和背景時，就應該把強調色留給少數決策訊號。正例：選中的方案突出；反例：未選項也一樣搶眼。例外：分類色有明確辨識用途時保留但補文字。基礎 V3。
31. 【推論】當狀態改變但外觀只微幅變色時，就應該增加明確結果標記。正例：選中項加勾選與名稱；反例：只從淡藍變深藍。例外：不可讓新標記使布局大幅跳動。基礎 V3。
32. 【推論】當使用者切換主題時，就應該確認圖表、placeholder、disabled 及 focus 狀態一起切換。正例：測全狀態畫面；反例：只看首頁靜態截圖。例外：第三方嵌入內容若不可換色須維持可讀的容器。基礎 V3。

#### Shape and Nested Corners

33. 【推論】當內外曲線要形成等距同心圓角時，就應該用兩條實際邊界間距推算半徑。正例：無 border、等 padding 4、內半徑 12，外半徑取 16；反例：內外都 16。例外：只有等距圓弧貼合時適用，不是所有巢狀 component 的義務。基礎 V9。
34. 【推論】當外層有 border 時，就應該把 border 厚度納入邊界距離。正例：border 2、padding 4、子元素貼 content edge、外半徑 18，子元素半徑可取 12；反例：只減 padding 得 14。例外：子元素有 margin 或位移要再算實際距離。基礎 V9。
35. 【推論】當水平與垂直 inset 不同時，就應該分軸判斷圓角。正例：分開檢查 x/y 半徑；反例：用單一 padding 值宣稱等距。例外：要維持圓形外觀時可放棄嚴格貼合，改光學調整。基礎 V9。
36. 【推論】當小按鈕只是放在大卡片內時，就應該優先遵循按鈕自己的 shape token。正例：卡片角 24、中央按鈕角 8 可並存；反例：一律套外角減 padding 導致按鈕變形。例外：按鈕恰好貼著容器邊緣形成雙層輪廓時另算。基礎 V9。
37. 【推論】當計算出的內半徑小於零時，就應該以零作幾何下限並重新檢查布局。正例：內角可為直角；反例：寫負 border-radius。例外：零半徑不代表設計必然協調，仍需看內容安全區。基礎 V9。
38. 【推論】當圖像貼滿圓角卡片時，就應該確認圖像裁切與卡片輪廓一致。正例：裁切容器管理邊角；反例：圖片直角露出。例外：會超出的陰影、選單與 focus ring 不可一起誤裁。基礎 V9。
39. 【推論】當膠囊、圓角矩形、直角在同角色混用時，就應該先定義 shape 的角色。正例：狀態 chip 與主要按鈕各有一致形狀；反例：每頁靠喜好換角。例外：品牌活動頁可有獨立且完整的風格。基礎 V2、V3。
40. 【推論】當指定的角很大而實際效果與預期不同時，就應該檢查容器尺寸是否觸發半徑縮放。正例：測短文字與長文字按鈕；反例：只比 CSS 數字認定兩個輪廓相同。例外：大半徑刻意用於 pill 可以接受縮放結果。基礎 V9。

#### Responsive Layout

41. 【推論】當螢幕變窄但任務不變時，就應該保留核心資料與操作，重排次要資訊。正例：訂單總額與狀態仍可見；反例：手機版刪掉付款結果。例外：次要分析可連到獨立頁。基礎 V8。
42. 【推論】當側欄擠壓工作區時，就應該切換適合可用空間的導航。正例：寬版 rail、窄版明確入口；反例：在小手機保留三欄。例外：具平台慣例時優先相容既有 mental model。基礎 V8。
43. 【推論】當斷點之間內容已經溢出時，就應該按內容失效點調整布局。正例：按鈕擠壓前先換行；反例：只因裝置名稱尚未到 tablet 就拒絕調整。例外：系統既有 breakpoints 可作起點。基礎 V8。
44. 【推論】當底部有固定操作區時，就應該留出內容與鍵盤可用空間。正例：最後一列可滾到操作區上方；反例：按鈕永久壓住最後欄位。例外：系統鍵盤變化需實機檢查。基礎 V8。
45. 【推論】當桌面 hover 才出現重要操作時，就應該為觸控與鍵盤提供可發現入口。正例：長駐更多按鈕；反例：手機完全找不到刪除。例外：不重要的裝飾 hover 可無替代。基礎 V8。
46. 【推論】當資料本質需要橫向比較時，就應該保留表格結構並提供可發現的橫向瀏覽。正例：比較方案欄位；反例：拆成長卡片後無法逐列對照。例外：只讀單筆摘要時卡片更合適。基礎 V4、V8。
47. 【推論】當內容靠近瀏海、系統手勢區或浮層時，就應該實測可見與可操作邊界。正例：主要動作有安全 inset；反例：按鈕貼住 home indicator。例外：背景可延伸，重要互動需留區。基礎 V8，為跨裝置應用建議。
48. 【推論】當使用者旋轉或改變視窗寬度時，就應該保留工作狀態。正例：編輯內容與篩選仍在；反例：重建畫面把輸入清空。例外：流程本來必須重新載入時先保存草稿。基礎 V8，為工作連續性推論。

#### Navigation and Location

49. 【推論】當使用者在不同頂層任務間移動時，就應該提供穩定的主導航。正例：訂單、商品、報表各自入口；反例：各頁隨意換順序。例外：權限差異可隱藏不可用項，但不要重排熟悉位置。基礎 V8。
50. 【推論】當一個控制會執行動作時，就應該讓它與導航目的地可區分。正例：「建立訂單」是按鈕；反例：把它混成與「報表」相同的主導航 tab。例外：平台有明確約定時仍要標明行為。基礎 V8。
51. 【推論】當需要讓人知道目前位置時，就應該同時保留頁標題與導航選中狀態。正例：訂單頁標題清楚；反例：只留一個變色 icon。例外：全螢幕媒體可有暫時隱藏但可喚回的導航。基礎 V3、V8。
52. 【推論】當網站有多層分類時，就應該考慮 breadcrumbs 幫助返回上層。正例：商品 > 電腦 > 筆電；反例：讓用戶只能連按瀏覽器返回。例外：扁平結構不必為了完整而硬加。基礎 V5。
53. 【推論】當畫面顯示結帳進度時，就應該使用步驟語義。正例：地址、付款、確認；反例：用 breadcrumbs 偽裝可任意前往所有步驟。例外：允許回改的已完成步驟應明確可操作。基礎 V5。
54. 【推論】當圖示名稱無法被新人猜中時，就應該提供可見標籤。正例：「稽核紀錄」配 icon；反例：只用一個不常見圖形。例外：熟悉工具的可收合側欄仍保留名稱取得方式。基礎 V8。
55. 【推論】當導航項很多時，就應該先按使用者任務分組。正例：帳務下有發票與收款；反例：把資料庫資料表名稱全部平鋪。例外：專家工具可提供 command search 加速。基礎 V7、V8。
56. 【推論】當使用者從清單進入明細再返回時，就應該恢復先前工作位置。正例：保留頁數與篩選；反例：每次都回第一頁。例外：資料改變時可更新結果，但應解釋原項目消失原因。基礎 V6、V8。

#### Tabs and Disclosure

57. 【推論】當同一物件有幾組互不必同時觀看的資訊時，就應該考慮 tabs。正例：客戶的基本資料與活動紀錄；反例：把必須一起比較的兩份價格分開。例外：少量內容直接顯示可能更快。基礎 V4。
58. 【推論】當讀者必須依序理解內容時，就應該保留連續閱讀。正例：申請教學逐段呈現；反例：步驟拆進不明顯 tabs。例外：每步是獨立操作的 wizard 可用進度控制。基礎 V4。
59. 【推論】當 tab 名稱只能叫「其他」時，就應該重整分類。正例：「帳單紀錄」；反例：「更多資訊 2」。例外：真正低頻且異質的次要項可收在明確更多選單。基礎 V4。
60. 【推論】當 tabs 數量在窄螢幕擠不下時，就應該使用有可發現性的替代排列。正例：可捲動並提示尚有項目，或改目錄；反例：無提示地裁掉最後一半。例外：不要只因窄屏把順序打亂。基礎 V4、V8。
61. 【推論】當切換 tab 會丟失輸入時，就應該先保留編輯狀態或阻止靜默遺失。正例：切回仍有草稿；反例：切換後清空表單。例外：必須捨棄時用明確離開確認。基礎 V4，為編輯流程推論。
62. 【推論】當資訊對所有人完成任務都必要時，就應該直接呈現。正例：費用在付款前可見；反例：藏在預設收起的「更多」。例外：重複的進階說明可折疊。基礎 V4。
63. 【推論】當不同區塊需同時展開比較時，就應該允許多區展開或改為連續內容。正例：保固與退貨可一起讀；反例：開一個必關另一個。例外：空間極受限且比較不是任務時單開可行。基礎 V4。
64. 【推論】當某個子區塊需要被分享或重訪時，就應該讓網址能表示所在狀態。正例：連結開到活動紀錄；反例：分享後總回預設 tab。例外：敏感或短暫狀態不直接放入 URL。基礎 V4、V7。

#### Search and Filtering

65. 【推論】當使用者知道名稱或編號時，就應該讓搜尋可直接定位。正例：輸入訂單號取得紀錄；反例：必須逐層分類猜路徑。例外：小型且一眼可見的清單可不加搜尋。基礎 V7。
66. 【推論】當頁面同時有全站與區域搜尋時，就應該寫清楚搜尋範圍。正例：「搜尋此專案檔案」；反例：兩格都只寫「搜尋」。例外：scope 可切換時顯示當前值。基礎 V7。
67. 【推論】當即時搜尋成本高或回應慢時，就應該考慮明確送出。正例：輸入條件後按搜尋；反例：每打一字就重載重型報表。例外：可快取的小資料集可即時。基礎 V7。
68. 【推論】當搜尋請求可能亂序回來時，就應該讓結果只對應目前查詢。正例：保留最新查詢結果；反例：輸入 ABC 卻顯示 AB 的舊結果。例外：顯示快取需註明更新中。基礎 V7，為非同步正確性推論。
69. 【推論】當查無結果時，就應該顯示查詢字詞與可調整方向。正例：提示移除日期範圍；反例：只留空白。例外：不得自動擴大條件卻假稱精準命中。基礎 V6、V7。
70. 【推論】當使用者需要組合多個條件時，就應該讓條件可被檢視及單獨移除。正例：已選「台北」「本週」各有移除；反例：關閉抽屜就看不到套了什麼。例外：機密條件不宜在共享畫面暴露時需另訂顯示政策。基礎 V6。
71. 【推論】當改一個條件就要等待很久時，就應該提供「套用篩選」。正例：先選日期、部門再查一次；反例：每點一下都鎖住畫面。例外：即時且便宜的單一篩選不必增加一步。基礎 V6。
72. 【推論】當條件尚未套用時，就應該區分草稿選擇與生效結果。正例：顯示待套用並保留舊結果標記；反例：結果數字看似已更新。例外：全部即時更新的流程不需此狀態。基礎 V6。
73. 【推論】當篩選結果可能為零時，就應該保留篩選入口。正例：空結果仍可清除條件；反例：連篩選列一起隱藏。例外：初次無資料與篩選無資料要分別處理。基礎 V6。
74. 【推論】當有多選條件時，就應該說清楚同類與跨類如何組合。正例：狀態任一符合、部門必須符合；反例：用戶無法判斷 AND/OR。例外：一般用戶可用自然語句，不必暴露查詢語法。基礎 V6。
75. 【推論】當清除與重設會產生不同結果時，就應該使用不同文案。正例：「清除全部」與「恢復預設」；反例：按清除卻默默套回本月。例外：產品只提供一種行為時仍需說清結果。基礎 V6。
76. 【推論】當排序與篩選同時存在時，就應該讓兩者角色清楚。正例：篩選決定有哪些、排序決定先後；反例：把「價格低到高」放進產品類別。例外：推薦排序若含個人化應另行揭露。基礎 V6、V7。
77. 【推論】當搜尋只涵蓋目前頁資料時，就應該明示範圍或擴大為完整資料集。正例：「搜尋這一頁」；反例：找不到就宣稱訂單不存在。例外：離線模式可說明只查已下載內容。基礎 V7。
78. 【推論】當用戶經常重複相同條件時，就應該考慮保存檢視。正例：「我的逾期工單」可重用；反例：每次重設五個條件。例外：跨帳號或租戶不要共享私密條件。基礎 V6、V7，為頻繁工作推論。
79. 【推論】當某筆結果因權限無法開啟時，就應該在揭露資訊前確認可顯示範圍。正例：搜尋只返回有權查看資料；反例：列出機密標題後才拒絕進入。例外：明確允許發現但須申請存取的產品需呈現授權流程。基礎 V7，為權限設計推論。
80. 【推論】當篩選改變結果集時，就應該重新檢查頁碼與選取範圍。正例：回到有效頁並說明選取仍涵蓋哪些資料；反例：留在不存在的第九頁，批次動作卻作用於隱藏舊項。例外：保留跨頁選取時要顯示完整範圍。基礎 V6，為資料操作推論。
