# Interaction and Workflow Research

查證日：2026-10-30。範圍：Web app、SaaS 後台與一般服務表單。以下「主流」指成熟設計系統的實務模式，不代表已取得市場使用率排名。原始規範摘要與原創情境建議分開；後者可用於編寫 cheat note，但不能宣稱每一條都是 WCAG 要求。

## Which patterns are supported by primary sources?

### Takeaway

先依使用者要做的事選 component，再決定何時提供 feedback。單選、多選、即時設定、提交表單和頁面導航不是同一種互動；成功、等待、失敗、無結果也必須是不同狀態。

### Cited Findings

下列每筆摘要均短於 200 字；來源頁為本次實際讀取，不是只讀搜尋片段。未標出版日期者表示頁面未提供可靠日期，不推測。

- 【事實 S01】GOV.UK Button：按鈕文字描述動作；主行動不應彼此競爭；disabled button 可能令人困惑，僅有研究支持時使用；重複提交需考慮 server 端防護。頁面含 2026-07 變更紀錄。[Button](https://design-system.service.gov.uk/components/button/)
- 【事實 S02】APG Button：button 觸發動作，link 有不同功能；button 支援 Enter 與 Space。toggle button 以 `aria-pressed` 表達狀態時保留穩定名稱。[Button pattern](https://www.w3.org/WAI/ARIA/apg/patterns/button/)
- 【事實 S03】GOV.UK Text input：input 需要 label，通常應可見；placeholder 不應替代 label、hint 或例子；多行答案用 textarea。[Text input](https://design-system.service.gov.uk/components/text-input/)
- 【事實 S04】GOV.UK Checkboxes：checkbox 支援選取一個以上選項；例子使用 fieldset、legend 與提示說明可複選。[Checkboxes](https://design-system.service.gov.uk/components/checkboxes/)
- 【事實 S05】GOV.UK Radios：radio 用於單選集合；其範例以 fieldset 與 legend 表達共同問題。[Radios](https://design-system.service.gov.uk/components/radios/)
- 【事實 S06】Carbon Toggle：適合立即生效的二元設定；非即時生效可改 checkbox 配合提交；不應用 toggle 表示刪除。頁面更新 2026-09-30。[Toggle](https://www.carbondesignsystem.com/building-blocks/core/components/toggle/guidelines)
- 【事實 S07】APG Combobox：可以允許自由輸入或限定合法選項，也有 editable 與 select-only 形式；自動完成的選擇模式需一致。[Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)
- 【事實 S08】GOV.UK Validation：保留輸入、提供欄位錯誤和摘要；通常等提交才驗證，避免 blur；server 驗證仍必要；資格不符不是格式驗證錯誤。[Validation](https://design-system.service.gov.uk/patterns/validation/)
- 【事實 S09】GOV.UK Error summary：該系統要求驗證錯誤時顯示摘要、移動 focus、連到錯誤答案；摘要與欄位文案一致。[Error summary](https://design-system.service.gov.uk/components/error-summary/)
- 【事實 S10】GOV.UK Date input：適合記得或可查到的日期；例子讓日、月、年有各自 label 與 numeric inputmode。[Date input](https://design-system.service.gov.uk/components/date-input/)
- 【事實 S11】GOV.UK Check answers：提交前讓使用者檢查答案，摘要提供修改入口。[Check answers](https://design-system.service.gov.uk/patterns/check-answers/)
- 【事實 S12】APG Modal dialog：開啟時 focus 移入、Tab 留在 dialog、Escape 關閉；關閉後回到觸發點或合理後繼位置。不可逆動作可初始 focus 最不具破壞性的選項。[Modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
- 【事實 S13】Carbon Modal：短暫且不頻繁的阻斷任務可用 modal；複雜工作流考慮完整頁；其表單建議可在 blur 驗證。頁面更新 2026-09-30。[Modal](https://www.carbondesignsystem.com/building-blocks/core/components/modal/guidelines)
- 【事實 S14】APG Tooltip 頁仍標示草案、未達 task force consensus；描述 tooltip 不取得 focus，可由 hover/focus 觸發、Escape 關閉。[Tooltip](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/)
- 【事實 S15】Carbon Notification：區分 inline、toast、actionable、callout；通知應節制使用，呈現強度應與任務影響相稱。更新 2026-09-30。[Notification](https://www.carbondesignsystem.com/building-blocks/core/components/notification/guidelines)
- 【事實 S16】Carbon Loading：loading 表示處理中；有明確內容結構的初載可使用 skeleton；局部等待可在相關區塊顯示。更新 2026-09-28。[Loading](https://www.carbondesignsystem.com/building-blocks/core/components/loading/guidelines)
- 【事實 S17】Carbon Empty states：區分首次無資料、使用者行動後無結果與錯誤/權限問題，並給對應下一步。更新 2026-08-11。[Empty states](https://www.carbondesignsystem.com/building-blocks/core/patterns/empty-states)
- 【事實 S18】GOV.UK File upload：同時提供選檔與拖放；同一路程可重用已上傳檔案，但需考量共用裝置上的隱私。[File upload](https://design-system.service.gov.uk/components/file-upload/)
- 【事實 S19】GOV.UK Password input：預設隱藏密碼，可讓人主動顯示；登入錯誤不揭露帳號或密碼何者錯誤；範例支援 autocomplete。[Password input](https://design-system.service.gov.uk/components/password-input/)
- 【事實 S20】GOV.UK Passwords：允許貼上、明確說明限制；忘記密碼以限時重設連結/代碼處理，不寄原密碼。[Passwords](https://design-system.service.gov.uk/patterns/passwords/)
- 【事實 S21】GOV.UK Confirmation pages：完成交易後顯示完成狀態、參考編號（若有）、接下來何時會發生什麼及可保存紀錄。[Confirmation pages](https://design-system.service.gov.uk/patterns/confirmation-pages/)

### Inferences

- 【推論】GOV.UK 偏向跨能力、低頻公共服務；Carbon 偏向複雜產品工作流。應按場景選驗證時機，不能把不同設計系統的局部建議拼成互相矛盾的「通則」。
- 【推論】原生 HTML component 能滿足需求時，使用它可減少自行重建 keyboard、focus、語意的工作；客製 component 仍須測試實際互動。

### Gaps

- 【未查到】無可支持「所有 UI 都應在 blur 驗證」或「所有 disabled submit 都錯」的跨平台通則。
- 【未查到】Apple onboarding 本次只取得 JavaScript 提示頁，其 Markdown fetch 失敗，故以下 onboarding 條目標為綜合建議，不冒稱 Apple 要求。
- 【未查到】本研究沒有市場採用率資料，不為 component 排名，也不把 2026 更新日期當成 UI 趨勢證據。

## How should the book express actionable scenario rules?

### Takeaway

以下 90 條是可供正文採用的原創情境規則，全部屬【推論／綜合設計建議】。括號來源 ID 表示推理基礎而非聲稱官方逐字規定；範例與反例為本次撰寫。每條先給判斷，再給做法、例子與適用邊界。

### Cited Findings

本節依前節 S01–S21 的可點擊來源建立。正式編入書中時，應將來源 ID 改成章節就近的來源連結，並保留第 3 節的差異說明。

### Inferences

#### Actions and Labels

1. **當操作要改變資料或狀態時，就應該使用 button 語意。** 好：以「封存專案」按鈕執行封存；壞：用沒有 href 的文字假裝連結。若只是前往專案頁，使用 link。基礎：S02。
2. **當操作會導向另一個可定位頁面時，就應該使用真正的 link。** 好：訂單編號可開新分頁；壞：整列只有 click handler，無法複製網址。頁內開 modal 則屬動作。基礎：S02。
3. **當同一任務有主要與次要出口時，就應該讓主要操作更突出。** 好：「建立專案」為實心，「取消」為低強調；壞：兩者都用醒目品牌色。多個獨立區塊可各有自己的主操作。基礎：S01。
4. **當按下後會產生具體結果時，就應該把結果寫進按鈕。** 好：「儲存地址」；壞：「確定」卻實際送出訂單。純確認已讀訊息才可用「知道了」。基礎：S01、S13。
5. **當提交仍欠缺資訊時，就應該讓使用者知道缺少什麼。** 好：可提交並定位錯誤，或在 disabled 操作旁顯示前提；壞：灰色按鈕無說明。不要只把原因藏在 disabled 按鈕 hover。基礎：S01、S09。
6. **當送出可能被連按時，就應該立即顯示處理狀態並防止同一請求重複執行。** 好：「送出中」加 server 去重；壞：只延遲關按鈕而產生兩筆訂單。取消操作是否保留取決於能否真正取消。基礎：S01、S16。
7. **當 icon 的意思可能被誤解時，就應該加可見文字或可存取名稱。** 好：「下載報表」文字搭配箭頭；壞：三個未命名箭頭。熟悉且密集工具列可只顯示 icon，但仍要名稱。基礎：S02。
8. **當同一按鈕切換狀態時，就應該讓名稱與 pressed 語意保持一致。** 好：固定「釘選」搭配 pressed 狀態；壞：「取消釘選，已按下」混雜兩種描述。也可改用動作名稱切換，但不要同時矛盾使用。基礎：S02。
9. **當目前模式會改變按鈕後果時，就應該讓後果就地可見。** 好：批次工具列寫「封存 12 筆」；壞：離開勾選區才看到泛稱「執行」。大量操作可再有摘要。基礎：S01、S13。

#### Choice Controls

10. **當答案可同時包含多項時，就應該使用 checkbox。** 好：通知管道可同選 email 與簡訊；壞：用 radio 迫使只能選一個。若項目彼此互斥，改單選。基礎：S04。
11. **當同組答案只能選一項時，就應該使用 radio 或單選 select。** 好：配送方式三選一；壞：三個 checkbox 到提交才說只能勾一項。需要直接比較差異時優先展開。基礎：S05。
12. **當設定只有開關兩態且立即套用時，就應該考慮 switch。** 好：開啟深色模式立即生效；壞：開關切了還要到頁尾儲存卻未提示。整份設定統一提交時改 checkbox 或清楚標示暫存。基礎：S06。
13. **當選項數量多且使用者知道名稱時，就應該提供可搜尋選取。** 好：輸入員工姓名縮小候選；壞：要求捲動五百人名單。短且易比較集合不必增加搜尋。基礎：S07。
14. **當可搜尋欄位只接受既有項目時，就應該清楚區分輸入文字與已選值。** 好：選中部門後顯示確定的部門名稱；壞：打了不存在名稱仍像已完成。允許新建時明示「建立新部門」。基礎：S07。
15. **當選項有成本或後果差異時，就應該把差異放在選項旁。** 好：配送選項列到貨日與運費；壞：選完才揭露加價。較長解釋可提供展開資訊。基礎：S04、S05。
16. **當複選含「以上皆非」時，就應該讓它與其他選項互斥且結果可預期。** 好：選「皆非」清掉其他值並顯示狀態；壞：「皆非」與三個項目同時勾選。不可靜默帶入與畫面不同的資料。基礎：S04。
17. **當某選擇會顯示額外欄位時，就應該把欄位放在該選擇附近。** 好：「其他」後出現說明欄；壞：頁尾突然多一段看不見的問題。改選後隱藏欄位是否保留資料要明確。基礎：S04、S05。
18. **當選項需要使用者主動同意時，就應該避免偷偷預選。** 好：使用者自行選擇是否收促銷；壞：把購買必要動作和行銷同意混在一起。本條是信任與控制權建議，非本研究法律結論。基礎：S04、S05。

#### Fields and Input

19. **當使用者開始輸入後仍需確認欄位用途時，就應該保留可見 label。** 好：email 上方固定標籤；壞：placeholder 打字後消失只剩字串。浮動 label 仍需足夠可讀與測試。基礎：S03。
20. **當格式會影響成功率時，就應該在輸入前提供 hint。** 好：「發票號碼，例如 AB12345678」；壞：輸入失敗才說格式錯。hint 應與欄位程式化關聯。基礎：S03、S08。
21. **當某些欄位可以不填時，就應該用一致方式標出選填。** 好：「分機（選填）」；壞：只靠星號顏色猜必填。若大多選填，也可明示少數必填，整頁規則需一致。基礎：S03、S08。
22. **當問題可以用系統已有資料回答時，就應該先提供帶入或確認。** 好：顯示已驗證的聯絡地址供修改；壞：每一頁重新輸入同資料。資料可能過期或敏感時讓使用者確認。基礎：S11、S18。
23. **當內容通常是一段描述時，就應該提供 textarea。** 好：退貨原因可換行；壞：長文塞進窄單行欄位。若後端只接受短代碼則仍用單行。基礎：S03。
24. **當輸入值是代碼而非算術數量時，就應該保留前導零與格式。** 好：郵遞區號「00123」不變成 123；壞：一律用 number 讓瀏覽器處理成數值。可用文字欄位搭配合適 inputmode。基礎：S03、S10。
25. **當有安全且無歧義的格式差異時，就應該容忍差異。** 好：電話允許合理空白；壞：每個空格都報錯。不要對密碼或有意義識別碼任意 trim、改大小寫。基礎：S08、S20。
26. **當欄位有字數限制時，就應該在接近限制時提供可理解的計數。** 好：「還可輸入 24 字」；壞：提交時才丟棄超長段落。需先定義字元、字數或 byte 計算方式，畫面與 server 一致。基礎：S08。
27. **當多個欄位共同回答一個問題時，就應該提供群組標題。** 好：日期欄位共享「開始日期」並各有年/月/日標籤；壞：只有三格無上下文數字。基礎：S04、S05、S10。

#### Validation and Recovery

28. **當使用者還未完成輸入時，就應該避免過早宣告格式錯誤。** 好：email 打到 `vic@` 時先不責備；壞：第一個字就全紅。真正有益的即時長度提示可例外。基礎：S08。
29. **當設計一般低頻服務表單時，就應該先以提交驗證作基線，再驗證是否需要 blur。** 好：填完整頁後一次得到可修復錯誤；壞：一律套用失焦紅字。高頻 enterprise modal 可能採 blur，但需測試收益。基礎：S08、S13。
30. **當錯誤已被指出而使用者正在修正時，就應該及時移除過期錯誤。** 好：合法日期輸入完成後不再顯示月份錯誤；壞：紅字一直留到下一次提交。檢查成本高時可顯示重新驗證中。基礎：S08、S13。
31. **當提交有多個錯誤時，就應該提供可跳到欄位的摘要。** 好：摘要「請填聯絡 email」連到該欄；壞：只在頁頂寫「資料不正確」。GOV.UK 對單一錯誤亦要求摘要，其他產品依頁面長度與測試決定。基礎：S09。
32. **當欄位驗證失敗時，就應該說明怎麼改。** 好：「結束日期需晚於開始日期」；壞：「Invalid input」。無法安全提供細節的登入錯誤是例外。基礎：S08、S19。
33. **當普通表單提交失敗時，就應該保留已輸入資料。** 好：只修一個錯字就能重送；壞：整張申請表清空。密碼、付款秘密等敏感欄位另依安全設計處理。基礎：S08、S19。
34. **當錯誤發生在 server 而不是使用者輸入時，就應該給服務失敗訊息。** 好：「暫時無法儲存，內容已保留，請重試」；壞：將全部欄位標紅。基礎：S08、S13。
35. **當使用者缺乏權限時，就應該說明權限狀態與可行出口。** 好：「需專案管理員授權，聯絡管理員」；壞：把正確輸入標成格式錯誤。敏感資源存在與否仍要避免洩漏。基礎：S08、S17。
36. **當資料必須經遠端檢查時，就應該區分檢查中、可用與檢查失敗。** 好：帳號名稱顯示「檢查中」而非預先綠勾；壞：網路失敗就說名稱已使用。送出時仍需權威端重新驗證。基礎：S08、S16。

#### Dates and Multi-step Work

37. **當日期是使用者已知的歷史值時，就應該允許直接輸入。** 好：出生日期可直接填年月日；壞：只能連按月曆回到三十年前。分欄順序依語系清楚標明。基礎：S10。
38. **當日期選擇取決於可用時段時，就應該顯示日曆或可預約清單。** 好：訂房可看可用晚數；壞：先輸入後才逐次告知不可訂。仍提供鍵盤操作與明確日期文字。基礎：S10、S12。
39. **當系統接受日期範圍時，就應該顯示起訖與範圍結果。** 好：「10/30–11/02，共 3 晚」；壞：兩個相同未命名的 date picker。業務上日數是否含結束日需明確。基礎：S10。
40. **當時間跨時區時，就應該在決策點顯示時區。** 好：會議「09:00 台北時間」；壞：只寫 09:00 讓旅客猜測。使用者旅行時需分清裝置時區與活動時區。綜合建議，非 S10 明文要求。
41. **當流程長到一次呈現會造成負擔時，就應該依有意義任務拆步驟。** 好：聯絡資料→配送→確認；壞：每一欄都一頁而無實際好處。短表單不用為了 stepper 強拆。基礎：S11、S13。
42. **當流程可往返修改時，就應該保留前一步資料。** 好：從確認頁返回地址仍保留其他答案；壞：回上一頁整段重填。上游選項改變下游答案時，說明需重確認的內容。基礎：S11。
43. **當步驟數會依答案改變時，就應該避免承諾不可靠的固定百分比。** 好：顯示目前階段名稱；壞：顯示 90% 後突然多十頁。總數穩定時可用完整步驟進度。基礎：S11、S16。
44. **當最後送出會造成重要後果時，就應該提供可編輯的確認摘要。** 好：送申請前看到申請人、項目與日期；壞：直接從最後欄位跳成功。小型可撤銷操作通常不需此頁。基礎：S11。
45. **當流程允許稍後繼續時，就應該明確區分草稿與正式送出。** 好：「已儲存草稿，尚未送審」；壞：單一綠勾讓人以為流程完成。可恢復期限與跨裝置能力需如實說明。基礎：S01、S21。

#### Identity and Onboarding

46. **當使用者輸入密碼時，就應該支援貼上與 password manager。** 好：可自動填入與顯示密碼；壞：阻擋貼上迫使手打。隱藏預設與顯示切換都要有清楚名稱。基礎：S19、S20。
47. **當登入失敗時，就應該提供能恢復而不洩漏帳號存在性的訊息。** 好：「帳號或密碼不正確」加重設入口；壞：「此 email 存在，但密碼錯」。基礎：S19、S20。
48. **當驗證碼由外部管道取得時，就應該支援整串貼上。** 好：貼六碼即可填入；壞：六個框要求逐格切換。到期、重寄等待與驗證失敗需有明確狀態。綜合建議，參照 S03、S08 的輸入與恢復原則。
49. **當登入中斷原本任務時，就應該在登入後返回原任務。** 好：登入後仍回到原本待編輯專案；壞：總是送到首頁而丟失目的。無權限或資源已失效時說明原因。綜合建議，參照 S08、S17。
50. **當需要權限才能完成某功能時，就應該在有上下文的時機解釋用途。** 好：使用掃描時說明需要相機；壞：首次進站連續索取多種權限。拒絕後保留可行替代流程。綜合建議，參照 S17。
51. **當初次使用需要學會核心操作時，就應該引導完成一個真實任務。** 好：建立第一筆項目時介紹必要欄位；壞：先強迫看十張功能介紹。需要安全訓練的工具可保留必要教學。綜合建議，參照 S17；非 Apple 已核實要求。
52. **當教學不是使用前提時，就應該允許跳過並稍後重開。** 好：「稍後再看」及說明中心入口；壞：每次登入都自動播放導覽。必須完成的法定或安全內容不以可跳過建議覆蓋。綜合建議，參照 S17。
53. **當展示範例資料時，就應該讓它與真實資料可辨識。** 好：樣本專案標「示範」並可清除；壞：假訂單混進正式 dashboard。若示範含可執行操作，明示是否有真實副作用。綜合建議，參照 S17。
54. **當使用者換帳號或 workspace 時，就應該清楚展示當前身分與範圍。** 好：邀請視窗寫「加入 A 公司」；壞：操作完成後才知道改到 B 公司。高後果動作在確認點重申範圍。綜合建議，參照 S11、S13。

#### Overlays and Focus

55. **當任務必須暫停背景才能完成時，就應該使用真正的 modal。** 好：確認不可逆刪除時背景不可操作；壞：視覺蓋黑但鍵盤仍進入背後控制。若需要比較背景資料，改非 modal panel。基礎：S12。
56. **當工作會頻繁進行或包含很多步驟時，就應該優先放在頁面。** 好：大型訂單編輯有自己的頁；壞：在小 modal 捲動十個區塊。短暫補充小欄位仍可用 modal。基礎：S13。
57. **當使用者需要邊看列表邊改細節時，就應該考慮非 modal drawer。** 好：側欄顯示選中任務並保留列表上下文；壞：每次都打斷列表操作。窄螢幕可轉完整頁或 modal，並同步調整 focus 行為。綜合建議，參照 S12、S13。
58. **當浮層包含可點連結或表單時，就應該使用支援互動的 popover/dialog。** 好：通知偏好浮層可正常 Tab 進去；壞：把互動按鈕塞進 tooltip。基礎：S14，該 APG 頁仍為草案。
59. **當提供補充 tooltip 時，就應該讓鍵盤使用者也能觸發與關閉。** 好：focus 出現、Escape 收起；壞：只有滑鼠 hover 才看得到。完成任務必需的資訊仍應直接顯示。基礎：S14，草案性質需保留。
60. **當 modal 打開時，就應該把 focus 移到最適合開始理解內容的位置。** 好：長確認內容先聚焦標題；壞：總聚焦最底部按鈕跳過全文。簡短表單可從首欄開始。基礎：S12。
61. **當 modal 關閉時，就應該把 focus 還給合理工作位置。** 好：取消後回到「新增」按鈕；壞：focus 掉到頁面頂端。觸發項目已刪除時移到下一項或列表標題。基礎：S12。
62. **當即將執行難以撤銷的行動時，就應該避免讓初始 focus 鼓勵誤觸破壞性操作。** 好：先聚焦取消或摘要；壞：Enter 習慣性連按直接刪除。仍需依平台語意與操作頻率測試。基礎：S12。
63. **當關閉浮層會丟失未儲存內容時，就應該讓使用者選擇保留或放棄。** 好：「繼續編輯／放棄變更」；壞：點背景就清空表單。已自動存草稿時可直接關閉並說明保存狀態。綜合建議，參照 S13。

#### Feedback and Waiting

64. **當操作成功且不需後續決定時，就應該提供低干擾 feedback。** 好：收藏狀態更新並簡短提示；壞：每次收藏都要求按「確定」。結果本身已明確時不必額外 toast。基礎：S15。
65. **當訊息需要使用者採取行動時，就應該讓它持續可找到。** 好：上傳失敗留在檔案列並提供重試；壞：錯誤 toast 消失後無處查。非關鍵短狀態可短暫顯示。基礎：S15。
66. **當問題影響整個頁面或服務時，就應該用對應範圍的通知。** 好：離線 banner 出現在工作區上方；壞：每個欄位都顯示同一網路錯誤。單一欄位錯誤應就地呈現。基礎：S15、S08。
67. **當載入只影響局部內容時，就應該只替該區塊呈現等待狀態。** 好：報表更新時導航仍可用；壞：整個 app 每次都全屏 spinner。操作要求原子完成時可限制相關區域。基礎：S16。
68. **當初次載入的內容結構已知時，就應該考慮對應結構的 skeleton。** 好：列表骨架符合真實列高；壞：假骨架先放滿全頁又整頁跳動。未知結果或純計算則可用狀態文字。基礎：S16。
69. **當能量測完成進度時，就應該顯示真實進度。** 好：「已處理 240 / 500 筆」；壞：假百分比停在 99%。總量未知時明示處理中，不假裝精準。綜合建議，參照 S16。
70. **當工作可能持續較久時，就應該提供離開後仍能追蹤的方式。** 好：匯出成背景任務，完成後到下載中心領取；壞：要求一直盯著 spinner。需使用者等待的流程應如實解釋。綜合建議，參照 S16、S21。
71. **當任務可以取消時，就應該讓取消的後果可理解。** 好：「停止上傳」並說明已傳檔案仍保留；壞：按取消只關視窗，後台繼續執行卻沒提示。不可取消時不要提供假取消。綜合建議，參照 S16。
72. **當資料只是背景刷新時，就應該保留可用內容並標明刷新。** 好：舊資料仍顯示並標「更新中」；壞：每隔十秒整表清空成 skeleton。舊值不安全時改顯示不可用而不是假即時。綜合建議，參照 S16。

#### Empty States and Destructive Actions

73. **當是首次沒有資料時，就應該告訴使用者第一步。** 好：「尚無專案，建立第一個專案」；壞：空白區只放插畫。功能受權限限制時不要提供做不到的 CTA。基礎：S17。
74. **當是搜尋或篩選後沒有結果時，就應該提供調整條件的方法。** 好：「沒有符合項目，清除篩選」；壞：提示建立新資料，彷彿資料庫是空的。基礎：S17。
75. **當資料未取得是因錯誤時，就應該顯示失敗而不是空資料。** 好：「無法讀取訂單，重試」；壞：「目前沒有訂單」掩蓋 API 問題。基礎：S17。
76. **當正常完成工作後清單為空時，就應該肯定已完成狀態。** 好：「今天的待辦都完成了」；壞：以紅色錯誤標示清單空白。不必加入過度慶祝妨礙工作。基礎：S17。
77. **當操作可可靠撤銷且後果輕微時，就應該考慮直接操作加 Undo。** 好：移除一個篩選條件立刻生效；壞：每次都問「確定嗎」。Undo 必須真的可還原，不能掩蓋不可逆外部副作用。綜合建議，參照 S13、S15。
78. **當刪除會造成重大或不可逆損失時，就應該在執行前說明對象與後果。** 好：「永久刪除專案 Alpha，含 26 個任務」；壞：「是否繼續」。重要數字須由當前資料計算。基礎：S13。
79. **當刪除範圍容易被誤認時，就應該把範圍明確列出。** 好：「刪除此頁選取的 20 筆」或「全部搜尋結果 2,400 筆」；壞：只寫「刪除選取項目」。必要時提供明細。綜合建議，參照 S11、S13。
80. **當需要額外確認高風險對象時，就應該讓確認有助於辨識對象。** 好：要求輸入專案名稱以避免刪錯；壞：所有小刪除都要求輸入 DELETE。額外摩擦應與後果匹配。綜合建議，參照 S13。
81. **當交易已經完成時，就應該給可保存、可追蹤的確認結果。** 好：申請編號、送出時間與下一步；壞：瞬間 toast 後回首頁。等待審核不應寫成「已核准」。基礎：S21。

#### Upload, Autosave, and Offline

82. **當要求上傳檔案時，就應該在選檔前說明限制。** 好：標可用格式與容量，再提供選檔；壞：上傳到最後才說不接受。限制以實際後端能力為準。綜合建議，參照 S18。
83. **當提供拖放上傳時，就應該同時保留選檔入口。** 好：拖放區含「選擇檔案」；壞：只能把檔案拖進畫面。行動裝置與鍵盤使用者不能依賴拖曳。基礎：S18。
84. **當一次上傳多個檔案時，就應該逐檔顯示狀態。** 好：每列呈現完成、失敗及重試；壞：總訊息「上傳失敗」卻不知道哪一份。可只重試失敗項目以免重複。綜合建議，參照 S18、S15。
85. **當同一路程已上傳過同一文件時，就應該提供重用。** 好：選擇「剛才的證明文件」；壞：反覆要求重新找檔。共用裝置與敏感文件需限制預覽或下載。基礎：S18。
86. **當採用 autosave 時，就應該展示真實儲存狀態。** 好：「儲存中／已儲存／尚未同步」；壞：本地輸入就一律顯示「已儲存」。若僅儲存在本機，明示本機草稿。綜合建議，參照 S15、S16。
87. **當 autosave 失敗時，就應該保留內容並提供恢復方式。** 好：顯示重試與複製內容；壞：只顯示短暫 toast 然後關頁丟資料。敏感資料不能任意寫入長期本機儲存。綜合建議，參照 S08、S15。
88. **當使用者離線時，就應該區分可做與暫時不可做的事。** 好：可編輯草稿，送出顯示「連線後才能送出」；壞：所有操作都看似正常成功。離線佇列需說明真正送出時機。綜合建議，參照 S16、S17。
89. **當多端變更可能互相覆蓋時，就應該讓衝突可辨識與處理。** 好：顯示本地與伺服器版本供比較；壞：默默採最後寫入而丟掉長文。低價值設定可以採較簡單策略，但應符合預期。綜合建議，參照 S08、S15。
90. **當重新連線可能觸發外部副作用時，就應該讓執行狀態與重送行為可追蹤。** 好：待送訊息列出「待送／已送／失敗」；壞：使用者以為已取消的訂單在恢復連線後送出。重要交易重送前需確認狀態及避免重複。綜合建議，參照 S01、S21。

### Gaps

以上各條都不是可脫離情境的法律或通用規範。時間門檻、選項數量、toast 秒數、欄位數量等沒有在此列出固定值，因為本次沒有足夠證據支持跨產品通用數字。

## Which conflicts and boundaries must the final book preserve?

### Takeaway

將設計系統的局部規範寫成萬用規則，會比沒有 cheat note 更危險。正文應直接帶適用條件，不要把所有例外塞到書末。

### Cited Findings

- 【事實】驗證時機存在明確差異：GOV.UK 建議等提交；Carbon modal 建議可在欄位失焦時做 inline validation。這是來源間不同場景的指引，不應隱藏差異。[GOV.UK validation](https://design-system.service.gov.uk/patterns/validation/)、[Carbon modal](https://www.carbondesignsystem.com/building-blocks/core/components/modal/guidelines)
- 【事實】APG modal 允許依內容調整初始 focus，特別提到不可逆行動可聚焦最不破壞性選項；Carbon modal 較一般地描述首欄或主要按鈕。採用 APG 情境細分可避免危險誤觸。[APG modal](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)、[Carbon modal](https://www.carbondesignsystem.com/building-blocks/core/components/modal/guidelines)
- 【事實】APG Tooltip 是尚未獲 task force consensus 的 work-in-progress，不是可宣稱已定案的標準。[Tooltip](https://www.w3.org/WAI/ARIA/apg/patterns/tooltip/)

### Inferences

- 【推論】採用某設計系統時，優先讓同一產品的互動一致，但對不可逆後果與 accessibility 需要較精細的判斷。
- 【推論】book 中以「建議」標識 UX 決策，以「WCAG 成功準則」標識真正標準，兩者不應混為一談。
- 【推論】具體範例使用專案、訂單、報表等熟悉情境，能讓 React 開發者直接轉成畫面決策，避免只背 component 名稱。

### Gaps

- 【未查到】沒有研究可支持「本書全部建議一定提高 conversion」；是否改善需以任務成功率、錯誤率及實際 usability test 驗證。
- 【未查到】無法從官方系統文件推出「2026 所有產品都改用某外觀」。本文件聚焦互動模式，不推測流行視覺風格。
