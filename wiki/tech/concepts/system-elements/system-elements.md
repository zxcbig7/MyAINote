## 3.1 導論：在建模之前，先看清楚系統裡有誰

在 [[mp-model-fundamentals]] 中我們已經知道，一個 mathematical programming 模型最終會落成 decision variables、constraints 和 objective function。但在動筆寫出第一條 constraint 之前，García Sánchez 的方法論要求先做一件更基礎的事：把系統裡「誰在參與」講清楚。這些參與者就是本章的主題——elements。

Elements 是系統裡的個別行動者或實體：它們是系統的輸入、系統使用的資源，也是系統產出的結果。它們的性質可以是任何東西——材料、工具、人員、地點、物件——也可以是被定義在其他元素之上的類型（typology），甚至是空間或時間這種資源。元素之所以重要，是因為它們要嘛參與系統中發生的 activities，要嘛提供了 specifications 或 objective 所需要的資訊。換句話說，元素是連接「現實世界的描述」與「數學模型」的第一座橋。

哪些東西算元素、哪些不算，書裡給出一個實用的判準。算作元素的包括：任何參與系統的實體或人物（人、地點、機器、工具、零件、產品）；決策發生或規格被提出所依據的時間區段；系統中對其他元素定義出來的類型；以及系統中出現的階段、流程、模式或狀態。不算元素的則有兩類：純粹的計量單位（公斤、公克、小時、分鐘、公升、歐元、件數等）本身不是元素，它們只是資料的量測單位；以及系統中沒有被特別記錄下來的動作，也不會被當成元素。

這個判準聽起來簡單，但實務上常常需要反覆推敲。書中用一個貫穿全章的例子說明：一家公司有四個供應商，要決定跟每個供應商買多少單位以滿足市場需求。光看敘述，在還沒拿到價格、折扣、交期等任何資料之前，我們已經能單靠描述本身列出元素清單：四個供應商、公司本身（也就是系統）、產品、市場。這說明了一個重要的原則——元素的初步識別不需要等到資料齊全，甚至有些被列出來的元素最後可能根本不參與最佳化問題，這都無妨，先列出來不會妨礙後續建模。

另一個例子把這個原則推得更遠：有一組 100 個物件（各有重量、高度、寬度）要分配到 25 個貨架、每個貨架又由 10 個 section 組成，目標是在符合寬度、高度、承重限制下，把最多物件放進去。這裡的元素清單包含每一個物件、每一個貨架、以及每一個貨架底下的每一個 section——換言之，元素的顆粒度可以细到「貨架裡的每一個 section」這麼具體。

值得特別記住的是：系統本身永遠可以被視為一個元素。當某些資料或規格只能歸屬於「整個系統」而不屬於任何具體的參與者時（例如全系統的總產能上限），我們就把這個值掛在「系統」這個元素上，而不必勉強塞進某個實體元素裡。

最後，元素的識別本身有一個看似違反直覺、但貫穿全章的核心觀念：**一個系統的元素清單不是唯一的**。同一個真實系統，可能可以用兩種、甚至三種不同方式列出元素，而每一種都是「可接受」（admissible）的模型設定，差別只在於模型的效率高低。這個觀念會在 3.3 節與 3.4 節反覆出現，也是這一章之所以重要的原因——正確識別元素不是背答案，而是一種要練習的判斷力。當元素數量夠多、彼此性質相同時，我們可以把它們組織成 **Set**，這件事會在 3.4 節詳細展開。

## 3.2 元素的資料：屬性從哪裡來、屬於誰

元素被識別出來之後，下一步是搞清楚它「帶著什麼資料」。資料是元素的特定性質或屬性（attribute），用來定義這個元素在系統中的樣子。這裡有一個對建模極為關鍵的區分：元素的屬性值，有些是「已經決定、不會再變」的（這些才叫做 data，必須有明確的數值），有些則是「值尚未決定、要靠最佳化過程去求出來」的——後者其實就是後面 [[decision-activities]] 要處理的決策變數雛型，不是本章的資料。

書中用一個簡單例子把這個界線畫出來：某系統要製造貨櫃，貨櫃的高度是 4 公尺、寬度是 3 公尺（已知），但貨櫃的「長度」要由系統決定，好讓一批已知尺寸的棧板能夠裝下。這裡高度與寬度是資料，因為它們的值已確定；長度不是屬性，因為它的值尚待決定——它會變成之後的決策變數所量測的對象。另一個更直接的例子：一項產品的利潤是每單位 10 元、市場需求是 1000 單位，這兩者都是資料，各自代表這個「產品」元素的一個 attribute。

多數資料表達的是連續或整數的量，但邏輯值與元素之間的連結關係，也會用二元值（1/0）當作資料來表達，用來表示某個元素是否具備某種能力、或元素之間是否存在某種邏輯關聯。這類資料的分類方式會在 3.2.3 節詳細討論。

一個 attribute 由兩個部分組成：一個「定義」（名稱、在模型中要用的參數符號、所屬關係、值的型態）加上一個「數值」。這個結構之後會落成一張標準化的 Table of Elements，在 3.2.4 節說明。

### 3.2.1 Own 與 Shared：屬性屬於一個元素，還是屬於關係

資料按照「歸屬」（belonging）可以分成兩種。**Own Attribute（自有屬性）**只屬於一個元素本身，不涉及任何其他元素。**Shared Attribute（共享屬性）**則描述的是元素之間的關聯——它的值是由多個元素共同決定的，邏輯上這個值可以歸給任何一個共享它的元素，但它並不是被某個函數在元素之間「分配」出來的，而是完整地同時歸屬給每一個共享它的元素。

書中沿用一個貫穿整章的基準例子來說明這個區分：一家奶油工廠生產兩種奶油（Sweet、Raw），用兩台機器（Pasteurization 機、Whipping 機）加工。若只看 Pasteurization 機這個元素，它的「每日可用時間 3.5 小時」是它自己的own attribute，不涉及其他元素。但「Sweet 奶油每公斤在 Pasteurization 機上需要 3 分鐘」這筆資料，同時關係到「Pasteurization 機」與「Sweet 奶油」兩個元素——它是一個 shared attribute，該被同時記錄在兩者身上（實務上通常只需要在其中一個元素上寫出參數定義，另一邊沿用同一個參數即可，避免重複）。

這裡也順帶埋了一個重要的實務提醒：系統中有些數值，其實是直接依附在 activities 或 system calculations 上的（也就是牽涉到 decision variable 或其函數的值），這類數值不必勉強掛在某個元素的屬性上，硬要塞反而容易造成模型設計不良。哪些值該歸給元素、哪些該留給後面的 activity 或 calculation 去處理，是需要經驗判斷的地方，這個界線會在 [[system-calculations]] 講計算類型時看得更清楚。

### 3.2.2 Primary Element：共享屬性裡誰是主角

當一個 shared attribute 所描述的，其實是「某一個共享元素自身的量」時，那個元素就叫做這段關係裡的 **Primary Element（主要元素）**，其餘共享此屬性的元素只是扮演次要角色。最典型的情況，就是這個屬性代表某個元素的數量值。

用批發服飾的例子最容易理解：百貨公司有 200 件襯衫、100 件長褲庫存，設計兩種組合優惠 Batch Offer A、B。「Offer A 裡有 1 件襯衫」這筆資料同時關聯到「襯衫」與「Batch Offer A」兩個元素，但它描述的其實是「襯衫」的數量，所以襯衫才是這段關係裡的 primary element。書中在完整的 Table of Elements 裡特地加了一欄「Primary element」，把這種歸屬關係標示出來，方便之後查核。

但並非所有 shared attribute 都有主角。有些共享屬性描述的不是任何單一元素的量，而是所有共享元素平等共有的一個性質——這種情況常見於二元值屬性，例如「這個門市是否座落在某個行政區」，或「某中心是否可以配置某種生產模式」。這類沒有主角的共享屬性，通常代表的是元素之間的相容性（compatibility）或連結（link），而不是誰的量。書中用工廠設置的例子說明:每個工作中心對三種生產模式各有不同的相容性（Center 1 只能裝 Mode 1，Center 2 只能裝 Mode 2、3……），這張「相容性表」就是一個沒有主角的 shared binary attribute，同時屬於「中心」與「模式」兩種元素。

判斷一個屬性有沒有 primary element，決定了之後在 [[decision-activities]] 中要怎麼寫決策變數的下標，也會影響 3.2.3 節要介紹的「資料型態」該選哪一種。

### 3.2.3 資料的型態：連續、次序、二元

每個 attribute 都有一個對應的數值型態，書裡整理成三類：

**連續或整數量（Continuous or Integer Quantity）**：這是最直覺的一種，代表某種可測量的量，例如長度、體積、重量、時間；若是連續值可以指定量測單位，若是整數則是計件的數量。這裡書中特別提醒一個常見的陷阱：用文字描述數量時，很容易把「不定冠詞」（indeterminate article，像英文的 a/an）跟「數詞」（numeral）搞混。例如「一個產品需要一台 A 機器和兩個 B 工具」，這裡「一個產品」是不定冠詞（不是屬性），但「一台」和「兩個」才是真正的數量屬性。分辨方法是試著把該詞換成「每個」（each）——「每個產品需要一台 A 機器和兩個 B 工具」讀起來通順,就代表原本那個詞其實是數詞、是屬性;反過來，如果一句話講的是「工廠有四台機器 M1、M2、M3、M4」，這裡「四」只是在描述元素的個數，而不是某個元素的屬性,通常不需要另外記錄。

**次序值（Ordinal）**：屬性值是一個整數，代表某份選項清單裡的第幾項，這份清單裡的選項可以選擇要不要被列為正式的元素。書中用「20 件物品、每件有顏色（白/紅/黑）與重量，要分裝進 10 個 section、同一 section 內顏色不可混雜」這個例子示範：可以直接把顏色編碼成次序值 1（白）、2（紅）、3（黑），存在「物品」這個元素的 own attribute 裡。但次序值有一個限制——它只適用於「一個元素對應清單裡一個選項」這種單純關聯；如果一個元素可能同時對應多個選項（例如一件物品有多種顏色），次序值就不夠用了，必須改用二元值。

**二元值（Binary）**：用來表示「是/否」性質，是三種型態裡最有彈性的一種,因為它允許多重關聯。當一個屬性的值本質上是在指向「另一個元素」時（也就是上一節提到的、沒有 primary element 的 shared attribute），解法就是在兩個元素之間建立一個 shared binary attribute。因此二元值特別常用來表達元素之間的「所屬關係」（belonging）或「相容性」（compatibility）。回到剛才的顏色例子，如果我們把「白/紅/黑」本身也升格成三個獨立的元素，物品跟顏色之間的關聯就要用三個 shared binary attribute（White_Colour、Red_Colour、Black_Colour）來表示,而不再是一個次序值——這也示範了同一份資料,可以依照顏色是否被視為元素,在「次序值」與「二元值」之間轉換設計。

三種型態的選擇並非誰對誰錯,而是要看「這份資料在系統裡實際被使用的方式」——是否需要被當成獨立元素參照、是否有多重關聯、後續在 activities 與 specifications 裡要怎麼引用它,才是決定型態的依據。

### 3.2.4 用表格記錄元素（Table of Elements）

前面三節的資訊,書裡統一收斂成一張標準表格,叫做 **Table of Elements**。每一列描述一個 attribute,固定包含以下欄位:名稱(name)、在模型中使用的參數符號(parameter)、值的型態(C 連續 / I 整數 / O 次序 / B 二元)、歸屬(W 表 Own / S 表 Shared),以及數值。如果這個屬性有 primary element,還會多一欄標出來。

這張表格的價值在於,它把「識別元素」與「定義資料」這兩件原本容易在描述文字裡糾纏不清的事,拆成一個可以逐列核對、逐列補齊的清單。書中把奶油生產的例子完整地攤開成一張表:Pasteurization 機的 own attribute 是使用時間(180 分鐘);它與 Sweet butter、Raw butter 之間各有一個 shared attribute(每公斤加工所需的分鐘數);Sweet butter 與 Raw butter 各自的 own attribute 是利潤。這張表也示範了一個簡化技巧——同一個 shared attribute 只需要在其中一個共享它的元素列出完整定義,其餘元素只需要註記使用同一個參數即可,不必重複整段定義。

### 3.2.5 衍生資料:從既有資料算出新資料

為了讓之後的 specifications 更容易寫,有時候值得先從既有資料算出一份新的、衍生的資料,再把這份新資料也記錄成某個元素的屬性。書中的例子是:奶油生產系統想知道「哪些奶油每公斤加工需要超過 8 分鐘」,這個判斷可以先算出一個二元屬性(是/否超過 8 分鐘),掛在 Sweet butter、Raw butter 各自的 own attribute 底下,之後的 specification 就能直接引用這個算好的旗標,而不必每次都重新做一次比較。

這一節其實是在為後面整整一章的內容(系統中的計算,見 [[system-calculations]])埋伏筆——什麼時候該把一個值算成「元素的靜態資料」、什麼時候該把它算成「跟著決策變數變動的系統計算」,是判斷模型設計好壞的重要分水嶺,書裡會在該章展開得更完整。

## 3.3 元素的量化性質:individual 與 collective

如果說 3.2 節在談「元素帶著什麼資料」,那麼 3.3 節談的是一件更根本的事——**這個元素本身,在系統裡是以什麼樣的量化方式存在**。這叫做元素的 **quantitative nature(數量性質)**,書裡把它分成兩大類、四種子類型,是本章份量最重、也最容易在初學時搞混的一節。

**Individual Element(個體元素)**代表一個個別實體,它在系統中的離散數量就是「這一個」,元素本身即為計量單位。多數我們日常直覺會想到的「一台機器」「一個產品種類」都屬於這類。但 individual element 底下還要再細分,依據它是否帶有一個「值尚未決定、且會被連續地部分使用」的性質:

- **I.1 Unitary Individual Element(單一個體元素)**:這個元素沒有任何在決策中可以被連續量測、或部分使用的性質。就算它有連續屬性,這個屬性也只會被整體使用(不能切割),或者它的部分使用是靠邏輯/整數決策達成的,而不是連續決策。如果它擁有 shared measurable data,它也絕不會是那段關係裡的 primary element。
- **I.2 Measurable Individual Element(可量測個體元素)**:這個元素帶有一個值尚未決定的連續性質,或者它的連續資料可以透過連續決策被部分使用。當有 shared measurable data 存在於多個元素之間時,這個「可被量測」的性質會歸屬給該關係裡的 primary element。

回到奶油例子:Sweet butter 與 Raw butter 都是 measurable individual element,因為系統並不知道最終要生產多少公斤,這個「產量」正是有待決策決定的連續性質。相對地,Pasteurization 機與 Whipping 機是 unitary individual element——它們雖然有「使用時間」這個連續屬性,但這個時間的部分使用是透過一個函數(奶油產量 × 每公斤耗時)間接算出來的,系統本身並不需要直接對「機器使用了幾分鐘」做決策,所以機器的可量測性並不重要。

這裡書中特別演示了一件事,呼應 3.1 節提到的「元素清單不唯一」原則:同一個奶油系統,其實也可以換一種方式設定決策變數——改成直接決策「Pasteurization 機分配給 Sweet butter 的時間」、「分配給 Raw butter 的時間」等四個變數,而奶油產量則反過來變成由這些時間值透過下界計算導出。這樣一來,機器就變成 measurable individual element,而奶油產量的角色反倒退居計算結果。兩種設定在數學上是等價的,只是後者引入了更多變數,通常較不精簡。這說明了「量化性質」的判斷並非憑空而來,而是必須配合 [[decision-activities]] 一起分析才能確定——這也是為什麼書裡把量化性質的完整深入討論,留到專門的 [[quantitative-nature-of-elements|Ch.7]] 才展開。

**Collective Element(集合元素)**代表的則是一個「概念」,這個概念在系統裡對應著一批離散的單位,這批單位不管數量是否已知,都稱為這個 collective element 的 **items**。書中對 collective element 有一條硬性規定:它裡面的每一個 item 必須彼此完全相同——同樣的資料定義、同樣的數值——而且這批 item 絕對不能在決策或規格裡被個別地引用。collective element 永遠帶有可量測的特質(不論是在 activities 還是 specifications 裡),而且在整數決策變數中,一定會有一個 collective element 參與其中。依照這批 item 的總量是否已知,又分成:

- **II.1 Determined Collective Element(數量已定的集合元素)**:總量在系統描述中已經給定。
- **II.2 Undetermined Collective Element(數量未定的集合元素)**:總量本身也是系統要處理的未知量。

一個很有教育意義的例子是零件生產系統:市場上有三種機型(M1、M2、M3)可供採購,兩種生產模式各自需要固定數量的機台,工廠一天要生產 3000 個零件。這裡的「零件」是 determined collective element(3000 個零件,系統不會個別追蹤每一個零件),而「M1 機型」「M2 機型」「M3 機型」則各自是 undetermined collective element——雖然這三種機型彼此互不相同(不能合併成同一個 collective),但系統從頭到尾只在乎「要採購幾台某機型」這個數量,並不會去區分具體是哪一台機器,所以每種機型仍然是以數量而非個體的方式被處理。至於「生產模式」本身,則是 unitary individual element,因為模式沒有自己的連續屬性,只是與機台數量、生產速率之間有 shared data。

### 3.3.1 Collective Element 對上 Individual Items:分組的代價與好處

這一小節把「什麼時候該把一群東西合併成 collective element、什麼時候該堅持個別列為 individual element」的判準講得更清楚,而且用一個經典的 **knapsack problem** 示範得非常直接:

假設有一個容量已知的背包,和五件物品,每件各有自己的體積與價值,目標是在容量限制下讓放入背包的物品總價值最大。如果五件物品彼此的體積、價值各不相同,它們就必須各自被視為 individual element(而且是 unitary,因為背包對它們的使用是整體式的邏輯決策,而非連續量測),對應的決策變數就是五個各自獨立的二元變數 α₁…α₅,分別代表「是否放入這件物品」。

但如果換一個情境,五件物品其實可以分成兩組、組內物品完全相同(同樣的體積與價值,只是件數不同),此時系統描述也只用「這一組有幾件」這種方式提及物品、從未特別指名某一件,那麼這兩組物品就可以分別視為兩個 determined collective element,對應的決策變數也從五個二元變數,精簡為兩個代表「從這組拿幾件」的整數變數。書中甚至用代數把兩種設定的模型互相代換,證明兩者在數學上完全等價,只是後者變數更少、求解更有效率。

這個對比揭示了合併 item 為 collective element 的本質權衡:把一群本來各自獨立的 individual element 合併成一個 collective element 的 item,一定會損失一些「哪一個具體項目被選中」的關聯資訊(不過這份資訊通常在模型解出來之後還能還原);但換來的是變數數量大幅減少,一般而言模型的求解效率會更好。這個取捨原則,會在後面案例(例如把 180 位遊客依「行程+語言」偏好合併成 15 組)反覆被使用,也是為什麼把元素識別做對,能直接影響模型規模與求解速度的原因。

## 3.4 把元素組成集合(Sets)

當多個元素彼此性質相同、功能相同、資料定義也相同時,可以把它們組織成一個 **Set**,用下標(subscript)來指涉集合裡的每一個成員。這樣做的好處,是讓模型的數學表示與後續的程式實作都能大幅簡化——不必為每個機器、每種產品各寫一條一模一樣的 constraint,只需要寫一條帶下標的通式。

延續奶油例子:把 Pasteurization 機與 Whipping 機組成「機器」這個 set(下標 i = 1, 2),把 Sweet butter、Raw butter 組成「奶油」這個 set(下標 j = 1, 2),那些原本要分別寫四遍的「每公斤加工時間」,現在可以統一寫成一個帶雙下標的 shared attribute TM_ij,一行就把原本要佔四列的資料收斂完畢。要注意的是,一旦元素被納入 set,它們就改用集合內的順位(ordinal)來指涉,而不再各自保留專屬名稱。

### 3.4.1 補資料湊出集合

有時候一群元素幾乎可以組成同一個 set,只差某些成員缺了某個屬性。這時候可以主動幫這些成員「補上」一個中性、不影響問題結果的數值,讓所有成員的資料結構整齊劃一,藉此把它們統一納入同一個 set。書中的例子是三家供應商 P1、P2、P3,只有 P3 提供大量採購折扣,如果想把三者組成同一個「供應商」set,可以直接給 P1、P2 補上「折扣 = 0、門檻 = 100」這種形式上存在、但實質上不影響任何計算結果的資料,這樣三家供應商就能用統一的下標與屬性結構處理。

### 3.4.2 同一集合內的共享資料

一般來說一個 set 只用一個下標指涉。但如果資料描述的是「同一個 set 裡兩個成員之間」的關係,就需要用兩個下標來參照同一個 set——最常見的情境就是距離矩陣。書中舉了「四個城鎮之間兩兩距離」的例子:城鎮這個 set 的下標是 i、j(i, j = 1…4),距離這筆 shared attribute 就寫成 D_ij,同時參照到同一個 set 裡的兩個不同成員。這個例子也順便展示了一件事:一個元素(這裡是要選址的門市)完全可以不帶任何屬性,單純作為決策的對象存在。

### 3.4.3 階層式集合

當系統裡的元素彼此構成「父—子」的樹狀包含關係時,可以用「父層下標 + 子層下標」的組合來指涉子元素,前提是每個父元素底下的子元素結構都必須完全相同。這麼做可以顯著減少 Table of Elements 裡實際列出的元素數量,而父子之間的依附關係也就自然嵌入在下標裡,不需要再額外用一筆屬性去記錄。

書中的例子是 10 個箱子、每個箱子裡有 5 個完全相同的隔層,要把 30 件物品分配進隔層。如果不用階層結構,就得把 50 個隔層逐一編號(j = 1…50),再用一個屬性記錄每個隔層屬於哪個箱子;但如果採用階層式下標,隔層只需要在「箱子」下標 i 之下再編一次「隔層」下標 j(j = 1…5),依附關係就直接體現在 (i, j) 這組下標裡,對應的決策變數也就自然帶著三個下標(物品、隔層、箱子)。

## 3.5 資料生成元素:把隱含的關係變成明確的元素

3.2.2 節已經提過,沒有 primary element 的 shared attribute,代表的是元素之間平等共享的一段關係。這一節把這個觀念再往前推一步:**這樣的關係本身,有時候值得被拉出來,變成一個全新的、獨立的元素**,而不是永遠只當作兩個舊元素之間的一筆屬性。

要不要把一段隱含的關係升格成一個新元素,取決於系統中有沒有 decision activity 或 specification 直接落在這段關係本身上。如果沒有,把它留作屬性通常比較精簡;如果有,把它獨立出來當元素反而會讓模型更清楚。

書中用「市鎮之間是否可以互相調度物資」延伸出一組漂亮的對照:給定四個市鎮,已知彼此距離、以及兩兩之間是否可以調度。

- **設定一**:只把市鎮跟門市列為元素,距離與調度可行性都是市鎮之間沒有 primary element 的 shared attribute。
- **設定二**:另外新增一個「Connection(連結)」元素,把距離與調度可行性都改記錄成這個新元素自己的屬性,再用一個 shared binary attribute 把每個 Connection 跟它所連結的兩個市鎮綁在一起。四個市鎮兩兩配對,恰好產生 6 個 Connection 元素。
- **設定三**:延續設定二的想法,但改變 Connection 元素的下標方式——不再用自己的流水編號,而是直接用一組 (i, j) 元組(對應到它所連結的兩個市鎮下標)來指涉每一個 Connection,這樣市鎮之間的歸屬關係就內建在下標裡,不需要再另外用一個 shared attribute 去綁定,而且這種寫法剛好也相容於 LINGO 這類建模語言的 tuple 語法。

這節也用一個更早的例子補充說明「什麼時候乾脆不必把關係獨立出來」:一座城市有 20 個街區,每個街區有登記人口數,要決定一個資訊站該設在哪個街區的中心點,使全體居民到資訊站的總距離最小。這裡「居民」完全可以不當元素——因為沒有任何 decision 或 specification 是直接對居民本身下的,居民的角色只需要當作「街區」這個元素的一筆整數 own attribute(登記人口數)即可。書裡也順便示範了如果硬要把居民獨立成一個 collective element(數量已定),資料結構會怎麼變——多了一層转介,但沒有真的解決任何建模上的需要,純粹是選項之一。

## 3.6 圖形環境中的元素

當系統本來就是用圖(graph)來表示時(最常見於網絡最佳化問題),識別元素要多一個步驟:先依照文字描述辨認元素,再從圖本身把節點之間的圖形關係(通常是連結、涵蓋範圍或距離)萃取出來,當作資料。**連結(connection)**是圖形系統裡最常出現、也最需要處理好的一種屬性。

書中用一個博物館監視器佈建的例子(10 個房間、14 道門,兩種型號的監視器——A 型裝在門上、B 型裝在房間裡)說明這裡的判斷邏輯:房間與門都可以考慮設成 collective element 或 individual element,取決於後續有沒有 decision activity 直接落在它們身上。由於系統確實要對「每一道門裝不裝 A 型監視器」做決策,門就必須被明確列為 individual element(且是 unitary,因為門本身沒有連續屬性),而不能只當作房間之間的一筆共享屬性草草帶過——書中把「不把門獨立列為元素,只用房間對房間的一個二元屬性表示門的存在」列為**不建議**的替代設計,理由正是因為門上有實質的決策落在其上。監視器的兩種型號則各自是 undetermined collective element,各帶一個成本 own attribute。

在更抽象、標準的 graph G(N, A) 表示法裡(節點集合 N、邊集合 A),書中列出三種等價但實作考量不同的元素設定:節點本身列為 individual element、邊只當作節點之間的 shared binary attribute(最精簡);把邊也獨立列為 element(方便額外掛資料在邊上,例如邊的成本);或者用一組 (i, j) tuple 直接指涉每一條邊(相容於 LINGO 這類建模語言)。當節點帶有自己的權重、邊帶有自己的成本時,三種設定都可以自然擴充去容納這些額外資料。有向圖(directed graph)的處理方式類似,只是每個節點需要多帶「來源(source)」與「目的地(destination)」兩個 shared binary attribute,或者在 tuple 表示法裡把第一個下標視為起點、第二個視為終點。

## 3.7 時間元素

時間是最容易被誤解的一種元素——因為「時間」既可以是元素本身,也可以只是某個屬性的量測單位,這兩者必須分清楚。**只有當系統裡設立了好幾個明確的時段(天、週、月……),而 activities 或 specifications 是針對這些時段分別展開時,時間才需要被獨立列為元素**;而且這些時段元素通常是 unitary(除非時段本身還帶有需要被量測的連續資料,例如每個時段各自的可用產能)。

書中用兩個直接的例子建立基本感覺:一組任務要被排到一週七天的某一天執行,「七天」就是七個 unitary individual element;一項採購決策要逐月決定每月採購量,「十二個月」就是十二個 unitary individual element。

但書裡也花了不少篇幅釐清「時間參與系統、卻不需要被當成元素」的幾種情況:當某個元素(例如一項任務)有一個尚未決定的性質、而這個性質本身就是「它被排在哪個時間點」時,時間只是這個決策的量測單位,不必獨立成元素;當某筆時間資料只是描述某資源在系統裡的可用產能時(例如奶油機器的每日可用工時),它是資源的一筆屬性,而非元素;而當元素代表的任務或時段可以被部分地分配給其他元素、或者這個任務本身的長度需要被系統決定時,情況會更複雜,需要視系統實際的量測方式而定。

一個很有教學價值的綜合例子是短跑選手的訓練規劃:選手要在三週內,於速度、耐力、肌力三種訓練項目上分配訓練時數,每週有各自的目標總時數,而且有一系列複雜的邏輯限制(例如第三週速度訓練不能超過該週總時數的一半)。這裡「三種訓練項目」被設為三個 measurable individual element(各自有績效權重的 shared attribute、最低時數的 own attribute),「三週」被設為三個 unitary individual element(各自的可用時數是 own attribute)。書中特別指出,這個系統其實存在兩種同樣有效、但對稱互換的元素設定——一種是把「各週分配給各項目的時數」當成決策(訓練項目 measurable、週 unitary),另一種則反過來把週視為 measurable、項目視為 unitary——兩者互為鏡像,選哪一種純粹是設計上的偏好。至於選手本人,由於他隱含地存在於所有活動之中、卻沒有任何決策是直接對他本身下的,因此可以完全不必列為元素。

## 3.8 元素重複的陷阱

本章最後一個提醒篇幅雖短,卻是實務上很容易踩到的坑:**在描述系統時,如果用了兩種不同的說法去表達同一個概念,很容易在無意間把同一個東西當成兩個元素重複列出來。**

書中用奶油例子做示範:如果把原本的「Pasteurization 機、Whipping 機」改稱為「Pasteurization 流程(process)、Whipping 流程」,這其實只是換了個說法,流程與機器指的是同一件事,只要文字上有自覺,重新命名並不會產生問題,新的「流程」元素會直接取代原本的「機器」元素。但危險發生在措辭不夠精確的時候——書中示範了一段描述,裡面同時提到「Pasteurization 流程」與「用來執行這個流程的機器」,乍看像是兩個不同的東西,但仔細推敲後,兩者其實沒有任何屬性或用途是彼此區分開來的,說穿了它們就是系統裡的同一個元素。如果沒有察覺這一點,就會把同一份資料重複記錄在兩個名字底下,造成模型設計上不必要的混亂與冗餘。

避免這個陷阱的方法,就是每當識別出一個新元素候選時,回頭檢查:它跟清單上已經有的其他元素,是否真的在資料或功能上有所區隔?如果答案是否定的,它們就該被合併為同一個元素。

## 3.9 綜合範例:把方法論套進真實問題

本章最後用一組獨立的小案例,把前面所有觀念串起來,示範同一套判斷邏輯如何應用在不同性質的問題上。以下挑幾個最有代表性的來看。

**消防站選址**是一個示範「元素清單可以有一種以上正確答案」的好例子:五個轄區之間有一份「從某轄區出發回應另一轄區事故」的平均時間矩陣,以及各轄區的平均日呼叫頻率,要決定兩座消防站設在哪裡。第一種設定把兩座消防站視為 unitary individual element,因為文字描述始終只提到「轄區對轄區」的時間,並沒有真的針對某一座具體的站做出區分性描述;第二種設定則反過來,把消防站視為一個 determined collective element(2 個 item)。兩種設定都是合理的,取決於怎麼解讀原始描述。

**電視轉播攝影機佈建**是一個經典的 set covering 問題:10 個可能的攝影機架設點、25 個需要被涵蓋的場館區域,每個點能涵蓋哪些區域已知,某些區域(例如區域 9)一定要被涵蓋、某些區域(例如區域 1、2)甚至需要兩台以上攝影機同時涵蓋,目標是用最少的攝影機達成涵蓋。這裡場館區域與架設點都是 unitary individual element,涵蓋關係是一個 shared binary attribute,而攝影機本身則是一個 undetermined collective element——這個案例後面在方法論其他章節會反覆被拿來當作 set covering / set packing 的範例,對應 [[decision-activities]] 中量測型與邏輯型決策活動的差異。

**旅行團排巴士**這個案例,則是把 3.3.1 節「合併 item 為 collective element」的效益,直接放大到現實規模來看:180 位旅客各自選了 5 種行程之一、與 3 種語言偏好之一(西語、英語、或兩者皆可),要用最少數量的 8 輛巴士(每輛限 60 人)安排座位,而且同一輛巴士上的旅客,其行程與語言偏好都必須與該車配置相容。若把每一位旅客都當成獨立元素,決策變數的規模會隨 180 人線性增長;但只要留意到「行程 × 語言」實際上只有 15 種組合,所有選擇相同組合的旅客彼此完全無法區分,就可以把 180 位旅客直接合併成 15 個 determined collective element(「旅客群組」),對應的決策變數規模大幅壓縮。這正是 3.3.1 節 knapsack 範例的原理,在更貼近實務的場景中發揮作用。

**固定作業排程問題**(fixed job scheduling)則呼應了 3.2.5 節「衍生資料」的用法:一組任務各自有起始時間、結束時間與權重,一組機器要挑選一批互不重疊的任務去執行以最大化總權重。這裡機器雖然彼此完全相同,但因為規格描述明確是針對「一台機器」個別做出限制(不能同時執行兩個重疊的任務),機器仍必須被當成 individual element,不能合併。任務之間是否互相重疊,則可以先算成一筆衍生的 shared binary attribute(藉由起訖時間的邏輯比較算出),供之後的 specification 直接引用,而不必每次都重新推導重疊條件。

這一組範例共同的教學重點是:元素識別從來不是套公式,而是要不斷回到「這段文字究竟有沒有針對某個具體項目做出區分性的描述、有沒有 decision 或 specification 直接落在它身上」這個問題上反覆核對。這套判斷方式會在 [[gs-worked-examples]] 有更完整的實作案例延伸。
