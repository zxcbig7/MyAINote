# 附錄 U：從既有系統遷移上 K8s

這套教材到目前為止有一個共同的假設：**你的應用已經在 K8s 上，或者即將被部署上去**。實戰篇甚至從一個乾淨的 ASP.NET Core 專案開始。

但多數公司真正面對的專案不是這個，而是：**有一批跑了三五年的系統在 VM 或實體機上，現在要搬到 K8s。** 那些系統有人在用、不能停、原作者可能已經離職、而且它們對環境的依賴常常沒有文件。

這一份講那個專案怎麼做。它比較少 YAML、比較多判斷與節奏——因為遷移失敗的原因幾乎從來不是技術，而是順序錯了、範圍太大、或者搬了不該搬的東西。

---

## Part 0：先問該不該搬

**這是最容易跳過、也最該問的一題。** K8s 不是免費的——它帶來新的失敗模式、新的學習成本、新的維運責任。搬一個系統上去要有具體理由。

### 好理由

- 需要彈性擴縮（流量有明顯波峰）
- 部署頻繁，希望自動化與零停機
- 已經有其他服務在 K8s 上，這個系統要跟它們互動
- 多環境一致性是痛點（「測試好好的正式就掛」）
- 硬體要汰換，反正要搬

### 不是理由

- 「別人都在用」
- 「聽起來比較現代」
- 「主管說要上雲原生」

### 該留在原地的東西

誠實列出來，會省下很多痛苦：

| 系統性質 | 為什麼不該搬 |
| --- | --- |
| 一年跑一次的批次 | 搬的成本遠高於收益 |
| **授權綁定硬體**（MAC、dongle） | 技術上做得到，但麻煩且脆弱 |
| 依賴特殊硬體（讀卡機、串列埠） | 容器不是為此設計的 |
| 已經排定汰除的系統 | 搬完就要退役 |
| **對延遲極度敏感**且已調校到極致 | 多一層網路可能就不能接受 |
| 資料庫（多數情況） | 見實戰第五章的決策表 |

**「不搬」是一個合法的專案結論。** 一個遷移專案的產出如果是「這 12 個系統搬，那 5 個維持現狀直到退役」，那是好的規劃而不是失敗。

## Part 1：盤點

沒有盤點就開始搬，是遷移專案失敗的頭號原因。要盤的是三件事。

### 應用清單與依賴圖

每個系統至少記錄：對外提供什麼、依賴誰、誰依賴它、跑在哪台機器、誰負責、有沒有原始碼與建置流程。

**「有沒有可重現的建置流程」這一項特別關鍵。** 相當比例的老系統是「某台機器上編出來的，沒有人再編過」——那你要先解決建置問題，才談得上容器化。

依賴圖畫出來之後，**遷移順序基本上就決定了**：從依賴少的葉節點開始往中心推。

### 容器化難度評分

給每個系統打分，找出試點對象：

| 維度 | 容易（1 分） | 困難（5 分） |
| --- | --- | --- |
| 執行環境 | .NET / Java / Node，跨平台 | .NET Framework、依賴 Windows API |
| 狀態 | 完全無狀態 | 本機檔案、記憶體 session |
| 設定 | 環境變數或設定檔 | 硬編在程式碼、註冊表 |
| 建置 | 有 CI，可重現 | 手工編譯，無人知曉 |
| 依賴 | 只呼叫 HTTP API | 共用磁碟、具名管道、COM |
| 測試 | 有自動化測試 | 只能手動驗證 |
| 團隊 | 原團隊還在 | 沒人熟悉 |

**總分最低的那個就是你的試點。** 不要從最重要的系統開始——第一個專案的目標是**建立能力與信心**，不是創造最大價值。

### 隱性依賴：最容易漏的一類

這些在文件裡不會有，只能靠問與觀察：

- **本機檔案路徑**：`D:\uploads`、`C:\logs`、暫存目錄
- **共用磁碟**：`\\fileserver\share`
- **Windows 排程工作**：不在應用程式碼裡，在作業系統設定裡
- **Windows 服務**：另一個要一起搬的東西
- **硬編 IP 或主機名稱**
- **憑證在機器的憑證存放區**
- **依賴機器時區或地區設定**
- **IIS 的設定**：應用程式集區、虛擬目錄、URL 重寫規則
- **人工步驟**：「每個月要有人去按那個按鈕」

**找出它們的方法是觀察而不是問**——問「有什麼依賴」的答案通常是「沒有」。比較有效的做法是：看那台機器上還跑著什麼、看排程工作清單、看應用的設定檔、以及**在測試環境把它斷網一次看什麼壞掉**。

## Part 2：分批策略

**不要大爆炸。** 一次搬全部的專案幾乎都會失敗，因為問題會同時爆發而你無法歸因。

三個波次的節奏：

| 波次 | 選什麼 | 這一波要學到什麼 |
| --- | --- | --- |
| **第一波：試點**（1–2 個） | 難度分最低、且**不是關鍵系統** | 建立 CI/CD、chart、監控、上線流程的樣板 |
| **第二波：同類推廣**（一批） | 跟試點技術棧相同的 | 驗證樣板可複製，把流程文件化 |
| **第三波：困難的** | 有狀態、有隱性依賴、跨團隊 | 個案處理，每個都要單獨設計 |

第一波的產出**不只是「一個服務上線了」**，而是：一份可複製的 chart（附錄 T）、一條 CI/CD 管線（實戰第三章）、一份 runbook 樣板（附錄 H）、以及一份「這次踩到什麼」的紀錄。**第二波的速度取決於第一波的產出品質。**

第三波不要勉強。到這裡你已經有能力判斷「這個系統搬過去真的划算嗎」——Part 0 那張表可以再拿出來用一次。

## Part 3：應用要改的五件事

實戰第一章列過「讓應用適合跑在容器裡」的四件事。遷移舊系統時還會多幾件：

### 1. 設定外部化

老系統常見的模式是設定檔跟著程式走，甚至硬編在程式裡。要改成環境變數或掛載的設定檔（實戰第一章）。

**過渡技巧**：不必一次全改。先讓設定檔可以被環境變數覆蓋，容器化時只覆蓋會變的那幾項，其餘沿用原本的設定檔。

### 2. 日誌改 stdout

老系統多半寫檔案（`D:\logs\app.log`）。改法有兩條：

- **改應用**（推薦）：輸出到 stdout
- **不改應用**：掛一個 `emptyDir`，旁邊放一個 sidecar 讀檔案送出去

第二條是妥協方案，適合「沒有原始碼」或「改動風險太高」的系統。代價是多一個容器、多一份複雜度。

### 3. 檔案儲存

`D:\uploads` 這類本機檔案是遷移最常見的卡點。三個選項：

| 方案 | 適合 | 代價 |
| --- | --- | --- |
| **改用物件儲存**（S3/MinIO） | 長期正解 | 要改程式 |
| **PVC（RWX）** | 不改程式 | 需要 NFS/CephFS，效能與成本 |
| **PVC（RWO）+ 單副本** | 過渡 | 無法水平擴展，更新會中斷 |

**第三個是很多遷移專案的實際起點**——先搬上去、維持單副本、之後再改成物件儲存。這是合理的分階段，但**要明確記錄它是技術債而不是終點**，否則三年後還是單副本。

### 4. Session 外部化

記憶體 session 在多副本下會出現「一下登入一下登出」。三個選項：把 session 移到 Redis（正解）、用 sticky session（附錄 F 的 cookie 黏著，過渡方案）、或先維持單副本。

**注意 sticky session 在滾動更新時仍然會斷**（`affinity-mode: balanced` 的行為），所以它只是過渡而不是解法。

### 5. 排程工作

Windows 排程工作或應用內的計時器，搬過去要面對一個新問題：**多副本下每個副本都會執行**。

三種處理方式：

- **抽成 CronJob**（推薦）：一次執行、天然單例，且有重試與紀錄（附錄 C-2）
- **分散式鎖**：應用自己搶鎖，只有拿到的執行
- **維持單副本**：最簡單但放棄了高可用

CronJob 是最乾淨的做法，而且順便解決了「排程藏在作業系統設定裡沒人知道」的問題——**它變成 git 裡的一份 YAML**。

## Part 4：流量切換

### 雙跑期

**不要一次切完。** 讓新舊系統並行一段時間，是遷移最重要的安全網。

三種並行方式，可以疊加：

| 方式 | 做法 | 風險 |
| --- | --- | --- |
| **影子流量** | 複製一份流量到新系統，回應丟棄 | 最低（使用者無感）；但有副作用的請求要小心 |
| **權重分流** | 5% → 25% → 50% → 100% | 低，可隨時退回 |
| **依使用者分流** | 內部人員先用 | 低，且回饋品質高 |

影子流量用 Istio 的 `mirror`（附錄 C-7）或 ingress-nginx 的 `mirror-target`（附錄 F）。**要注意會產生副作用的請求**——鏡像一個「送出訂單」的請求，會真的送出兩次訂單。實務上只鏡像讀取類流量，或讓新系統連到獨立的測試資料庫。

### 切換的技術手段

| 手段 | 切換速度 | 回滾速度 |
| --- | --- | --- |
| DNS 改指向 | 慢（受 TTL 影響） | 慢 |
| 前置反向代理改後端 | 快 | 快 |
| LB 權重調整 | 快 | 快 |

**優先用「前面加一層代理」而不是改 DNS。** DNS 的 TTL 讓你的回滾速度不受控（附錄 L 講過同樣的問題）。如果一定要用 DNS，事前把 TTL 調到 60 秒。

### 回滾點設計

**每一個步驟都要能單獨退回。** 具體來說，在動手之前先回答：

- 這一步做完之後，退回去需要幾分鐘？
- 退回去會不會遺失資料？
- 誰有權限執行回滾？半夜找得到人嗎？
- 退回去之後，新系統累積的資料怎麼辦？

最後一項是雙跑期最麻煩的部分。**新舊系統共用同一個資料庫是最簡單的解法**——這樣切回去不會有資料落差。代價是資料庫 schema 要同時相容新舊系統（實戰第五章的 expand-contract 模式在這裡再次適用）。

如果新舊系統用不同資料庫，你就需要雙寫或同步機制，**那是整個遷移專案裡最容易出錯的部分**。能避免就避免。

## Part 5：Windows 應用

### 先問能不能不搬 Windows

.NET Framework 應用有三條路：

| 路線 | 成本 | 結果 |
| --- | --- | --- |
| **改寫成 .NET（跨平台）** | 高 | Linux 容器，完全享受 K8s 生態 |
| **Windows container** | 中 | 能跑，但限制多 |
| **不搬** | 零 | 維持現狀直到退役 |

**第一條路的成本常常被高估。** 如果應用不用 WCF、WebForms、System.Drawing 這類 Windows 專屬的東西，升級到現代 .NET 的工作量可能比想像中小。值得先用 .NET Upgrade Assistant 之類的工具評估一次再做決定。

### Windows container 的現實

真的要用的話，先知道這幾件事：

- **映像很大**（動輒數 GB，相對 Linux 的數十 MB）
- **Windows 容器只能跑在 Windows 節點上**，叢集要混合節點池與對應的 taint/nodeSelector
- **主機與容器的 Windows 版本要相容**（版本綁定比 Linux 嚴格）
- **生態支援較弱**：很多 CNI、CSI、service mesh 對 Windows 支援有限或沒有
- **啟動較慢**，對 HPA 的反應速度有影響

```yaml
spec:
  nodeSelector:
    kubernetes.io/os: windows
  tolerations:
    - key: os
      operator: Equal
      value: windows
      effect: NoSchedule
```

還有 `pod.spec.os.name: windows` 這個欄位（附錄 C-1），能讓排程與欄位驗證更準確。

**務實的建議**：Windows container 適合「一定要搬、但短期不可能改寫」的系統，當成過渡而不是終點。如果那個系統的生命週期本來就不長，Part 0 的「不搬」可能是更好的答案。

## Part 6：專案節奏

### 每一波的驗收標準

「上線了」不等於「搬完了」。每一波要通過這些才算數：

- [ ] 服務在新環境正常運行**至少兩週**（涵蓋一次月結或週期性負載）
- [ ] 監控與告警已建立，且**實際觸發過一次**（附錄 H）
- [ ] runbook 已寫且**由不是搬的人**照著操作過一次
- [ ] 舊環境已停用（不是「先留著」——留著就永遠不會關）
- [ ] 團隊知道怎麼部署、怎麼看日誌、怎麼回滾

**倒數第二項是最常被拖延的。** 舊環境不關的話，你同時維護兩套、成本沒降、而且下次出事時大家會想「要不要切回去」——那個選項存在本身就會拖慢新環境的成熟。設一個明確的關閉日期。

### 什麼時候該停下來

三個訊號代表這一波該暫停檢討，而不是硬推：

1. **同一類問題在不同系統重複出現** → 樣板有問題，先修樣板
2. **上線後的事故頻率高於舊環境** → 能力還沒建立，回頭補
3. **團隊開始繞過流程**（手動 apply、直接改線上）→ 流程太痛，先改流程

第三項是最重要的訊號（呼應附錄 O 的「採用率低代表工具不好用」）。**團隊繞道不是紀律問題，是設計問題。**

## Part 7：常見失敗模式

| # | 失敗模式 | 症狀 | 解法 |
| --- | --- | --- | --- |
| 1 | **沒盤點就開始** | 搬到一半發現有共用磁碟／排程工作 | 先做依賴盤點，含隱性依賴 |
| 2 | **從最重要的系統開始** | 第一次就出大事，專案失去信任 | 從最容易的開始建立能力 |
| 3 | **大爆炸切換** | 問題同時爆發，無法歸因 | 分波、雙跑、權重分流 |
| 4 | 舊環境一直不關 | 兩套並行，成本沒降 | 每一波設明確關閉日期 |
| 5 | 只搬不改 | 本機檔案、記憶體 session 造成詭異行為 | Part 3 的五件事至少評估過 |
| 6 | 沒有回滾計畫 | 出事只能硬撐 | 每一步都要能退，且演練過 |
| 7 | 新舊用不同資料庫又沒想清楚同步 | 資料落差，切回去更痛苦 | 雙跑期盡量共用資料庫 |
| 8 | 影子流量造成副作用 | 訂單送兩次 | 只鏡像讀取類，或用獨立資料庫 |
| 9 | 用 DNS 切換卻沒調 TTL | 回滾要等一小時 | 用前置代理，或事前調 TTL |
| 10 | 把「不搬」當成失敗 | 硬搬不該搬的東西 | 「維持現狀直到退役」是合法結論 |

## 檢查清單

**開始之前**

- [ ] 每個系統的遷移理由是具體的，不是「別人都在用」
- [ ] 已列出「不搬」的清單與理由
- [ ] 有應用清單與依賴圖
- [ ] 每個系統有容器化難度評分
- [ ] **隱性依賴已用觀察而非詢問的方式盤點過**
- [ ] 確認每個系統有可重現的建置流程

**每一波之前**

- [ ] 試點選的是最容易的，不是最重要的
- [ ] 這一波要建立的「樣板產出」已明確定義
- [ ] 回滾程序已設計且演練過
- [ ] 雙跑期的資料處理方式已想清楚

**切換時**

- [ ] 用前置代理而非 DNS（或 TTL 已調短）
- [ ] 權重分流，不是一次切完
- [ ] 影子流量不會產生副作用
- [ ] 有明確的中止條件與決策人

**每一波之後**

- [ ] 穩定運行兩週以上，涵蓋週期性負載
- [ ] 監控告警實際觸發過
- [ ] runbook 由他人驗證過
- [ ] **舊環境有明確關閉日期並執行**
- [ ] 這一波的教訓已回饋到樣板與文件
