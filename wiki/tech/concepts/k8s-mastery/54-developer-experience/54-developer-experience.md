# 附錄 AF：本機開發與 Inner Loop

附錄 O 講了平台怎麼讓五個團隊安全地上線、附錄 V 講了怎麼讓知識不只存在一個人身上。但兩者都跳過了開發者每天感受最深的那件事：**他們怎麼寫程式、怎麼測試改動。**

這件事重要的原因是算術。開發者一天可能改動並驗證五十次，如果每次要等三分鐘，那是**兩個半小時**——比任何架構優化省下的時間都多，而且它每天都在發生。

這一份講 inner loop 在 K8s 環境為什麼會壞掉，以及四種修法各自的取捨。

---

## Part 1：Inner Loop 是什麼

**Inner loop** 是「改一行程式碼 → 看到結果」的循環。**Outer loop** 是「提交 → CI → 部署 → 上線」。

傳統開發的 inner loop 是秒級的：改 code、按 F5、瀏覽器重新整理。上了 K8s 之後，天真的做法會變成：

```
改 code → docker build（60s）→ push registry（30s）
        → 更新 manifest → 等 Pod 重新拉取與啟動（40s）→ 看結果
```

**兩到三分鐘，而且中間有好幾個可能失敗的環節。** 更糟的是它打斷了心流——三分鐘足夠讓人切去看訊息，然後忘記自己剛才在測什麼。

一個明確的立場：**開發者不該為了測一行改動而等三分鐘。** 如果你的團隊現在是這樣，那不是他們不夠有耐心，是工具鏈需要處理。

**而且這件事會影響行為**：inner loop 慢的團隊會傾向「一次改很多再測」，而那讓除錯變難、讓改動變大、讓 review 變痛苦。**快的 inner loop 不只是省時間，它會讓人寫出更小的改動。**

## Part 2：四種策略

| 策略 | 速度 | 真實度 | 複雜度 | 適合 |
| --- | --- | --- | --- | --- |
| **完全本機**（直接跑 + Compose 起依賴） | **秒級** | 低 | 低 | 依賴少、邏輯為主的服務 |
| **本機 K8s**（kind/minikube + 自動化） | 十幾秒 | 中 | 中 | 需要驗證 K8s 行為 |
| **遠端叢集 + 檔案同步** | 十幾秒 | 高 | 中 | 依賴多個內部服務 |
| **遠端叢集 + 流量攔截** | **秒級** | **高** | 中高 | 依賴多、且要用真實流量除錯 |

### 完全本機

應用直接在 IDE 裡跑（F5 除錯、熱重載全部可用），依賴用 Compose 起（實戰第一章的做法）。

**這仍然是最快也最舒服的方式**，而且對「這個服務的邏輯對不對」這類問題完全夠用。不要因為「我們用 K8s」就放棄它。

限制是它驗證不了任何 K8s 相關的行為——probe、resource limit、Service DNS、SA token、Ingress 路由。但**那些東西不該在每次改動時驗證**，它們屬於 CI（附錄 Z）。

### 本機 K8s + 自動化工具

用 kind 或 minikube 在本機跑一個叢集，配 Skaffold / Tilt / DevSpace 自動化「build → 部署」：

```yaml
# skaffold.yaml（概念示意）
apiVersion: skaffold/v4beta6
kind: Config
build:
  artifacts:
    - image: my-api
      docker:
        dockerfile: Dockerfile
      sync:
        manual:
          - src: "src/**/*.cshtml"    # 這類檔案直接同步，不重建映像
            dest: /app
deploy:
  helm:
    releases:
      - name: my-api
        chartPath: ./charts/my-api
        valuesFiles: ["./charts/my-api/values-dev.yaml"]
```

**關鍵在 `sync`**：靜態資源、模板、設定檔這類東西可以直接複製進 Pod，不需要重建映像——這把某些改動的循環從兩分鐘壓到兩秒。

編譯型語言（C#、Go）就沒那麼幸運，改邏輯仍然要重建。**但可以讓重建變快**：多階段建置的層快取（實戰第一章）、以及在開發用的映像裡保留 SDK 以便增量編譯。

### 遠端叢集 + 流量攔截

這是依賴多的環境裡最有效的一招：**你的服務在本機跑，但叢集裡的其他服務以為它還在叢集裡。**

Telepresence 或 mirrord 的原理是在叢集裡放一個代理，把原本要送給某個 Service 的流量轉發到你的本機程序，同時讓你的本機程序能存取叢集內的其他服務、ConfigMap、Secret 與 SA 身分。

**效果是「本機開發的速度 + 叢集的真實度」**——你可以在 IDE 裡下中斷點，然後從真實的上游服務送一個真實請求進來。

三個限制要知道：**它會影響共用環境**（攔截的期間，別人打那個服務也會打到你的機器——所以要用個人專屬的 namespace 或用「只攔截帶特定 header 的流量」的模式）、**網路延遲**（你的機器到叢集的往返會加進每次呼叫）、以及**它是額外的元件**，本身也會壞。

## Part 3：判準——你的服務需要多少真實度

不要一律用最重的方案。用這個順序判斷：

| 你的服務依賴什麼 | 建議策略 |
| --- | --- |
| 只有資料庫／快取 | **完全本機 + Compose** |
| 少數幾個內部服務，且它們有穩定的 API | 完全本機 + mock 或 stub |
| 多個內部服務，狀態複雜 | 遠端叢集 + 流量攔截 |
| 需要驗證 K8s 特有行為（probe、DNS、SA token、Ingress） | 本機 K8s 或遠端叢集 |
| 需要驗證資源限制下的行為 | 本機 K8s（設一樣的 limits） |

**最常見的錯誤是高估自己需要的真實度。** 「我們的服務要跟五個服務溝通所以一定要在叢集裡開發」——但如果那五個呼叫在你這次的改動裡根本沒被觸及，mock 掉它們完全沒問題。

**另一個實用的觀念：真實度是可以分階段的。** 日常開發用最快的方式，改完之後在推 PR 之前才用一次高真實度的驗證（預覽環境，附錄 Z）。不必每一次改動都追求最高真實度。

---

## Part 4：讓本機與叢集不要漂移

inner loop 工具最大的風險是**本機跑的東西跟叢集跑的東西變成兩套**：本機用 Compose 的設定、叢集用 chart 的設定，兩邊慢慢長歪，然後出現「本機好好的上叢集就掛」。

三條原則：

**用同一份 chart，只換 values。** 本機開發用 `values-dev.yaml`，跟正式環境用同一個 chart（附錄 T）。這樣 chart 的變更會立刻在本機被驗證，不會等到部署才發現。

**不要為了「本機能跑」在程式碼裡加分支。** `if (isLocal) { ... }` 是一個會擴散的模式——它讓本機跑的路徑跟正式跑的路徑不同，也就讓本機測試的價值下降。**差異應該在設定，不在程式碼。**

**依賴的版本要一致。** 本機 Compose 起 Postgres 16、叢集是 15，那是一個等著發生的問題（實戰第一章與附錄 Z 都提過同一件事）。

## Part 5：團隊層面的設計

### 不要讓每個開發者都要懂 K8s

呼應附錄 O 與 V：**一般開發者的最小知識集合裡不該包含「怎麼設定本機叢集」。**

平台團隊該提供的是**一鍵起環境**：

```powershell
# 理想狀態：一行指令，新人第一天就能跑
./scripts/dev-up.ps1
```

那個腳本背後做什麼（起 kind、裝 ingress、套 chart、種資料）不該是每個人都要懂的。**「新人第一週能不能自己跑起開發環境」是附錄 V 那個上手時間指標的一部分。**

### 共用開發叢集的隔離

多人共用一個開發叢集時，**每人一個 namespace** 是最實際的隔離方式（附錄 O 的自助化正好可以用上）：

- 各自的服務不互相干擾
- 資源用 ResourceQuota 限制
- 名稱固定（`dev-<username>`），好記也好清理
- 加 TTL 或定期清理閒置的

**流量攔截的工具在共用叢集特別要小心**：預設的攔截模式會把**所有人**的流量都導到你的機器。務必用「只攔截帶特定 header 的流量」那種模式，或在自己的 namespace 裡做。

### 成本

開發叢集常常是被遺忘的成本項——它二十四小時開著、資源配置照抄正式環境、而且沒人盤點。三個手段：**下班自動縮容**（CronJob 把 Deployment 縮到 0，早上再擴回來）、**用 spot 節點**（附錄 S，開發環境被中斷完全可接受）、以及**附錄 K 的孤兒資源盤點在開發叢集要跑得更勤**。

## Part 6：除錯

本機跑的話用 IDE 的除錯器就好。跑在叢集裡的話有三種方式：

| 方式 | 做法 | 適合 |
| --- | --- | --- |
| **遠端除錯** | 開除錯 port，`kubectl port-forward` 接上 IDE | 需要下中斷點 |
| **流量攔截** | 把流量導回本機，用本機除錯器 | 最舒服，見 Part 2 |
| **臨時容器** | `kubectl debug` 注入一個帶工具的容器 | distroless 映像、正式環境排查 |

```powershell
# 遠端除錯：把 Pod 的除錯 port 接到本機
kubectl port-forward deploy/my-api 5005:5005

# 臨時容器：正式環境的映像沒有 shell 時
kubectl debug -it my-api-abc123 --image=busybox:1.36 --target=api
```

**臨時容器（`kubectl debug`）值得團隊都知道**，因為它是「正式環境用 distroless 映像」（附錄 P）之後唯一的排查手段。附錄 C-1 有它的欄位說明。

## Part 7：反模式

| # | 反模式 | 為什麼糟 |
| --- | --- | --- |
| 1 | **直接在正式叢集上開發** | 不用解釋 |
| 2 | 每個人 build 映像推到共用 registry 再部署 | 慢、registry 塞滿、tag 互相覆蓋 |
| 3 | 用 `kubectl cp` 熱抽換檔案 | 容器重啟就沒了，且沒有紀錄 |
| 4 | 為了本機能跑在程式碼裡加 `if (isLocal)` | 本機路徑與正式路徑不同，測試價值下降 |
| 5 | 每個人維護自己的一套本機設定 | 環境不一致，「我這邊可以」 |
| 6 | 開發環境照抄正式環境的資源配置 | 成本浪費，且本機跑不動 |
| 7 | 在共用叢集用預設模式做流量攔截 | 把別人的流量搶過來 |
| 8 | 一律追求最高真實度 | 慢，而且多數改動不需要 |
| 9 | 開發叢集沒有清理機制 | 資源與成本持續累積 |
| 10 | 要求所有開發者都會設定本機叢集 | 那是平台該提供的一鍵腳本 |

第 2 項值得展開，因為它很常見：**「改一行 → build → push → 部署」的流程裡，push 到共用 registry 是最不必要的一段。** 本機 K8s 的話可以直接把映像載進叢集（`kind load docker-image`、`minikube image load`），完全跳過 registry。Skaffold 這類工具會自動處理。

## 檢查清單

**個人的 inner loop**

- [ ] 日常改動的驗證循環在**十秒以內**
- [ ] 能在 IDE 裡下中斷點除錯
- [ ] 不需要 push 到共用 registry 才能測
- [ ] 靜態資源／模板的改動走檔案同步，不重建映像

**一致性**

- [ ] 本機與叢集用**同一份 chart**，只換 values
- [ ] 程式碼裡**沒有 `if (isLocal)` 分支**
- [ ] 依賴（DB、快取）的版本本機與叢集一致

**團隊**

- [ ] 有一鍵起開發環境的腳本
- [ ] 新人第一天能跑起來
- [ ] 共用開發叢集有 per-developer namespace 與 quota
- [ ] 流量攔截不會影響其他人

**成本**

- [ ] 開發叢集有下班縮容或 spot 節點
- [ ] 有定期清理閒置 namespace
- [ ] 開發環境的資源配置沒有照抄正式環境

**除錯**

- [ ] 團隊知道 `kubectl port-forward` 遠端除錯
- [ ] 團隊知道 `kubectl debug` 臨時容器（distroless 映像的唯一手段）

## 常見誤區

| # | 誤區 | 真相 |
| --- | --- | --- |
| 1 | 用了 K8s 就不能在本機直接跑 | 多數改動完全本機就夠 |
| 2 | inner loop 慢只是不方便 | 一天五十次 × 三分鐘 = 兩個半小時，且會讓人寫出更大的改動 |
| 3 | 一定要在叢集裡才測得準 | 高估真實度需求是最常見的錯誤 |
| 4 | 真實度要一次到位 | 可以分階段：日常最快、推 PR 前才高真實度 |
| 5 | 本機用 Compose、叢集用 chart 沒關係 | 兩套設定會漂移 |
| 6 | `if (isLocal)` 只是小小的方便 | 它讓本機測試的價值下降 |
| 7 | 流量攔截很安全 | 預設模式會搶走共用環境的流量 |
| 8 | 開發叢集成本不重要 | 24 小時開著、照抄正式配置、沒人盤點 |
| 9 | 每個開發者都該懂本機叢集設定 | 那是平台該提供的一鍵腳本 |
| 10 | distroless 映像沒辦法除錯 | `kubectl debug` 臨時容器 |
