# 附錄 AG：日誌策略與成本

正文第 15 章講了 ELK 的機制——倒排索引怎麼運作、`text` 與 `keyword` 差在哪、KQL 怎麼寫。實戰第六章講了結構化日誌與 trace ID 關聯。但兩者都沒回答一個管理員遲早要面對的問題：**該記什麼、留多久、以及這東西為什麼這麼貴。**

日誌是典型的「寫的時候不痛、帳單來才痛」——每個 `logger.LogInformation` 都是免費的，直到你發現日誌儲存已經是雲端帳單的前三名，而且沒有人知道哪些日誌真的有人在看。

---

## Part 1：三種用途，三套要求

**最常見的錯誤是把所有日誌當成同一種東西。** 實際上它們有三種截然不同的用途，而三者的要求幾乎沒有重疊：

| 用途 | 誰在看 | 保留期 | 要求 |
| --- | --- | --- | --- |
| **除錯** | 開發者，事故當下 | 短（7–30 天） | 細節多、要能全文搜尋、要快 |
| **趨勢與告警** | 監控系統 | — | **應該用 metric，不是 log** |
| **稽核** | 合規、資安、事後調查 | 長（半年到七年） | 不可竄改、欄位固定、量少 |

**第二列是最重要的一條紀律：不要用日誌做監控。**

「數一下錯誤有幾筆」用日誌做的話，每次查詢都要掃過大量原始資料——慢、貴，而且無法拿來做即時告警。同樣的資訊用一個 counter metric 表達（實戰第六章），成本差好幾個量級。

**判準很簡單：如果你想知道的是「數量、比例、趨勢」，那是 metric 的工作；如果想知道的是「這一筆到底發生什麼事」，那才是 log。**

第三列的稽核日誌則該**單獨存放**：它的保留期是除錯日誌的十倍以上，如果混在一起，你會為了留住稽核紀錄而付出留住所有 DEBUG 日誌的代價。

## Part 2：該記什麼、不該記什麼

### 該記

| 類別 | 例子 |
| --- | --- |
| **請求邊界** | 收到請求（含 trace id、使用者、關鍵參數）、回應（狀態碼、耗時） |
| **狀態變更** | 訂單建立、狀態轉換、權限變更 |
| **外部呼叫** | 打了哪個下游、耗時、結果 |
| **錯誤與例外** | 完整堆疊、當時的關鍵上下文 |
| **決策點** | 「因為 X 所以走了 Y 分支」——事後最有用的一類 |

**最後一項最容易被忽略，也最有價值。** 事故當下最想知道的往往不是「發生了什麼錯誤」，而是「為什麼系統做了那個決定」——走了降級路徑、選了哪個後端、命中了哪條規則。

### 不該記

| 不該記 | 為什麼 |
| --- | --- |
| **密碼、token、金鑰** | 日誌保留數週、多人可讀、可能被匯出——**寫進日誌等同外洩**（附錄 P） |
| **個資** | 同上，且有法規風險 |
| **完整的請求／回應 body** | 量大、可能含上述兩項 |
| 每次迴圈的內容 | 一筆訂單一行，不是一個品項一行 |
| 成功的例行操作 | 「快取命中」這種每秒幾千次的事件 |
| **能用 metric 表達的東西** | 見 Part 1 |

**「完整 body」值得特別提醒**：它看起來很有用（除錯時什麼都有），但它同時是最大的量、最高的外洩風險、以及最可能包含個資的地方。需要的話用取樣（只記 1% 或只記失敗的），而不是全記。

### 一個實用的自我檢查

**每加一行 log，問一次：「誰會在什麼情況下看它？」**

答不出來的就不該加。這個問題會過濾掉大量「加了以防萬一」的日誌——而那些正是佔了大部分量卻從來沒人查詢的部分。

## Part 3：日誌等級的紀律

等級不是「感覺重要程度」，而是**有明確判準的分類**：

| 等級 | 判準 | 保留 |
| --- | --- | --- |
| `Trace` / `Debug` | 只在本機或除錯時開啟 | 正式環境預設關閉 |
| `Information` | 正常流程的關鍵節點 | 短期 |
| `Warning` | **不正常但系統自己處理了**（重試成功、降級生效、設定用了預設值） | 短期 |
| `Error` | **需要人採取行動**，或使用者受影響 | 較長 |
| `Critical` | 服務無法運作 | 長期 + 告警 |

**`Error` 的定義是最重要的一條：需要人採取行動。**

如果你的 ERROR 日誌每天有幾千筆而沒有人看，那它們就不是 ERROR——那是被誤標的 WARNING 或 INFO。**而且它會讓真正的 ERROR 被淹沒**，這是「告警疲勞」在日誌上的版本。

`Warning` 則常被當成垃圾桶：「不確定嚴不嚴重就標 WARN」。正確用法是「有異常但已被處理」——它的價值在於**趨勢**（重試率上升了嗎），而那又回到 Part 1 的結論：如果你在乎的是趨勢，那應該同時有一個 metric。

### 動態調整等級

正式環境預設關閉 DEBUG，但排查時需要臨時打開。**這正是附錄 AE 說「熱重載只保留給不影響行為正確性的東西」的典型用例**——日誌等級改了不會改變業務邏輯，所以適合用 volume 掛載的設定檔動態調整。

三個實務要點：**只對特定的 namespace 或 logger 打開**（不要全叢集開 DEBUG，那會瞬間產生大量資料）、**要有自動關閉機制或提醒**（忘了關是常見的成本事故）、以及**開之前先確認儲存空間夠**。

## Part 4：成本從哪裡來

日誌成本的公式大致是：

```
成本 ≈ 每日產生量 × 保留天數 × 儲存單價
     + 索引產生的額外空間與運算
     + 查詢時的運算
```

**其中「索引」是多數人低估的部分。** Elasticsearch 為了讓全文搜尋快，會為欄位建立倒排索引——索引本身可能跟原始資料一樣大甚至更大。所以「我只存了 100GB 日誌」實際佔用可能是 200GB 以上，加上副本再翻倍。

### 一個具體的算術

假設一個中等規模的服務：

| 項目 | 數字 |
| --- | --- |
| 每秒請求 | 200 |
| 每個請求產生的日誌行數 | 5 |
| 每行平均大小 | 500 bytes |
| 每日原始量 | 200 × 5 × 500 × 86400 ≈ **43 GB/天** |
| 保留 30 天 | 1.3 TB |
| 加索引（×1.5）與副本（×2） | **約 4 TB** |

**而這只是一個服務。** 二十個服務就是 80 TB——這個數字通常會讓人重新思考「每個請求真的需要五行日誌嗎」。

### 四個減量手段

**1. 把 metric 從 log 裡拿出來。** 通常是效果最大的一項——請求計數、耗時分布這些如果已經有 metric（實戰第六章），那對應的 INFO 日誌就可以大幅減少。

**2. 取樣。** 成功的請求只記 1–10%，失敗的全記。**這保留了除錯所需的資訊（出事的那些），同時砍掉大部分的量。**

**3. 分級保留。** DEBUG 留 3 天、INFO 留 7 天、ERROR 留 30 天、稽核留一年。

**4. 只索引需要查詢的欄位。** Elasticsearch 可以把某些欄位設成 `index: false`——它們仍然存著、查得到內容，但不佔索引空間。完整 body 這類欄位特別適合。

### Loki 的成本差異

Loki 的設計取捨值得知道：**它只索引標籤（label），日誌內容本身壓縮後直接存進物件儲存。**

| | Elasticsearch | Loki |
| --- | --- | --- |
| 索引 | 全文 | **只有 label** |
| 儲存成本 | 高 | **低**（物件儲存，附錄 AD） |
| 任意欄位搜尋 | 快 | 慢（要掃過符合 label 的區塊） |
| 適合 | 需要複雜查詢與分析 | **主要用「先過濾服務再看內容」的模式** |

**多數團隊的實際查詢模式是後者**：「demo namespace 的 api 服務、過去一小時、含 error 的行」——這正是 Loki 最擅長的。如果你的查詢很少需要「跨所有服務全文搜尋任意關鍵字」，Loki 能省下可觀的成本。

**但 Loki 的 label 有跟 Prometheus 一樣的高基數陷阱**（實戰第六章）：把 trace ID 或使用者 ID 當 label 會讓它爆炸。label 只放服務、namespace、等級這類低基數的維度。

## Part 5：保留與分層

Elasticsearch 的 ILM（索引生命週期管理）讓資料隨時間降級：

| 階段 | 特性 | 典型時間 |
| --- | --- | --- |
| **Hot** | 可寫入、查詢最快、用最好的硬體 | 0–3 天 |
| **Warm** | 唯讀、減少副本、可能合併分片 | 3–14 天 |
| **Cold** | 更慢的儲存、查詢較慢 | 14–90 天 |
| **Frozen / 快照** | 存在物件儲存，查詢前要還原 | 90 天以上 |
| **Delete** | 刪除 | 到期 |

**設定 ILM 是日誌成本控制投報率最高的單一動作**——它是一次性設定，之後自動生效，而且不需要應用改任何東西。

稽核日誌則要走另一條路：**單獨的索引或儲存、更長的保留期、而且要考慮不可竄改**（寫入後不可修改的儲存、或至少嚴格的存取控制）。K8s 自己的 audit log（附錄 C-6、附錄 P）也適用同樣原則——而且它**必須送到叢集外**，否則攻擊者取得節點權限後第一件事就是清掉它。

## Part 6：收集架構

### DaemonSet vs Sidecar

| | DaemonSet（每節點一份） | Sidecar（每 Pod 一份） |
| --- | --- | --- |
| 資源開銷 | **低**（每節點一個） | 高（每個 Pod 都有） |
| 設定 | 統一 | 可以每個應用不同 |
| 適用 | **預設選擇** | 應用寫檔案而非 stdout 時的妥協 |

**預設用 DaemonSet。** 它讀取節點上的容器日誌檔（那正是 `kubectl logs` 讀的同一份），一個 Pod 服務整台機器。

sidecar 只在一種情況合理：**應用無法改成輸出 stdout**（附錄 U 講的老系統遷移）。那時候用一個 `emptyDir` 讓應用寫檔案、sidecar 讀檔案轉送——這是妥協方案，代價是每個 Pod 多一個容器。

### 收集器的選擇

| 工具 | 特點 |
| --- | --- |
| **Fluent Bit** | 輕量（C 寫的），資源佔用小，最常見的 DaemonSet 選擇 |
| **Fluentd** | 功能多但較重，通常放在聚合層 |
| **Vector** | 較新，效能好，設定表達力強 |
| **Promtail** | Loki 專用，輕量 |

多數情況 **Fluent Bit 當節點收集器**就夠了。量大的話可以加一層聚合器做緩衝與批次寫入，避免每個節點直接打後端。

### 不要忘記節點上的日誌輪替

附錄 C-6 提過但值得再說：kubelet 的 `containerLogMaxSize` × `containerLogMaxFiles` × 節點上的容器數，決定了日誌會佔多少節點磁碟。**設定不當會撐爆磁碟、觸發 `DiskPressure`、把整台節點上的 Pod 全部驅逐**——這是一個「日誌設定造成叢集事故」的真實路徑。

## Part 7：讓日誌真的可用

量控制住之後，還要讓它好查。四件事：

**結構化。** 實戰第六章講過：用樣板參數而非字串內插，讓欄位可以被查詢與聚合。

**統一的欄位命名。** 所有服務用同一組欄位名（`service`、`env`、`version`、`trace_id`、`user_id`）。不統一的話，跨服務查詢會變成猜謎——**這是平台團隊該定義並寫進共用函式庫或 golden path chart 的事**（附錄 O）。

**trace ID 貫穿。** metrics 看到尖峰 → 找到對應的 trace → 跳到日誌。這條鏈是可觀測性的骨幹（實戰第六章）。

**查詢的紀律。** 先縮時間範圍、先用 label／欄位過濾、最後才全文搜尋。反過來做（先全文搜尋整個月）在任何後端上都會很慢很貴。

## 檢查清單

**分類**

- [ ] 除錯／稽核日誌分開存放與設定保留期
- [ ] **沒有用日誌做監控與告警**（該用 metric）
- [ ] 稽核日誌送到叢集外且有存取控制

**內容**

- [ ] **沒有記密碼、token、個資**
- [ ] 完整 body 不記，或只取樣／只記失敗
- [ ] 有記「決策點」（為什麼走了這個分支）
- [ ] 每行 log 都能回答「誰會在什麼情況下看它」

**等級**

- [ ] `Error` 的定義是「需要人採取行動」
- [ ] ERROR 的量是可以被人看完的
- [ ] 正式環境預設關閉 DEBUG
- [ ] 有動態調整等級的機制，且**有自動關閉或提醒**

**成本**

- [ ] 算過每日產生量與保留成本
- [ ] 已把能用 metric 表達的東西移出日誌
- [ ] 成功請求有取樣
- [ ] **有設 ILM 或等價的分層／刪除規則**
- [ ] 不需要搜尋的欄位沒有建索引
- [ ] 評估過 Loki 這類只索引 label 的方案

**架構**

- [ ] 用 DaemonSet 收集（除非應用無法輸出 stdout）
- [ ] **kubelet 的日誌輪替有設定**（避免撐爆節點磁碟）
- [ ] 量大時有聚合／緩衝層

**可用性**

- [ ] 日誌是結構化的
- [ ] 跨服務的欄位命名統一
- [ ] 每筆日誌帶 trace ID

## 常見誤區

| # | 誤區 | 真相 |
| --- | --- | --- |
| 1 | 日誌多一點比較保險 | 量大到查不動、貴到要砍，反而更不保險 |
| 2 | 用日誌算錯誤數量 | 慢又貴；那是 metric 的工作 |
| 3 | 所有日誌一起存一起留 | 稽核的保留期是除錯的十倍，混在一起等於全部照長的算 |
| 4 | 「100GB 日誌」就是佔 100GB | 索引 + 副本可能是三到四倍 |
| 5 | 不確定嚴不嚴重就標 WARN | WARN 是「異常但已處理」，不是垃圾桶 |
| 6 | ERROR 很多是正常的 | ERROR 的定義是「需要人採取行動」；很多沒人看的 ERROR 會淹沒真的 |
| 7 | 記完整 body 方便除錯 | 最大的量、最高的外洩風險、最可能含個資 |
| 8 | 密碼寫進日誌影響不大 | 日誌留數週、多人可讀、可能匯出——**等同外洩** |
| 9 | Loki 一定比較便宜 | 查詢模式不對的話會很慢；label 高基數同樣會爆 |
| 10 | 節點日誌不用管 | 撐爆磁碟會觸發 DiskPressure 驅逐全部 Pod |
| 11 | 開 DEBUG 排查完再說 | 忘了關是常見的成本事故 |
| 12 | 每個服務用自己的欄位名沒差 | 跨服務查詢會變成猜謎 |
