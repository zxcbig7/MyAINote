# 附錄 AM：合規與稽核

正文第 8 章講了安全的**預防**（認證、授權、准入），附錄 P 講了**應變**（外洩、入侵、蒐證）。但還有第三件事沒講：**怎麼向稽核者證明你做了。**

這是不同性質的問題。安全問的是「有沒有做」，合規問的是「**能不能證明有做**」——而後者常常是工程團隊最痛苦的部分，因為證據往往在事後才開始蒐集，然後花兩週截圖。

這一份講的是把合規要求翻譯成 K8s 的具體機制，以及**怎麼讓證據自動產生**，讓稽核季不必停下所有工作。

> 本份不談任何特定認證的條號（那會過期、也因版本而異），而是談**各種框架共通的控制項類別**，以及它們在 K8s 上對應到什麼。你的稽核清單長什麼樣，要跟稽核單位確認。

---

## Part 1：合規要求對應到 K8s 的什麼

多數框架（不論名稱）都會問同一批問題。翻譯成 K8s：

| 控制項類別 | 稽核者實際在問 | K8s 上對應的機制 |
| --- | --- | --- |
| **存取控制** | 誰能碰生產環境？怎麼授予、怎麼撤銷？ | RBAC、ServiceAccount、OIDC（[[08-security-and-rbac]]） |
| **職務分離** | 寫程式的人能不能自己推上線？ | GitOps + PR review（[[practice-3-gitops-pipeline]]） |
| **變更管理** | 這個變更誰核准的？能回溯嗎？ | git 歷史 + ArgoCD sync 紀錄 |
| **稽核軌跡** | 誰在什麼時候做了什麼？ | K8s audit log（[[23-yaml-fields-rare-builtins]]） |
| **資料保護** | 敏感資料在哪、怎麼加密、怎麼刪 | etcd 靜態加密、TLS、Vault（[[06-config-and-storage]]） |
| **可用性與復原** | 掛了多久能回來？演練過嗎？ | RTO/RPO、還原演練（[[34-multicluster-and-dr]]） |
| **供應鏈** | 你跑的程式碼從哪來？ | 映像掃描、簽章、SBOM（[[38-security-incident-response]]） |
| **設定基線** | 怎麼確保沒有人偏離安全設定？ | PSA、admission policy（[[37-platform-engineering]]） |

**這張表最有用的讀法是反過來看**：如果你照著這套教材建立了 GitOps、PSA、audit log、還原演練，那你**已經滿足了大部分控制項**——只是證據沒有被整理成稽核者看得懂的形式。

合規工作的多數成本，其實在最後那一段。

---

## Part 2：存取控制與職務分離

### 「誰能碰生產環境」要能列舉

稽核最常見的第一個問題就是這個，而它在 K8s 上有明確的答案來源：

```powershell
# 誰被綁到高權限角色
kubectl get clusterrolebinding -o wide | Select-String "cluster-admin|admin"

# 某個身分實際能做什麼（比讀 YAML 推理可靠）
kubectl auth can-i --list --as=user@example.com
kubectl auth can-i --list --as=system:serviceaccount:prod:deployer -n prod

# 所有 namespace 的 RoleBinding 主體
kubectl get rolebinding -A -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,ROLE:.roleRef.name,SUBJECTS:.subjects[*].name'
```

**`auth can-i --list` 是產生存取清單最可靠的方式**——它反映的是實際生效的權限，而不是「我以為我設了什麼」。

### 職務分離：GitOps 天然滿足

「寫程式的人不能自己把程式推上生產」是幾乎所有框架都有的要求。傳統做法是「開發者沒有生產環境的部署權限，要開單給維運」——慢、而且維運只是照做，並沒有真正審查。

**GitOps 的結構天然滿足這一項，而且比開單更好**：

| 要求 | GitOps 怎麼滿足 |
| --- | --- |
| 變更要經過審查 | manifest repo 的 PR review（可強制至少一人核准） |
| 執行者與核准者分離 | 提交者不能核准自己的 PR（repo 設定） |
| 人不直接碰生產 | **只有 ArgoCD 有叢集寫入權限**，人只有讀 |
| 變更可回溯 | git 歷史 |

**「只有 ArgoCD 有寫入權限」這一條要真的做到**——如果開發者仍然有 `kubectl apply` 的權限，那職務分離只是紙上的。務實的做法是：生產環境的人類身分一律只給 `view`，寫入權只給 ArgoCD 的 ServiceAccount。

### 特權存取與 break-glass

但總會有「必須立刻手動介入」的時刻（附錄 P 的事故應變）。完全禁止會逼人繞過流程，所以要**設計一條有紀錄的緊急通道**：

- 一個平常不啟用的高權限帳號或 RoleBinding
- 啟用需要第二人核准（或至少通知）
- **啟用本身會產生告警**（讓所有人知道有人用了）
- 有時效，事後自動撤銷
- 用完要補一份說明

**「有 break-glass 且它被用過並留下紀錄」比「沒有 break-glass 但大家都有 admin」好得多**，而且稽核者通常更能接受前者。

### 定期存取審查

多數框架要求定期（季或半年）確認「這些人還需要這些權限嗎」。要讓它可執行，關鍵是**清單要能自動產生**——把上面那幾條指令包成一個腳本，定期輸出成表格交給負責人確認即可。

離職流程也要涵蓋：**人走了，他的 OIDC 群組成員資格移除之後，K8s 的權限就自動失效**——這是用群組而非個人綁定的好處（[[08-security-and-rbac]]）。

## Part 3：變更管理

稽核者會問四件事：**誰改的、什麼時候、誰核准、能不能回溯**。

GitOps 環境的答案很乾淨：

| 問題 | 證據 |
| --- | --- |
| 誰改的 | git commit author |
| 什麼時候 | commit / ArgoCD sync 時間 |
| 誰核准 | PR 的 approver |
| 能不能回溯 | `git log` + `argocd app history` |

### 但有三個漏洞

**漏洞一：手動 `kubectl`。** 有人繞過 git 直接改叢集，那個變更沒有任何紀錄。**`selfHeal: true` 讓它被自動改回去**（實戰第三章），但更重要的是它讓「繞過 git」變成技術上做不到——這比規定有效得多。

**漏洞二：緊急變更。** 事故當下沒有人會先開 PR。所以要有**事後補登**的流程：緊急變更允許先做，但要求在 N 小時內補上 git 的對應變更與說明。這件事要寫進 runbook（[[30-production-readiness]]）。

**漏洞三：平台層變更。** 升級 K8s、換 Ingress controller、改 PSA 政策——這些常常不在應用的 manifest repo 裡。**平台層的設定也應該進 git**（IaC 或另一個 repo），否則變更管理只涵蓋了一半。

### 稽核者會想看的證據

- 一段時間內所有生產變更的清單（`git log` 加篩選即可）
- 隨機抽一筆，能追到：PR、核准者、部署時間、對應的叢集狀態
- 有變更失敗後回滾的例子（證明回滾機制真的能用）

**最後一項常被忽略**：稽核者想看的不是「沒有失敗過」，而是「失敗時有妥善處理」。有一筆漂亮的回滾紀錄，比宣稱從未出錯更有說服力。

## Part 4：稽核軌跡

### K8s audit log

附錄 C-6 有完整的 `Policy` 欄位，這裡講合規視角的三個要求：

**該記什麼。** 最小配置是：Secret 相關操作記 `RequestResponse`、RBAC 變更記 `RequestResponse`、其餘寫入類記 `Metadata`、高頻的唯讀（`system:kube-proxy` 的 watch）設 `None` 避免淹沒。

**必須送到叢集外。** 留在節點上的稽核日誌，攻擊者取得節點權限後第一件事就是清掉它（附錄 P）。而且從合規角度，**存在被稽核對象自己的機器上的日誌，證據力是有問題的**。

**保留期要對得上要求。** 稽核日誌的保留期通常遠長於除錯日誌（附錄 AG 的三種用途分開存放，這裡是它的合規理由）。

### 稽核者可能會問的具體問題

| 問題 | 怎麼回答 |
| --- | --- |
| 誰讀過這個 Secret？ | audit log 篩 `objectRef.resource=secrets` + `objectRef.name` + `verb=get/list` |
| 誰改過 RBAC？ | 篩 `objectRef.apiGroup=rbac.authorization.k8s.io` + 寫入類 verb |
| 有沒有人嘗試越權？ | 篩 `responseStatus.code=403`，看有沒有集中在某個身分 |
| 這個 Pod 是誰建立的？ | 篩 `verb=create` + `objectRef.name` |
| 生產環境有人手動改過東西嗎？ | 篩非 ArgoCD ServiceAccount 的寫入操作 |

**最後一條特別有價值**：它同時是合規證據與漂移偵測。把它做成定期報表，你會知道「職務分離」是不是真的在運作。

### 應用層的稽核是另一回事

K8s 的 audit log 記的是「誰對叢集做了什麼」，**不記「誰對業務資料做了什麼」**。「誰查了某位客戶的資料」「誰核准了這筆交易」屬於應用層的稽核，要由應用自己記錄（附錄 AG 的第三類用途）。

**兩者都需要，而且不能互相取代**——這是常被混淆的一點。

## Part 5：資料保護

### 三個位置要盤點

稽核會問「敏感資料在哪裡」，而 K8s 環境的答案通常比想像中分散：

| 位置 | 保護手段 |
| --- | --- |
| **資料庫**（多在叢集外） | 資料庫自己的加密與存取控制 |
| **PV / 物件儲存** | 靜態加密、存取控制（附錄 AD） |
| **etcd**（Secret 存在這裡） | `EncryptionConfiguration` 靜態加密（附錄 C-6） |
| **日誌**（最常被遺忘） | 不要記個資（附錄 AG）；已經記了要有清理機制 |
| **備份** | 備份也含有敏感資料，同樣要加密與存取控制 |

**「日誌」與「備份」是最常被漏掉的兩個。** 個資盤點如果只列了資料庫，稽核者一問「那日誌裡有沒有」通常就沒有答案。

### 刪除請求在 K8s 環境的難處

個資法規常有「被遺忘權」——使用者要求刪除他的資料。技術上的難處是：**資料庫刪掉了，備份裡還有**（附錄 L 的保留期可能是數月）。

務實的處理方式有三種，要事先決定並寫下來：**備份保留期到期後自然消失**（要能說明期限）、**還原時套用刪除清單**（還原後重跑一次刪除）、或**對特定資料做加密刪除**（銷毀金鑰使其不可還原）。

**這件事不能等到收到請求才想**——它牽涉備份策略，而備份策略改不了過去已經產生的備份。

### 資料落地位置

多數框架會問「資料存在哪個國家/區域」。K8s 環境要能回答：節點在哪個區域、PV 在哪個區域、備份送到哪裡、日誌送到哪裡、以及**第三方服務（監控 SaaS、錯誤收集）把資料送去哪**。

最後一項最常被漏掉——把日誌送到境外的 SaaS，在某些規範下是需要說明的。

## Part 6：讓證據自動產生

**這一節是整份最有價值的部分。**

多數團隊的合規成本集中在「稽核季花兩週截圖」。而 K8s 環境有一個特性可以徹底改變這件事：**它的狀態是可查詢的**。

### 從「事後蒐證」到「持續證據」

把稽核者要的東西做成定期自動產生的報表：

| 證據 | 怎麼自動產生 |
| --- | --- |
| 誰有生產環境權限 | `auth can-i --list` 對每個身分，輸出成表 |
| 所有生產變更清單 | `git log --since` + ArgoCD sync 歷史 |
| 違反安全基線的工作負載 | `kube-linter` / policy report |
| 未加密或公開的儲存 | 掃描 bucket 設定與 PV 設定 |
| 有漏洞的映像 | `trivy` 定期掃描報告（附錄 P） |
| 備份與演練紀錄 | 演練時就記錄，而不是事後回想 |
| 存取審查結果 | 每季的清單與確認紀錄 |

**做成 CronJob 每月輸出一次**（附錄 AC），存到物件儲存。稽核時直接給檔案，而不是臨時去撈。

### Policy as code 本身就是證據

這是 K8s 環境相對於傳統環境的實質優勢：**「我們規定不能用 root」是一句話，「這是擋掉 root 的 admission policy，這是它的測試，這是它上線的 git commit」是證據。**

同一份 policy 同時做到三件事：**強制執行**（實際擋住）、**證明存在**（在 git 裡）、**證明有效**（有測試與被擋的紀錄）。傳統環境需要分別準備這三樣。

所以**附錄 O 講的「能自動強制的就不要靠 review」，在合規視角有第二層價值**——它同時省下了蒐證的工作。

### 演練紀錄要當下就記

還原演練（附錄 L）、事故檢討（附錄 H）、存取審查——**這些都要在做的當下就留下紀錄**，包含日期、參與者、實際耗時、發現的問題。

事後回想「我們去年好像有演練過」是沒有證據力的，而且通常也想不起細節。**一份簡單的表格，做完就填，比什麼都有用。**

## Part 7：十個常見提問與準備

| # | 稽核者的問題 | 你該能拿出什麼 |
| --- | --- | --- |
| 1 | 誰能存取生產環境？ | `auth can-i --list` 產生的清單 + 最近一次審查紀錄 |
| 2 | 開發者能自己部署到生產嗎？ | RBAC 顯示人類身分只有 `view`；只有 ArgoCD 有寫入權 |
| 3 | 這個變更誰核准的？ | PR 的 approver + ArgoCD sync 紀錄 |
| 4 | 有人繞過流程直接改過嗎？ | audit log 篩非 ArgoCD 的寫入操作（定期報表） |
| 5 | 敏感資料存在哪、怎麼加密？ | 位置盤點表 + etcd 加密設定 + 儲存加密設定 |
| 6 | 誰讀過這個 Secret？ | audit log 查詢 |
| 7 | 備份多久一次？還原過嗎？ | 備份排程 + **演練紀錄含實際耗時** |
| 8 | 你們跑的映像從哪來、有沒有漏洞？ | registry 來源 + 掃描報告 + 簽章驗證政策 |
| 9 | 怎麼確保沒人偏離安全設定？ | PSA `enforce` + admission policy + policy 報表 |
| 10 | 出事了怎麼辦？ | 事故分級與流程 runbook + 上一次事故的檢討報告 |

**注意第 7 與第 10 的共同點：稽核者要的不是「我們有政策」，而是「政策被執行過的紀錄」。** 這也是為什麼演練與檢討的紀錄比政策文件本身更重要。

## 檢查清單

### 存取控制

- [ ] 能用指令列出「誰能碰生產環境」
- [ ] 生產環境的人類身分只有讀取權，寫入只給 ArgoCD
- [ ] 權限綁在**群組**而非個人（離職自動失效）
- [ ] 有 break-glass 通道，且啟用會產生告警與紀錄
- [ ] 定期存取審查，清單自動產生

### 變更管理

- [ ] 所有應用變更透過 git + PR review
- [ ] 提交者不能核准自己的 PR
- [ ] **平台層變更也在 git 裡**
- [ ] `selfHeal` 開啟（讓繞過 git 變成做不到）
- [ ] 緊急變更有事後補登流程

### 稽核軌跡

- [ ] K8s audit log 已開啟，且**送到叢集外**
- [ ] Secret 與 RBAC 操作記錄到 `RequestResponse` 級別
- [ ] 保留期符合要求
- [ ] 應用層的業務稽核另外實作（不能靠 K8s audit log）

### 資料保護

- [ ] 敏感資料位置已盤點，**含日誌與備份**
- [ ] etcd 靜態加密已啟用
- [ ] 刪除請求的處理方式已事先決定並寫下
- [ ] 資料落地位置能回答（含第三方 SaaS）

### 證據自動化

- [ ] 主要證據有定期自動產生的報表
- [ ] Policy as code（同時是強制與證據）
- [ ] **演練與檢討當下就留紀錄**（日期、參與者、耗時、發現）

## 常見誤區

| # | 誤區 | 真相 |
| --- | --- | --- |
| 1 | 安全做好了合規就自然過 | 合規要的是**證明**，證據沒整理一樣過不了 |
| 2 | 稽核季再來蒐證 | 很多證據事後產生不出來（例如「當時誰有權限」） |
| 3 | 有政策文件就夠 | 稽核者要的是**執行紀錄**，不是文件 |
| 4 | 職務分離＝開單給維運 | 維運只是照做並未審查；GitOps 的 PR review 更實質 |
| 5 | 禁止所有手動操作 | 會逼人繞過；要設計有紀錄的 break-glass |
| 6 | K8s audit log 涵蓋業務稽核 | 它只記對叢集的操作，業務事件要應用自己記 |
| 7 | audit log 留在節點上就好 | 可被清除，且證據力有問題 |
| 8 | 個資盤點只要列資料庫 | **日誌與備份最常被漏掉** |
| 9 | 刪除請求刪資料庫就好 | 備份裡還有；要事先決定處理方式 |
| 10 | 演練有做就好，紀錄不重要 | 沒紀錄等於沒做過 |
