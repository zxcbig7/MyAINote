# 附錄 V：知識傳承與團隊能力建立

附錄 O 講的是平台——技術與制度怎麼設計，讓五個團隊能自己上線。這一份講剩下的那一半：**人**。

因為即使平台做得再好，還是會剩下一批只有你知道的東西：這座叢集為什麼這樣設計、那個 webhook 是誰裝的、半夜出事時第一個要看哪裡。而這帶來一個具體的風險——**你請假的那一週，誰接？**

這一份處理那個問題。它是整套教材裡唯一一份不談技術的，但對一個 K8s 管理員來說，它決定的東西不比前面 44 份少。

---

## Part 1：先誠實測一次

三個問題，答案不用告訴別人：

1. **你明天開始請假兩週，有人能處理 P1 事故嗎？** 不是「有人有權限」，是「有人知道從哪裡查」。
2. **你離職的話，公司剩下什麼？** 一座能跑的叢集，還是一座沒人敢動的叢集？
3. **上一次有人（不是你）獨立完成一次生產環境變更，是什麼時候？**

第三題最能反映真實狀況。如果答案是「沒有」或「想不起來」，那你目前是單點故障——**而且這通常不是因為別人學不會，是因為所有事情都由你處理，別人沒有機會學。**

一個殘酷但有用的觀察：**「只有我會」在短期是安全感，長期是負債。** 它讓你無法休假、無法專注在更高價值的事、而且組織會把你困在原地——因為你太重要而不能被調去做別的。

## Part 2：不是每個人都要學全部

最常見的知識傳承失敗，是把「傳承」理解成「大家都要學會我會的東西」。那不可能發生，也不必要。

正確的做法是**分層**——先定義每個角色需要什麼，再針對性地建立。

| 角色 | 必須會 | 不必會 |
| --- | --- | --- |
| **一般開發者** | 看自己服務的日誌與狀態、改 values 部署、看懂常見錯誤訊息、知道出事找誰 | etcd、CNI、scheduler 內部、RBAC 設計 |
| **資深開發者／技術負責人** | 上面全部 + 寫完整 manifest、probe 與資源設定、排查自己服務的問題 | 叢集升級、節點維護、網路外掛 |
| **值班人員** | 上面全部 + 分層定位、狀態判讀、隔離與回滾、什麼時候該叫人 | 深度調校、Operator 開發 |
| **平台工程師** | 全部 | — |

**「一般開發者不需要懂 etcd」這句話值得說清楚。** 有些人會覺得「都上 K8s 了大家當然要懂」，但那是把成本強加給所有人。開發者的時間應該花在他們的業務邏輯上；平台的職責是讓他們**不需要**懂那些也能安全上線（附錄 O 的 golden path）。

**要求所有人都學到平台工程師的深度，實際結果是沒有人學。**

## Part 4：文件該怎麼組織

多數團隊的文件失敗不是因為寫太少，是因為**四種不同性質的文件被混在同一頁**。

| 類型 | 回答什麼 | 讀者狀態 | 例子 |
| --- | --- | --- | --- |
| **教學**（tutorial） | 「帶我做一次」 | 完全新手，要建立信心 | 入門篇 |
| **操作指南**（how-to） | 「我要做 X，步驟是什麼」 | 有目標，要完成任務 | runbook、實戰篇 |
| **參考**（reference） | 「這個欄位是什麼意思」 | 查東西 | 附錄 C 系列 |
| **說明**（explanation） | 「為什麼要這樣設計」 | 想理解 | 正文 16 章 |

**這套教材本身就是這個分類的實踐**——入門篇是教學、實戰篇是操作指南、附錄 C 是參考、正文是說明。它們刻意分開，因為混在一起會同時失敗：新手被細節淹沒、老手找不到要查的東西。

實務上最常見的錯誤是**把 runbook 寫成教學**——半夜三點被叫起來的人不需要「為什麼會有這個機制」，他需要「第一步做什麼」。反過來，新人培訓文件塞滿指令但不解釋原理，他照做了但學不會。

### 什麼不該寫進文件

**會過期而且沒人會更新的東西。** 具體來說：

| 不該寫 | 該怎麼做 |
| --- | --- |
| 「目前有哪些服務」清單 | 讓它從叢集或 git 自動產生 |
| 「資源配置是多少」 | 指向 git 裡的 manifest |
| 詳細的 UI 點擊步驟 | 改成指令，或截圖只放關鍵畫面 |
| 「某某人負責某某系統」 | 用 label / OWNERS 檔，靠近程式碼 |

**判準：如果這份資訊在系統裡已經有一份權威來源，文件應該指向它而不是複製它。** 複製的那份注定會過期，而且過期的文件比沒有文件更危險——因為人會相信它。

### 文件要有所有權與保鮮期

每份文件標上：負責人、最後驗證日期、下次該檢查的時間。**runbook 尤其要標「上次演練日期」**——沒演練過的 runbook 跟沒備份過的備份是同一種東西（附錄 L）。

## Part 5：讓知識真的流動

寫文件是必要條件，不是充分條件。**知識主要透過「一起做事」傳遞，不是透過閱讀。** 五個具體機制：

### 1. 輪值

值班輪流是最有效的知識傳遞機制，因為它強制每個人都要面對真實問題。

導入時的節奏很重要：**新人第一次值班要有 shadow 期**——他跟著看，你處理；第二階段他處理，你在旁邊；第三階段他獨立處理，你只在他求助時介入。直接讓人獨立值班是不負責任的，但永遠不讓人獨立值班同樣有問題。

**事故指揮也該輪流。** 指揮不是最懂技術的人做，是負責決策與溝通的人做——輪流做能讓每個人理解事故的全貌而不只是自己那一塊。

### 2. 配對排錯

下次有人來問「我的 Pod 起不來」時，不要直接給答案。**開一個共享畫面，讓他操作，你在旁邊問問題**：「你怎麼知道是這個 Pod？」「describe 的 Events 說什麼？」

這比直接解決慢五倍，但下次他自己會查。**把「我來處理」換成「我陪你處理一次」，是知識傳承最直接的槓桿。**

### 3. 事故檢討當成教材

每次事故的檢討報告（附錄 H）都是最好的教材——它有真實的情境、真實的症狀、真實的推理過程。把它們集中放，新人培訓時讀。

正文第 13 章那 19 個真實案例就是這個做法的產物。**你的環境會累積出自己的版本，而它比任何外部教材都貼近你的實際情況。**

### 4. 分享要用實際操作，不是投影片

內部技術分享最沒效的形式是「一個人講 30 張投影片」。有效的形式是：

- **live 排錯**：在測試環境弄壞一個東西，現場查
- **一起讀一份 manifest**：逐欄位問「這個為什麼要設」
- **回顧一次真實事故**：從告警開始，重走一次推理過程

附錄 D 的 20 個實驗設計成這種形式——**破壞、觀察、診斷、修復**。拿它當團隊活動的素材比自己準備投影片省力得多。

### 5. 用「新人上手時間」當品質指標

一個具體可量測的目標：**新人第一週能不能自己把一個服務部署到開發環境？**

這個數字反映的是文件、範本、權限、環境的整體品質。如果要三週，問題不在新人身上（附錄 O 的度量那節說過同樣的邏輯）。

## Part 6：避免知識腐敗

知識傳承的另一半是**維持它不過期**。文件與現實的偏離是必然的，只能靠機制減緩。

**最有效的做法是：用可執行的東西取代文件。**

| 原本靠文件 | 改成可執行 |
| --- | --- |
| 「記得要設 resources.limits」 | admission policy 直接擋（附錄 O） |
| 「部署前要檢查這幾項」 | CI 跑 kube-linter（實戰第四章） |
| 「不要用 latest 標籤」 | 政策擋掉 |
| 「這個服務要留兩個副本」 | PDB |
| 「憑證快到期要換」 | 告警（附錄 H） |
| 「還原步驟是這樣」 | **腳本 + 定期演練**（附錄 L） |

**可執行的東西不會過期**——它要嘛能跑，要嘛壞掉被發現。文件則會靜靜地變成錯的。

剩下真的需要文件的部分（設計決策、為什麼這樣選、歷史脈絡），用**輕量的決策紀錄**：一頁、寫清楚背景與選項與理由、標日期、之後不改（要改就寫新的一份）。這種紀錄的價值在半年後——當有人問「為什麼當初不用 X」時，你有答案而不是憑印象。

## Part 7：你自己該改變的四件事

技術之外，這是最難的部分，因為它要求你**刻意放棄一部分掌控**。

**1. 不要當唯一的解答者。** 有人私訊問問題時，請他發到公開頻道——不是為了擺架子，是為了讓下一個人搜尋得到，也讓其他人有機會回答（附錄 O 的支援分層）。

**2. 刻意讓別人做你會做的事。** 下一次升級叢集，讓另一個人主導、你在旁邊。第一次會比較慢、可能出錯——那是必要的投資。**你自己做十次也不會讓團隊變強。**

**3. 把決策過程說出來。** 你判斷「這應該是 DNS 問題」的時候，把推理講出來而不只是結論。**別人學的是推理，不是答案。**

**4. 定期休假，而且真的不接。** 這是唯一誠實的測試——如果團隊在你休假時撐得住，傳承就成功了；撐不住的話，你會確切知道缺口在哪。

**很多人不敢做第四項，因為怕出事。但一直不測試的結果，是你永遠不知道自己有多脆弱**，而且真正非計畫性的缺席（生病、離職）不會事先通知。

## 常見失敗模式

| # | 失敗模式 | 症狀 | 解法 |
| --- | --- | --- | --- |
| 1 | 要求所有人學全部 | 沒有人學 | 分層，定義每個角色的最小集合 |
| 2 | 丟文件叫人自己讀 | 讀不完，也不知從何開始 | 給路徑而不是給資料 |
| 3 | 四種文件混在一起 | 新手被淹沒，老手找不到 | 教學/指南/參考/說明分開 |
| 4 | 文件複製系統裡已有的資訊 | 過期，且比沒文件更危險 | 指向權威來源 |
| 5 | runbook 沒演練過 | 事故當下才發現步驟不對 | 標上演練日期並定期執行 |
| 6 | 只靠文件傳承 | 知道但不會做 | 配對排錯、輪值、實驗 |
| 7 | 分享用投影片 | 聽完就忘 | live 排錯、一起讀 manifest |
| 8 | 什麼都自己處理 | 別人沒機會學 | 「我陪你處理一次」 |
| 9 | 從不休假 | 不知道團隊有多脆弱 | 定期休假當測試 |
| 10 | 把「只有我會」當安全感 | 被困在原地無法成長 | 那是負債不是資產 |

## 檢查清單

**能力分層**

- [ ] 四種角色的知識範圍已定義
- [ ] 每個角色有對應的閱讀路徑與**時數估計**
- [ ] 值班路徑的驗收是**實作測驗**而非「讀完」

**文件**

- [ ] 教學 / 操作指南 / 參考 / 說明四類分開
- [ ] runbook 是「第一步做什麼」不是「原理是什麼」
- [ ] 沒有複製系統裡已有的資訊
- [ ] 每份文件有負責人與最後驗證日期
- [ ] 重要決策有輕量的決策紀錄

**流動機制**

- [ ] 值班輪流，且新人有 shadow 期
- [ ] 事故指揮也輪流
- [ ] 有配對排錯的習慣
- [ ] 事故檢討被收集成內部案例庫
- [ ] 分享是實際操作而非投影片

**防腐**

- [ ] 能自動強制的規則已改成 policy / CI 檢查
- [ ] runbook 有定期演練（附錄 L 的三個情境）
- [ ] 新人上手時間有在量測

**你自己**

- [ ] 至少有一個人能處理 P1 事故
- [ ] 最近三個月有人（不是你）獨立完成生產變更
- [ ] 你有休過假且沒被找
