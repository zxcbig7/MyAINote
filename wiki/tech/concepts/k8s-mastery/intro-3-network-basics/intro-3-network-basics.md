# 入門第三章：兩台電腦怎麼講話

上一章你學會在一台機器裡活動。這一章要跨出去——因為服務的意義就是讓**別人**連得到。

這一章不會講網路的完整理論，只講一件事：**你在瀏覽器打上網址按下 Enter 之後，到底發生了哪幾件事**。把這條路走一遍，K8s 網路那一章的所有概念都會有掛鉤的地方。

## 一次請求的完整旅程

假設你輸入 `https://example.com/api/users`，中間發生五件事：

1. **找地址**：`example.com` 是名字，電腦需要的是數字位址 → 問 DNS
2. **敲門**：拿到位址後，往那台機器的 443 號門建立連線 → TCP
3. **驗身分並加密**：確認對方真的是 example.com，然後把通道加密 → TLS
4. **提出請求**：「我要 GET /api/users」→ HTTP
5. **收到回應**：狀態碼 + 資料 → HTTP response

下面逐一拆開。

## IP 位址：機器的門牌

網路上每台機器有一個 **IP 位址**，格式像 `140.112.8.116`（四個 0–255 的數字）。這是上一章那個「公寓大樓地址」的比喻裡的地址部分，port 則是房號。

IP 分兩種，這個區分很重要：

| 種類 | 範圍 | 意義 |
| --- | --- | --- |
| **公有 IP** | 上面兩類以外 | 全世界都連得到，要跟 ISP 或雲端業者取得 |
| **私有 IP** | `10.x.x.x`、`172.16–31.x.x`、`192.168.x.x` | **只在自己的網路內有效**，外面連不到 |

你家路由器分給筆電的通常是 `192.168.1.x`——這是私有 IP。所以就算你在自己電腦上跑起了服務，同一個 Wi-Fi 底下的人連得到，但網路上的其他人連不到。

還有一個特別的：**`127.0.0.1`，別名 `localhost`**，意思是「我自己這台機器」。上一章你打開 `http://localhost:8000` 就是在連自己。

**這裡先埋一個伏筆**：K8s 給每個 Pod 分配的 IP 也是私有 IP，只在叢集內部有效。這就是為什麼「Pod 有 IP 但外面連不到」——不是壞了，是設計如此。要讓外面連得到需要額外的東西（Service、Ingress），那正是它們存在的理由。

## DNS：把名字翻成數字

沒有人記得住 IP，所以有了 **DNS（Domain Name System）**——一個把名字翻成 IP 的全球查詢系統。

你可以親眼看到這個翻譯：

```powershell
Resolve-DnsName example.com
nslookup example.com
```

DNS 紀錄有幾種類型，日常會遇到的是這幾種：

| 類型 | 作用 |
| --- | --- |
| `A` | 名字 → IPv4 位址 |
| `AAAA` | 名字 → IPv6 位址 |
| `CNAME` | 名字 → 另一個名字（別名） |
| `TXT` | 任意文字，常用於驗證網域所有權 |
| `MX` | 郵件伺服器 |

兩個實務上一定會遇到的細節：

**TTL 與快取。** DNS 結果會被快取一段時間（TTL，存活時間）。所以你改了 DNS 設定之後，不會立刻全世界都生效——舊的答案還在別人的快取裡。這是「我明明改了為什麼還連到舊的」的標準答案。改 DNS 前先把 TTL 調短，是老手的習慣。

**hosts 檔案。** 每台電腦上有一個檔案可以強制指定「這個名字對應這個 IP」，優先於 DNS。Windows 在 `C:\Windows\System32\drivers\etc\hosts`，Linux 在 `/etc/hosts`。測試時很好用，但也是「為什麼只有我的電腦連錯地方」的經典元兇。

> K8s 內部也有一套 DNS（CoreDNS），把 Service 名稱翻成叢集內的 IP。所以在 K8s 裡你可以直接用 `http://my-service` 連到另一個服務，不必知道它的 IP——這跟外網 DNS 是同一個原理，只是範圍限於叢集內。

## TCP：建立一條可靠的通道

拿到 IP 之後要建立連線。網路上最常用的是 **TCP**，它的特性是「可靠」：資料保證會到、保證順序正確、丟了會重傳。

TCP 連線建立時會有一次「三次握手」（你打招呼、對方回應、你確認），這個細節現在不重要，重要的是它的**副作用**：建立連線本身要花時間（一個來回）。這就是為什麼頻繁地開關連線很浪費，也是「連線池」與 keep-alive 存在的理由。

相對的還有 **UDP**：不保證送達、不保證順序，但快。DNS 查詢就是用 UDP（查不到就再問一次，比維護連線划算）。

測試某台機器的某個 port 通不通：

```powershell
Test-NetConnection example.com -Port 443
```

回傳 `TcpTestSucceeded : True` 代表通。**這個指令是網路排錯的第一把刀**：它可以把「DNS 有沒有問題」跟「port 有沒有開」分開判斷。

## HTTP：請求與回應長什麼樣

HTTP 是網頁世界的共同語言。它的結構比想像中簡單——就是一段文字。

一個請求長這樣：

```
GET /api/users HTTP/1.1
Host: example.com
Authorization: Bearer eyJhbGci...
Accept: application/json
```

四個部分：**方法**（GET）、**路徑**（/api/users）、**標頭**（那幾行 Key: Value）、以及可選的**主體**（POST 時放要送出的資料）。

常見方法：

| 方法 | 語意 |
| --- | --- |
| `GET` | 取得資料，不應該改變任何東西 |
| `POST` | 新增，或觸發某個動作 |
| `PUT` / `PATCH` | 更新（整份／部分） |
| `DELETE` | 刪除 |

回應也是文字：

```
HTTP/1.1 200 OK
Content-Type: application/json

{"users": [...]}
```

**狀態碼是排錯時最有用的資訊**，因為它直接告訴你問題出在哪一端：

| 範圍 | 意義 | 常見的 |
| --- | --- | --- |
| 2xx | 成功 | `200 OK`、`201 Created`、`204 No Content` |
| 3xx | 轉址 | `301` 永久、`302` 暫時 |
| **4xx** | **你（客戶端）有問題** | `400` 格式錯、`401` 沒登入、`403` 沒權限、`404` 找不到、`413` body 太大、`429` 太頻繁 |
| **5xx** | **伺服器有問題** | `500` 程式爆炸、`502` 上游壞了、`503` 暫時無法服務、`504` 上游逾時 |

**4xx 與 5xx 的分界是排錯的第一個分岔**：4xx 表示請求本身有問題（改請求），5xx 表示伺服器端出事（去查服務）。

其中三個在 K8s 環境特別常見，先記起來：

- **502 Bad Gateway**：代理連得到，但後面的服務掛了或回了無效內容 → 去看後端 Pod
- **503 Service Unavailable**：代理找不到任何可用的後端 → 通常是所有 Pod 都沒 Ready
- **504 Gateway Timeout**：後端太慢，代理等不下去 → 看逾時設定與後端效能

用 curl 親自看一次完整的請求與回應：

```powershell
curl.exe -v https://example.com
curl.exe -s -o NUL -w "status=%{http_code} time=%{time_total}s`n" https://example.com
```

（Windows 上要寫 `curl.exe`，因為 `curl` 是 PowerShell 的別名，參數不一樣——上一章提過的別名陷阱。）

## HTTPS 與憑證：在證明什麼

HTTP 是明文的，中間任何一個路由器都看得到內容。HTTPS 在 HTTP 外面包一層 **TLS** 加密，解決兩個問題：**內容不被偷看**，以及**確認對方真的是他宣稱的那個網站**。

第二點靠**憑證**。憑證本質上是一份由公信第三方（CA，憑證頒發機構）簽名的文件，內容大意是「我證明持有這個憑證的人，確實擁有 example.com 這個網域」。你的瀏覽器內建一份信任的 CA 清單，憑證由清單內的 CA 簽的就綠鎖頭，否則跳警告。

實務上會遇到的三種憑證問題：

| 症狀 | 原因 |
| --- | --- |
| 憑證過期 | 憑證有有效期（Let's Encrypt 是 90 天），沒自動續簽就會過期 |
| 名稱不符 | 憑證是簽給 `example.com` 的，你用 `www.example.com` 連 |
| 憑證不受信任 | 自簽憑證，或 CA 不在信任清單裡 |

憑證過期是很典型的「不做事就會壞」的東西——所以 K8s 環境會用 cert-manager 自動續簽，並且把「憑證剩餘天數」做成告警。

檢查一個網站的憑證：

```powershell
curl.exe -vI https://example.com 2>&1 | Select-String "expire|subject|issuer"
```

## 反向代理與負載平衡

上一章結尾說過，服務量大了要多開幾台。那使用者怎麼知道要連哪一台？答案是**他不知道，也不需要知道**——前面放一個分派員。

這個分派員有兩個名字，因為它做兩件事：

**反向代理（reverse proxy）**：所有請求先到它這裡，它再轉給後面真正的服務。好處是後端可以隨意增減、換位置，外面完全無感；還可以順便做 TLS 終結（在代理這裡解密，後面走明文，省後端的計算）、快取、壓縮。

**負載平衡（load balancer）**：決定這次請求要轉給哪一台，讓流量平均分散。

nginx 同時扮演這兩個角色，這也是為什麼它在 K8s 世界無所不在——**Ingress Controller 本質上就是一個會自動讀取 K8s 設定並改寫自己 nginx 設定檔的反向代理**。

```
使用者 → [反向代理] → 服務A 副本1
                    → 服務A 副本2
                    → 服務B 副本1
```

這張圖之後會反覆出現，只是名字換成 Ingress、Service、Pod。

## 為什麼你家的電腦別人連不到

最後補一個常見困惑。你在自己電腦跑了服務，同事連不到，通常有三層原因：

1. **私有 IP**：你的電腦在路由器後面，沒有公有 IP（需要 NAT 轉發或穿隧工具）
2. **防火牆**：作業系統或公司網路擋掉了外來連線
3. **服務只聽 localhost**：程式綁在 `127.0.0.1` 而不是 `0.0.0.0`，等於只接受本機連線

第三點特別容易中招，而且在容器裡也會發生：**容器裡的程式如果綁 `127.0.0.1`，即使 port 對了，外面也永遠連不到它**。要對外服務就必須綁 `0.0.0.0`（所有網路介面）。這是新手部署第一個服務時最常撞的牆之一。

## 網路排錯的固定順序

遇到「連不上」的時候，照這個順序查，每一步都能排除一大塊可能性：

| 步驟 | 指令 | 通過代表 |
| --- | --- | --- |
| 1. 名字能不能翻成 IP | `Resolve-DnsName x.com` | DNS 正常 |
| 2. 對方 port 通不通 | `Test-NetConnection x.com -Port 443` | 網路可達且有程式在聽 |
| 3. HTTP 回什麼 | `curl.exe -v https://x.com` | 應用層有回應 |
| 4. 看狀態碼 | 同上 | 4xx 查請求，5xx 查服務 |

**不要跳步。** 直接看應用日誌卻發現是 DNS 沒設好，是很常見的時間浪費。

## 這些概念在 K8s 裡的對應

這張表是這一章的收束，也是之後學 K8s 網路時的翻譯詞典：

| 你剛學的 | K8s 裡對應的東西 |
| --- | --- |
| 私有 IP | Pod IP、ClusterIP（只在叢集內有效） |
| DNS | CoreDNS，把 Service 名稱翻成 ClusterIP |
| port | Service 的 `port` 與容器的 `targetPort` |
| 負載平衡 | Service（自動把流量分給多個 Pod） |
| 反向代理 | Ingress + Ingress Controller |
| TLS 憑證 | `kubernetes.io/tls` 型別的 Secret，用 cert-manager 自動續簽 |
| 防火牆規則 | NetworkPolicy |
| 綁 `0.0.0.0` 才連得到 | 容器裡的程式必須綁 `0.0.0.0` |

## 本章回顧

- 一次請求 = DNS 找地址 → TCP 建連線 → TLS 驗身分加密 → HTTP 提請求 → 收回應
- 私有 IP 只在自己網路內有效，`127.0.0.1` 是自己
- DNS 有快取（TTL），所以改了不會立刻生效
- 4xx 是請求有問題，5xx 是伺服器有問題；502/503/504 各自指向不同的地方
- HTTPS 的憑證在證明「我真的是這個網域」，而憑證會過期
- 反向代理 + 負載平衡 = Ingress Controller 的本質
- 程式綁 `127.0.0.1` 就只有自己連得到，要對外必須綁 `0.0.0.0`
