## 為什麼 specification 不等於 constraint

在讀完 [[system-elements]]、[[decision-activities]]、[[system-calculations]] 三章之後，讀者已經知道怎麼從一個系統中辨識出元素、決策活動與輔助計算。但一個模型光有變數還不夠——系統裡總有一些「規則」在限制哪些決策組合是允許的：不能超過某個容量、兩個東西不能同時選、某個條件成立時必須做另一件事。García Sánchez 把這些規則統稱為 **specification（規格）**，並且從一開始就刻意把它跟 **constraint（限制式）** 分開來看。

這個區分不是文字遊戲。Specification 是系統對某個行為所做的「陳述」——它可能來自文字描述裡的一句話（「每輛車只能選一條路線」），也可能只是隱含在資料裡從沒被明講過。Constraint 則是這句陳述被翻譯成數學之後的產物：一條不等式或等式。兩者不是一對一的關係，書中會反覆看到同一個 specification 被拆成好幾條 constraint，也會看到好幾個 specification 合併成一條 constraint（甚至看到同一條 constraint 同時扮演兩種語意角色）。如果把它們混為一談，讀模型的人很容易忘記「這條不等式當初到底想表達什麼」，之後要修改需求時也不知道該動哪裡。

作者也提到 Williams（2013）已經嘗試對 constraint 做分類，但他認為唯一「100% 有效」的分類法是依 constraint 的符號（≤、≥、=）來分——問題是，這種分類完全沒有觸及 constraint 的**語意**。兩條同樣是 `≤` 的不等式，一條可能在講「產能上限」，另一條可能在講「兩個東西不能同時被選」，意義天差地遠。García Sánchez 想要的是一套依「規格的意義」分類的系統，這正是本章的核心貢獻。

## 兩層分類：陳述方式優先

分類的第一層不看語意，而看規格**是怎麼被陳述的**。回顧 [[system-calculations]] 提過的命題（proposition）概念——一個命題在套用到某組解上時能被判定真或假——規格可以是：

- **Simple（simple proposition，又稱 atomic）**：不能再被拆解成更小命題的陳述，因為它沒有使用任何邏輯運算子。例如「`x₁ ≤ 50`」本身就是一句完整、不可再分的話。
- **Compound（compound proposition）**：由邏輯運算子（NOT、AND、OR、IF...THEN、IF AND ONLY IF、EITHER...OR）把一個或多個 simple proposition 連接起來的陳述。例如「如果 `x₁ > 10` 則 `x₃ ≤ 5`」就是一個 compound proposition。

以 simple proposition 陳述的規格，構成了絕大多數最佳化問題裡的 constraint；它們雖然形式簡單，卻仍然可以依「意義」再分成五種類型，這是本頁接下來的主軸（Sects. 6.3–6.7）。以 compound proposition 陳述的規格，則需要一套系統化的轉換方法才能變成線性限制式——這正是 [[logical-specifications-guide]] 要處理的問題。

Simple proposition 依語意分類，作者列出五種：

- **Quantitative specification of selection（選擇的數量規格）**：對一組二元選擇變數的總和設定上下界。
- **Capacity specifications（容量規格）**：以資源的可用容量做限制。
- **Supply of a demand（需求的供給）**：容量規格的鏡像，確保供給滿足需求。
- **Bound imposition specifications（界限施加規格）**：直接對變數或其函數設定最大/最小值，且不具備容量或需求的語意。
- **Allocation, balance, or equilibrium specifications（分配、平衡或均衡規格）**：對變數施加精確賦值，或要求變數（函數）之間的平衡。

作者也坦承這五類「不可避免地」會有重疊——某個規格常常同時符合一種以上的類型描述。這不是分類法的缺陷，而是提醒讀者：分類的目的是幫助辨識與建模，不是給每條規格貼上唯一標籤。

## 規格作用在誰身上：individual 與 indeterminate

在動手把任何規格寫成數學式之前，第一件要釐清的事是：**這個規格是套用在哪個元素上？** 如果規格只針對某個特定的元素（例如「機器 3 的產能是 500」），它是 individual（個別的），直接代入該元素的資料即可。但如果規格用「每個」「任一個」「所有」這種不指名道姓的語氣描述，它就是 indeterminate（不確定、泛指的）——這意味著這條規則必須為集合中的**每一個**元素都掛上一份。書中特別提醒：即使用「所有」這個字面上聽起來像是「整體」的詞，數學上仍然要逐一套用到每個元素身上，而不是對整個集合只寫一條。

當規格只適用於集合中滿足某個條件的子集，作者引入符號「/」（讀作 "such that"，「使得」）來表示這種篩選子句，例如 `∀i/Cᵢ>10: ...` 表示「對所有滿足 `Cᵢ>10` 的 i」。這裡有一條容易踩到的陷阱，值得特別強調：**絕對不能在 such that 子句裡使用決策變數**。原因很直接——決策變數的值在求解前是未知的，如果拿它當作篩選條件，模型在建構的當下根本不知道這條規格要不要套用到某個 i 上。書中舉了一個明確的錯誤示範：

```
∀i/xᵢ>10: ...   ← 錯誤！
```

正確的做法是把「用變數當條件」這件事改寫成一個 **IF...THEN 條件命題**，讓變數出現在條件句而不是篩選子句裡：

```
∀i: IF xᵢ > 10 THEN αᵢ + βᵢ ≤ 1
```

這條規則之所以重要，是因為它把「規格作用在哪些元素上」和「規格的邏輯內容是什麼」這兩件事徹底切開——前者只能用資料屬性或索引篩選，後者才輪到條件邏輯出場，而條件邏輯的完整轉換技巧正是 [[logical-specifications-guide]] 的主題。

書中用一個貫穿整節、後面 6.10 節還會回頭重新分析的案例來示範這套原則——**Ham Distribution（Illustration 6.2 / 6.41）**：一家火腿配送公司設計了 20 條配送路線，服務 350 個客戶，用 10 輛車運送。每輛車有載運容量，每個客戶有需求量，每輛車必須選擇「一條」路線。案例中兩條規格特別值得玩味：

1. **「兩輛車不能選同一條路線」**：問「哪兩輛車」？答案是不確定的——必須考慮十輛車裡任兩輛的所有組合；問「哪條路線」？同樣不確定，必須考慮全部路線。於是規格要對「每一對車輛、每一條路線」都套用，用邏輯命題寫成 `∀k,k',i: NOT(α_ik=1 AND α_ik'=1)`，但也可以等價地改寫成一條更精簡的算術式：「每條路線被選擇的車輛數最多為 1」，也就是 `∀i: Σₖ α_ik ≤ 1`。
2. **「如果一輛車送給某客戶超過 50 個火腿，就不能再送給其他客戶」**：這裡「一輛車」「一個客戶」「其他客戶」全部都是不確定的，规格必須對每個 (j, j', k) 組合展開；一個等價但更簡潔的寫法是直接對「其他客戶的總量」設限：`∀j,k: IF x_kj > 50 THEN Σ_{j'≠j} x_kj' = 0`。

這兩個例子共同傳達一個實務教訓：同一條規格常常有不只一種數學表達方式，選擇「聚合」的寫法（用求和取代枚舉全部組合）往往能大幅減少限制式的數量，這對求解時間可能有直接幫助。

## 選擇的數量規格（Quantitative Specification of Selection）

當系統裡有邏輯決策變數（二元變數）代表「選或不選」時，經常會有一條規則規定「要選多少個」——這就是 quantitative specification of selection。它的通用格式是對一組二元變數的總和設定上界、下界或等式：

```
α₁ + α₂ + ... + αₙ ≈ Value        （≈ 代表 ≤、=、或 ≥）
```

這一節有一個貫穿全書的重要提醒：這類規格**經常不會被明講**。系統描述裡很少會有人特地寫「你只能選一台機器」，因為對人類來說這太顯而易見了；但對一個線性規劃模型而言，如果沒有這條限制式，模型完全可能同時選十台機器。因此建模者必須主動去「補」這條隱含的規則，這也是為什麼 6.10 節會把「quantitative selection rules」列為系統中最容易被漏掉的隱含規格之一。

書中用一系列 illustration 展示這個規格在不同集合結構下的樣貌：

- **單一集合的選擇**（Illustration 6.3）：一組機器 `i=1...n`，規則可以是「至少選一台」（`Σαᵢ ≥ 1`）或「恰好選三台」（`Σαᵢ = 3`）。
- **兩個集合的配對選擇**（Illustration 6.4）：operator 分派到 machine，一邊的規則可能是「每台機器最多分派兩位 operator」（`∀i: Σⱼ αᵢⱼ ≤ 2`），另一邊則是「每位 operator 只能分派一台機器」（`∀j: Σᵢ αᵢⱼ = 1`）——同一個決策活動，兩個方向的選擇規則可能完全不對稱。
- **集合對自身的選擇**（Illustration 6.5）：當元素被拿來跟同一集合裡的另一個元素配對時（例如「每個元素跟自己集合裡另一個不同的元素配對」），除了選擇規則之外，還可能出現一種特殊的**對稱性約束**：因為 i 跟 j 的配對關係是雙向對等的，`αᵢⱼ = αⱼᵢ` 也必須成立。
- **兩個集合共享同一規則**（Illustration 6.6）：如果一群個體被拆成兩個因資料不同而分開建模的子集，但兩者其實共用同一條邏輯決策活動與選擇規則，這條規則必須把兩邊的變數加總在同一條不等式裡（例如「一個個體最多只能被分到一個群組」需要同時計入 `α` 與 `β` 兩組變數）。

## 容量規格（Capacity Specifications）

容量規格處理的是「資源」的語意——當系統裡某個元素具備容量或可用性屬性（不論是元素本身固有的，還是與某個可測量元素共享的），就會產生容量規格。它的通用格式是：

```
容量消耗 或 需求容量 ≤ 容量貢獻
```

書中進一步說明，消耗與貢獻兩邊都可能是「固定」或「變動」的，而且必須用同一單位表示，於是產生三種最常見的組合（Table 6.2）：

| Case | 格式 | 表達式 |
| --- | --- | --- |
| 1 | 變動消耗 ≤ 固定貢獻 | `c₁x₁+c₂x₂+...+cₙxₙ ≤ K` |
| 2 | 變動消耗 ≤ 固定＋變動貢獻 | `c₁x₁+...+cₙxₙ ≤ K + a₁y₁+...+aₘyₘ` |
| 3 | 固定需求 ≤ 變動貢獻 | `E ≤ a₁y₁+...+aₘyₘ` |

**Case 1** 是最經典的形式：一組活動 `x₁,...,xₙ` 消耗某項資源，每單位活動消耗 `cᵢ`，資源上限是固定的 `K`。書中用**奶油生產（Illustration 6.7）**示範最典型的情況——兩台機器（打發機、殺菌機）各自有使用時間上限，兩種奶油產品各自消耗不同的機器時間，於是每台機器各生成一條 `Σⱼ TMᵢⱼxⱼ ≤ Tᵢ` 的限制式。值得注意的是**倉儲管理（Illustration 6.8）**這個例子：容量消耗不一定要來自「連續量的活動」，邏輯決策活動（是否把物品 i 放進架子 j，`αᵢⱼ`）一樣可以扮演消耗者的角色，只是消耗量變成「物品重量 × 是否放置」的乘積形式 `Σᵢ pᵢαᵢⱼ ≤ PEⱼ`。

**Case 2** 較少見，但一樣重要：消耗方是變動的，貢獻方除了固定額度外，還可以透過額外活動來「增加」。**藥丸生產（Illustration 6.9）**示範這種彈性：600 公斤藥粉是固定容量，但可以額外花錢買更多藥粉（`z`），於是容量限制式變成 `Σcᵢxᵢ ≤ E + z`——一條容量限制式裡同時出現固定項與一個變動的貢獻項。

**Case 3** 則反過來，是固定的需求配上變動的貢獻——這種情況常見於「有個元素需要被滿足的容量，而提供容量的元素是可以被選擇、被組合的」場景。**婚宴會場（Illustration 6.10）**是很好的示範：150 位賓客的座位需求是固定的，14 張 8 人桌與 11 張 12 人桌則提供變動組合的座位貢獻，限制式寫成 `150 ≤ 8x₁ + 12x₂`，同時因為桌子的可用數量也有限，還要另外補上 `∀i: xᵢ ≤ Nᵢ` 這條與容量規格語意不同（屬於 bound imposition）的限制式。

書中收尾用**容器問題（Illustration 6.11）**做了一個特別有教學價值的對比：同一個「用最低成本的容器裝下 Q 公升液體」問題，可以用兩種版本建模。**Version 1（by capacity consumption）** 把液體當作可測量元素，直接測量裝進每個容器的液體量 `xᵢ`，於是有消耗限制式 `xᵢ ≤ Kᵢ`；但因為目標函數要「選容器」而非「裝多少」，還必須另外定義一個邏輯計算「是否選了這個容器」（`αᵢ=1 IFF xᵢ>0`），並把它轉成限制式 `xᵢ ≤ Kᵢαᵢ`。**Version 2（by capacity contribution）** 則乾脆放棄測量液體怎麼分配到哪個容器，只做「選容器」的邏輯決策，容量規格直接寫成 `Q ≤ Σ Kᵢαᵢ`。作者接著用代數證明這兩個版本其實完全等價——Version 2 的限制式可以由 Version 1 的兩條限制式相加後代換推得。這個例子傳達的建模心法是：**當你只在乎「有沒有被選中」而不在乎「內部怎麼分配」時，往往可以跳過測量的中間變數，直接用容量貢獻的角度建模，得到一個更精簡的版本。**

## 需求的供給（Supply of a Demand）

供給規格是容量規格的鏡像：容量規格講的是「消耗不能超過供給」，供給規格講的則是「供給必須滿足需求」。通用格式：

```
供給 ≥（或 =）需求
```

供給被視為變動量，需求則固定或變動都有可能，但最常見的情況是需求固定。這一節的重點在於**何時可以用 `≥`、何時只能用 `=`**——這個判斷牽涉到兩個因素：系統裡是否有成本（如果供給過剩沒有壞處，用 `≥` 才合理），以及供給方每單位貢獻是否恰好等於 1（如果單位貢獻不是 1，用等式反而可能把可行解排除掉）。書中給出的判斷規則是：

- 如果供給涉及成本，或單位貢獻不全部等於 1，用 `≥` 才是正確的。
- 只有當所有單位貢獻都恰好等於 1 時，用 `=` 才安全。

**跟供應商買貨（Illustration 6.12）**先示範最單純的情形：需要恰好 1000 單位商品，兩個供應商都按單位計價（每單位貢獻皆為 1），這時 `x₁+x₂≥1000` 與 `x₁+x₂=1000` 兩種寫法都對，因為購買本身有成本，求解自然不會多買。但當題目修改為「供應商 2 不接受零售，只接受一批 8 單位、售價 22 元的批量」（單位貢獻變成 8），問題就出現了：如果堅持寫成等式 `x + 8y = 1000`，1000 不是 8 的倍數時模型會直接無解，即使實際上供給 1000 以上一樣可以接受；正確寫法必須是 `x + 8y ≥ 1000`。這個對比清楚示範了「單位貢獻不是 1」時，用等式是一個真實存在的建模陷阱。

## 界限施加規格（Bound Imposition Specifications）

界限施加規格是系統裡最容易辨認的一種——它直接對某個可測量活動或變數函數施加最大值或最小值，且**不承載容量消耗或需求供給的語意**（雖然技術上容量規格與供給規格也可以看成 bound 的特例，作者仍選擇把它們獨立分類，因為語意不同）。這一類分成：

- Upper bound（施加最大值）
- Lower bound（施加最小值）

書中用**供應商採購（Illustration 6.13）**的三條規則示範最基本的形式：「不超過 50 單位」（`x₂≤50`）、「至少 10 單位」（`x₁≥10`）、以及「超過 20 單位」——這裡有個細節：`x₁>20` 因為求解上通常需要非嚴格不等式，會被轉寫成 `x₁≥21`（這個嚴格不等式的轉換技巧會在 [[logical-specifications-guide]] 裡有系統化的規則）。**操作員產量（Illustration 6.14）**則展示了 bound 不一定要對著一個固定數值，也可以是「一個變數（函數）相對於另一個變數」的下界——操作員 1 產量必須比操作員 2 至少多 1 公斤，寫成 `y₁ ≥ y₂ + 1`，其中 `y₁`、`y₂` 本身是輔助計算而非決策變數。

## 分配、平衡或均衡規格（Allocation, Balance, or Equilibrium Specifications）

這是本章分類體系裡結構最豐富的一類。它涵蓋兩種語意：

- 對某個整數或連續變數（或變數函數）做**精確賦值**。
- 變數（或變數函數）之間的**平衡或均衡**，包括輔助計算。

**買 10 單位／兩供應商合計 50 單位／總共買 500 單位／供應商 1 跟供應商 3 買一樣多**（Illustration 6.15）分別示範了賦值（`x₁=10`）、加總等式（`x₁+x₂=50`）、聚合等式（`Σxᵢ=500`）、以及變數間相等（`x₁=x₃`）四種樣貌。作者也提醒，這類規格容易讓「決策變數」與「輔助計算」的界線變得模糊——因為給定值之後，一個變數的角色可以在兩者之間自由詮釋，但系統本身的結構並不會因此改變。

這一節真正有分量的部分，是把 **flow balance（流量平衡）** 這個概念系統性地跟 **directed graph（有向圖）** 綁在一起。當系統裡有一個可測量元素透過「節點（node）與弧（arc）構成的圖 G(N, A)」流動時，flow balance 就是這種結構下最自然的均衡規格。作者特別強調有向圖跟無向圖意義完全不同：無向圖的邊表示元素之間某種「關聯」或「連結」的語意，而有向圖的節點才是系統的元素，弧則是讓某個「流」在節點之間流通的通道。當存在流動時，流本身就是系統裡的一個活動，必須被節點注入（injection）圖中，也必須被節點從圖中抽出（demand）。

流量平衡的通用格式非常直觀——**每個節點的流入等於流出**：

```
∀i: Σ_{k/NDᵢₖ=1} xₖ + Iᵢ = Σ_{k/NOᵢₖ=1} xₖ + Dᵢ
```

其中 `xₖ` 是流經弧 k 的流量，`Iᵢ` 是節點 i 注入的固定流量，`Dᵢ` 是節點 i 需求（抽出）的固定流量。書中把用到這個技巧的場景分成兩種：

### Explicit case（系統本身就是圖問題）

這是最直觀的情況：問題本身就是一個要在有向圖上求解的最佳化問題，例如最短路徑或最小生成樹。

- **最短路徑問題（Illustration 6.16，Dijkstra 1959）**：從來源節點到目的節點求最低成本路徑。這裡有一個細節值得留意——雖然實務上流量常被理解為「離散」的一單位，但由於係數矩陣的 unimodularity（單模性）性質，把流量宣告為連續變數，最佳解依然會自動落在整數上，不需要額外強制整數性。整個問題只需要 flow balance 這一條規格加上目標函數（`Min Σcₖxₖ`）就足夠，因為 flow balance 本身已經同時保證了流的守恆與路徑的連續性。
- **最小生成樹問題（Illustration 6.17，MST）**：這裡示範了一個很漂亮的建模轉換技巧——原問題是無向圖，作者把每條邊拆成兩條方向相反的弧，指定一個 root node 注入 `n-1` 單位流量（`n` 是節點數），其餘每個節點各需求 1 單位，藉此把「找一棵連通所有節點、成本最小的樹」轉換成一個有向圖上的流量平衡問題。目標函數則需要額外定義一個二元邏輯計算「這條弧是否有流通過」，因為生成樹的成本只跟「哪些弧被使用」有關，跟流過的具體數量無關。

### Implicit case（借用圖的概念來表達平衡，即使系統本身不是圖）

這是作者認為**更有意思、應用也更廣**的情境。系統的描述裡並沒有明講一個圖，但只要滿足一個條件——存在一個可測量元素（individual 或 collective），且有其他非可測量的個別元素參與這個可測量元素的活動——就可以建構一張隱含的圖來釐清平衡關係。如果系統裡還有**時間期間（time periods）** 作為元素參與，這個技巧會更有價值，因為多期存貨與流動的平衡關係在純文字描述裡很容易被搞混，畫成圖之後反而一目了然。

建構這張隱含圖的程序是：

- **Nodes**：每個時期裡每個參與流動的個別元素各自是一個節點（時間元素本身不作為節點，而是決定「有幾組節點」）。節點若有已知的注入或需求值，就標上負號上標（injection, `⁻`）或正號上標（demand, `⁺`）；如果注入或需求的具體數量還沒確定（本身是決策活動或輔助計算的結果），則不需要事先標出數值。
- **Arcs**：代表可測量元素在節點之間的移動，包含跨期儲存——因為節點本身不能「儲存」單位，如果某些單位沒有被任何活動消耗掉，必須透過一條弧把它們送到下一期「代表同一個個別元素」的節點，藉此讓存貨的概念也能被平衡方程式自然涵蓋。

書中用三個層層遞進的例子具體示範：

1. **運輸問題（Illustration 6.18，Öztürk et al. 2015）**：沒有時間維度，`m` 個倉庫對 `n` 個客戶供貨。倉庫節點注入不確定量的流（`yᵢ`，本身是輔助計算），客戶節點需求固定量 `Dⱼ`，弧上的決策變數 `xᵢⱼ` 就是運輸問題本身要求解的量。三條平衡／規格式子分別對應：倉庫端的流量注入定義（`yᵢ=Σⱼxᵢⱼ`）、客戶端的需求供給規格（`Σᵢxᵢⱼ=Dⱼ`）、以及倉庫的容量消耗規格（`Σⱼxᵢⱼ≤Kᵢ`）——三種規格類型（平衡、供給、容量）同時出現在同一個圖裡。
2. **產品生產排程（Illustration 6.19）**：三個月的生產計畫，工廠、倉庫、市場三個節點各自重複三次（每期一組），倉庫節點之間用弧相連以承載跨期存貨。作者先畫出最原始的圖，再逐步簡化標籤，最後發現真正需要寫出平衡方程式的**只有倉庫節點**（因為工廠與市場節點各自只有單一進出弧，平衡關係已經被隱含滿足），得到一條非常乾淨的通式：`Iₜ₋₁ + xₜ = Dₜ + Iₜ`（`I₀=SI`，期初庫存）。這個例子示範了「畫圖之後可以簡化圖」的重要性——不是每個節點都需要單獨寫平衡式。
3. **餐飲服務／桌布租洗（Illustration 6.20）**：三天的宴會需要消毒桌布，桌布可以買、可以送快洗或慢洗、用完可能進洗衣籃等下次處理。這是全書中隱含圖最複雂的一個範例，牽涉市場、倉庫、宴會、洗衣籃、快洗、慢洗六種節點。作者進一步指出，如果把「乾淨桌布」跟「髒桌布」當成同一個元素的兩種狀態放進同一張圖，圖會過度糾纏；更好的做法是拆成**兩張獨立的圖**（乾淨桌布圖、髒桌布圖），中間用桌布的「送洗」與「送回」數量作為橋接——這正好呼應這一節不斷強調的建模原則：圖的設計不是唯一的，怎麼畫要看能不能讓平衡關係最清楚、最不容易搞混。

## 如何在系統描述裡找出隱含的規格（Sect. 6.10）

前面六節建立了規格的分類體系，但光有分類表還不足以指導實作——真正的挑戰在於：拿到一段系統描述之後，要怎麼把裡面所有的規格，不論明講還是暗示的，全部揪出來？這正是 6.10 節要處理的問題，也是這個分類體系「拿來用」的收尾。

書中把規格分成兩種來源：

- **Explicit specifications（明講的規格）**：文字裡直接使用了施加語氣的動詞（must、cannot、only 等）或明確寫出邏輯命題，這類規格通常容易辨認，只要留意這些關鍵詞就好。
- **Implicit specifications（隱含的規格）**：文字描述裡完全沒有提到，但從元素的性質與活動的結構可以推論出必然存在的規格。這類最容易被建模者遺漏，作者歸納出五種常見來源，逐一檢查是實務上最保險的做法：

| 隱含來源 | 對應規格類型 | 檢查重點 |
| --- | --- | --- |
| I1. 資料本身 | 容量、供給 | 元素若有容量、可用性或需求屬性，幾乎必然衍生容量消耗或供給規格 |
| I2. 數量選擇規則 | 選擇規格（[[specification-types|Sect. 6.3]]） | 邏輯決策活動涉及的每組集合，是否有隱含的「選幾個」規則 |
| I3. 活動間的邏輯條件 | 邏輯命題 | 兩個決策活動之間是否有一方成立、另一方才有意義的隱含關係 |
| I4. 離散可測量活動的界限 | 界限施加 | 離散量測活動是否有沒被明講的上界（例如一個地點最多只能蓋一座設施） |
| I5. 流量平衡 | 分配／平衡（Sect. 6.7） | 系統若涉及時間期或可測量元素在多個活動間移動，是否隱含存貨或流動平衡 |

書中用三個例子完整走過這套檢查清單：

- **物件分派到位置（Illustration 6.40）**：描述完全沒有明講任何規格，全部要靠隱含分析找出——I1 每個位置有最大承重（容量消耗）、I2 每個物件必須恰好佔一個位置（隱含選擇規則，位置端則沒有規則）、I3/I4/I5 皆不存在。
- **Ham Distribution 重新分析（Illustration 6.41）**：回到本頁一開始的火腿配送案例，這次示範**明講規格如何跟隱含規格並存**。「每個客戶的需求必須被滿足」是明講的供給規格；但「每輛送貨車必須選擇一條路線」這句話字面上像是純粹的選擇規則（I2），細讀之後其實還藏著一條 I3——「每輛送貨的車」這個措辭本身暗示了「車輛與路線之間有一個邏輯先決條件」：唯有被指派了路線，車輛才能配送。這條隱含的邏輯命題（`IF x_kj>0 THEN 該車被指派的路線恰好是經過客戶 j 的那一條`）如果沒被抓出來，模型可能允許車輛在沒有路線的情況下配送火腿。
- **超市配送中心選址（Illustration 6.42）**：明講規格（E1–E4，含一條邏輯命題「同時在地點 3、5 設點就不能在地點 6 設點」）與隱含規格（I1–I5）在這個例子裡被完整並列示範，很適合當作這套五項檢查清單的操作範本。
