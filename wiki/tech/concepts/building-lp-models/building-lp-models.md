## 線性為什麼值得這麼重視

[[mathematical-programming-overview]] 已經介紹過 LP、NLP、IP 這三種模型的基本輪廓,但還沒有回答一個更根本的問題:為什麼線性規劃在數學規劃裡佔據這麼核心的位置?答案不在於線性模型「比較貼近現實」——事實上,大多數真實世界的關係都帶有一定程度的非線性。答案在於求解的難易度上有著本質性的落差,而這個落差大到值得在建模階段就認真考慮「能不能、該不該用線性去逼近」。

LP 模型要求目標函數與限制式都必須是線性運算式,這是一條硬性的界線:凡是出現 $x_1^3$、$e^{x_1}$ 或 $x_1x_2$ 這類項次,就已經跨出了 LP 的範圍。對很多實務問題而言,這是相當大的限制,足以排除 LP 的直接使用。但即使如此,LP 之所以在應用上獲得遠超過其他模型類型的關注,原因是它遠比非線性模型容易求解——理解這一點最直接的方式,是看一個雙變數的例子,因為兩個變數的模型可以直接畫在平面上。

考慮以下模型:

$$\text{Maximize} \quad 3x_1+2x_2$$
$$\text{subject to} \quad x_1+x_2 \le 4,\quad 2x_1+x_2\le 5,\quad -x_1+4x_2\ge 2,\quad x_1,x_2\ge 0.$$

把 $x_1,x_2$ 當作平面上的座標,三條限制式加上非負限制圈出一塊凸多邊形的可行域,而目標函數 $3x_1+2x_2$ 的每一個等值都對應一條斜率固定的直線。要讓這條直線代表的值愈來愈大,直線必須沿著法向量方向平移,而平移到不能再平移、仍與可行域相交的那一刻,直線幾乎必然剛好通過可行域的一個「頂點」(vertex)。這不是這個例子的巧合,而是凸多邊形(以及更高維度的凸多面體)的一般性質:只要目標函數的等值線不恰好平行於可行域的某一條邊,最佳解就必然落在頂點上;就算真的平行,例如把目標函數換成 $4x_1+2x_2$,也只會出現「兩個相鄰頂點之間的整條邊都是最佳解」這種 alternative solutions 的狀況([[interpreting-lp-solutions]] 會再深入討論),而不會出現最佳解落在可行域內部的情形。這個性質可以推廣到更多變數的模型(此時可行域是更高維度的多面體),而正是這個「最佳解必然落在頂點上」的事實,讓 LP 模型遠比非線性模型容易求解——simplex algorithm 之所以有效率,就是因為它只需要在數量有限的頂點解之間搜尋,而不必去檢查整個(通常是無窮多點的)可行域。

這個性質在非線性模型裡多半不成立。如果目標函數帶有非線性項,二維情況下目標函數的等值線不再是直線;如果限制式帶有非線性項,可行域的邊界也不再是直線段。在這樣的情況下,最佳解未必落在可行域的頂點上,甚至可能落在可行域內部——而一旦找到一個解,也很難確定它是全域最佳解而不是眾多 local optima 之一。這些議題會在 [[nonlinear-and-separable-programming]] 詳細討論。這裡想指出的重點很單純:線性性質正是讓數學規劃模型好解的關鍵原因。

不過,這不代表 LP 模型永遠只是對非線性現實的一種妥協性近似。有很多實務情境裡,線性規劃模型本身就是完全站得住腳的正確表示方式,而不是退而求其次的簡化版。真正該提防的,反而是反過來的偏誤——因為 LP 遠比非線性模型好解,建模者可能會被這個誘因牽著走,把一個其實不該用線性去表示的情境硬套進 LP 的框架裡。這句提醒值得記在心裡,因為接下來整章要討論的目標函數與限制式分類,都是在假設「線性表示是合理的」這個前提下進行的。

## 目標函數的分類

同一組限制式,搭配不同的目標函數,不見得會得到不同的最佳解。極端情況下,限制式本身就已經把可行域壓縮到只剩一個點——例如 $x_1+x_2\le 2$、$x_1\ge 1$、$x_2\ge 1$ 這三條限制式,無論目標函數是什麼,都只能得到 $x_1=x_2=1$ 這個唯一解。這種情況在複雜模型裡不容易一眼看出,如果嘗試了幾個不同的目標函數卻總是得到相同的最佳解,這其實是一個值得深挖的警訊:它通常意味著對這個系統有了更深一層的理解——而如果這個理解是真的,也就代表這個情境根本不需要線性規劃了。

在真正需要選擇目標函數的情境裡,一個組織可能提出的候選目標五花八門:最大化利潤、最小化成本、最大化效用、最大化營業額、最大化投資報酬率、最大化淨現值、最大化或最小化員工人數、最小化冗員、最大化顧客滿意度、最大化存活機率、最大化營運計畫的穩健度……這份清單還可以繼續列下去。很多時候會同時有好幾個目標並存,而且彼此之間可能互相衝突;也有些時候,組織其實根本沒有想清楚要最佳化什麼。Williams 在這裡的立場很明確:數學規劃在單一目標、多重且衝突的目標、乃至於完全沒有明確最佳化目標這三種情境下都可能派得上用場——差別只在於用法不同。以下依序介紹五種目標函數的類型。

### 單一目標:利潤與成本

大多數實務上的數學規劃模型,目標不是最大化利潤就是最小化成本,但這兩者都藏著一個容易犯錯的細節。目標函數裡的「利潤」,精確地說應該是 contribution to profit(利潤貢獻),而不是會計意義上的淨利;同樣地,成本極小化模型裡的成本,指的也只是 variable cost(變動成本)。理由很直接:假設每單位產品的成本是 $C$,只有當 $C$ 是 marginal cost(邊際成本)時,生產 $x$ 單位的總成本才會恰好是 $Cx$;如果把行政或資本設備這類 fixed cost(固定成本)也一併加進去,模型就不成立了——除非刻意把模型延伸成整數規劃,讓模型自己決定要不要產生這筆固定成本(例如「完全不生產就不會發生這筆固定成本,只要生產任何數量就會發生」這種邏輯,只有 IP 才能表達)。書裡特別提醒,一個常見的錯誤,是在計算利潤係數時用 average cost(平均成本)而不是邊際成本;同理,如果要從收入扣掉成本來算利潤,正確的做法也是只扣掉變動成本,所以「利潤貢獻」其實比「利潤」更貼切地描述目標函數真正在算的東西。

成本極小化與利潤極大化這兩種建模方式,反映了兩種不同的野心。成本極小化模型通常假設有一組已知、固定的需求量 $D_i$,模型要做的只是用最低的成本滿足這些需求,對應的限制式形如 $\sum_j x_{ij}=D_i$(對每個 $i$)。這裡有一個容易踩到的陷阱:如果不小心漏掉了這類「必須滿足需求」的限制式,成本極小化的最佳解很可能就是「什麼都不生產」——因為不生產永遠是成本最低的選項。利潤極大化模型則更進一步:與其把需求量 $D_i$ 當作固定常數,不如把它們變成模型自己要決定的變數 $d_i$,原本的等式限制就變成 $\sum_j x_{ij}-d_i=0$。這樣一來,模型能自行決定每項產品的最適生產水準,但代價是必須為每個 $d_i$ 提供對應的單位利潤貢獻係數 $P_i$,讓模型能夠權衡「多生產帶來的利潤」與「多生產耗用的成本」。這已經比單純的成本極小化模型做了更多事,實務上常見的做法是:先從一個容易被接受的成本極小化模型開始,等它被組織採用之後,再逐步擴充成利潤極大化模型。這裡還有一個技術上的但書:如果單位利潤貢獻 $P_i$ 本身又是產量 $d_i$ 的函數(例如售價隨數量增加而下降),目標函數裡就會出現 $P_i(d_i)\cdot d_i$ 這種非線性項,模型就不再是 LP 了(McDonald et al. (1974) 在一個醫療資源分配模型裡就遇到這種情形)。

當模型涉及跨期間的決策時,還會冒出另一層複雜度:未來的利潤或成本該怎麼跟現在的利潤或成本放在同一個目標函數裡比較?標準做法是用某個利率把未來的金額折現(discount),對應到未來期間的目標函數係數就要相應調低。這種模型稱為 multiperiod 或 dynamic 模型,會在 [[structured-lp-models]] 詳細討論。Part II 裡的 ECONOMIC PLANNING 案例正是這類問題的典型代表——模型必須在「現在少賺一點、把錢投資到新設備」與「維持現在的獲利水準」之間做取捨,而不同的成長路徑各自對應著不同的目標函數設計。

### 多重與衝突目標

一個數學規劃模型在定義上只能有一個目標函數,但這並不代表多目標問題就無法用數學規劃處理——只是需要一些額外的建模手法。第一種做法最直觀:把同一個模型,分別用每個候選目標各解一次,再比較這些解之間的差異。這種比較常常能提示出一個令人滿意的折衷解,或者至少指出還需要進一步調查的方向。Part II 的 MANPOWER PLANNING 案例就是很好的例子:成本與冗員這兩個目標可以分別拿來求解、互相比較。這裡有個計算上的小技巧可以省時間:如果把某一次求解得到的解,當作下一次換目標函數求解時的起始解,通常能大幅縮短計算時間(這正好呼應 [[mathematical-programming-overview]] 提到的 starting solution 功能)。

目標函數與限制式之間,其實常常可以互相轉換,這一點在很多模型裡都被嚴重低估。舉例來說,一個模型可能想追求某個社會性目標,但前提是成本不能超過某個上限;或者反過來,想在把「社會考量」當作一條限制式的前提下把成本壓到最低。把目標轉成限制式(或反過來)在技術上永遠是可行的,而一旦模型建好之後,把它反覆求解、每次微調那條限制式(或目標)的右手邊數值,就能一步步描繪出這個情境裡實際可行的操作選項全貌,這正是理解一個被建模情境的重要途徑。

另一種處理多目標的方法,是把所有目標函數取一個線性組合,合併成單一個複合目標去求解。這麼做勢必要替每個目標函數賦予相對的權重或效用(utility),而這些權重該怎麼訂,往往免不了帶有主觀判斷的成分——所以實務上常見的做法,是嘗試不同的權重組合,把得到的一系列解都攤開來,當作政策選項提供給決策者參考。這裡有一個漂亮的理論連結:當一個 LP 模型求解完畢,每一條限制式都會附帶一個 shadow price(見 [[interpreting-lp-solutions]])——如果把這些 shadow price 直接拿來當作複合目標裡對應限制式(如果它們被當作目標處理的話)的權重,會得到與原本相同的最佳解。這也說明了「把目標當限制式處理」跟「取線性組合當複合目標」這兩種方法,並不是彼此獨立、互不相干的兩條路。

當多個目標真正互相衝突時,不管採用上面哪一種做法都需要格外小心:把互相衝突的目標直接當作限制式硬性要求全部滿足,模型很可能就變成不可行(infeasible)。這時候需要把其中一些限制式放鬆,讓它們變成 goal(目標值),允許一定程度的超過或不足,而這個容許的偏離程度則由目標函數本身去決定——這就是 goal programming 的核心想法,細節留到下面「衝突限制與 goal programming」一節處理。整體而言,面對多重目標,並沒有一種放諸四海皆準的標準做法;實務上可能需要混用上述幾種方法。當一個情境裡的多個目標本來就沒有清楚、公認的權重時,不存在「一刀切」的解法反而是件健康的事,勝過假裝有一個唯一正確的權重組合、草率地得出單一解。

### Minimax 與 maximin 目標

有一類目標函數形如

$$\text{Minimize}\left(\max_i\sum_j a_{ij}x_j\right)\quad\text{subject to conventional linear constraints,}$$

也就是先在一組線性運算式裡取最大值,再把這個最大值最小化。雖然「取最大值」這個操作本身不是線性的,這種目標卻可以完整地轉換成一個常規的 LP:引入一個新變數 $z$ 代表這個目標值,模型改寫成

$$\text{Minimize}\ z \quad\text{subject to}\quad \sum_j a_{ij}x_j - z\le 0 \ \text{for all } i,$$

這組新增的限制式保證了 $z$ 必須大於或等於每一個 $\sum_j a_{ij}x_j$,而最小化 $z$ 的效果,就是把 $z$ 壓低到剛好等於這些運算式裡的最大值——這正是原始 minimax 目標想要的效果。maximin 目標(先取最小值再最大化)可以用完全類似的方式處理。但要特別留意的是,maximax(或 minimin)目標——也就是先取最大值(或最小值)再對外層做同方向的最佳化——**不能**用 LP 處理,必須訴諸整數規劃(見 [[integer-programming-fundamentals]])。Minimax 目標的一個特殊應用會出現在 goal programming 裡(見下面「衝突限制與 goal programming」一節),另外也常見於把零和賽局(zero-sum game)表示成線性規劃問題的場合。

### 比例型目標

還有一類目標函數的形式是兩個線性運算式的比值:

$$\text{Maximize (or Minimize)}\quad \frac{\sum_j a_jx_j}{\sum_j b_jx_j}.$$

單看這個式子,它顯然是非線性的(分子分母都含變數,整體是一個有理函數),但相當出人意料的是,這種比例型目標經過適當的變數代換之後,可以完整轉換成一個 LP 模型。轉換的做法分三步:第一步,用一個新變數 $t$ 代表 $1/\sum_j b_jx_j$;第二步,用新變數 $w_j$ 代表乘積 $x_jt$,這樣目標函數就變成線性的 $\sum_j a_jw_j$;第三步,為了讓 $t$ 真的等於 $1/\sum_j b_jx_j$,必須額外加入一條限制式 $\sum_j b_jw_j=1$。模型裡原本形如 $\sum_j d_jx_j\lessgtr e$ 的限制式,也要跟著做對應的代換,變成 $\sum_j d_jw_j-et\lessgtr 0$。這個轉換能不能用,取決於一個關鍵前提:分母 $\sum_j b_jx_j$ 在整個可行域裡必須恆為同號且不為零(如果分母恆為負,則所有不等式的方向都要反過來)。求解出轉換後的模型之後,只要把 $w_j$ 除以 $t$,就能還原出原本的 $x_j$。

這種比例型目標常見於某些沒有明確利潤指標可用的組織,想替自己設計一套「績效衡量」(performance measure)的場合:目標被表示成一組加權 inputs 與加權 outputs 的比值,而每個受評估的組織都被允許自行挑選這組權重,以求最大化自己的績效比值(當然仍受限於某些共同的限制式)。這個主題如今已經發展成一個獨立的研究領域,稱為 data envelopment analysis(DEA),Part II 的 EFFICIENCY ANALYSIS 案例就是一個具體示範。

### 不存在與無法最佳化的目標

「無法最佳化的目標」這個講法乍聽有點自相矛盾,但這裡的「目標」是在非技術性的日常意義上使用的——很多實務情境裡,根本沒有任何想要最佳化的東西。就算一個組織確實抱持某種目標(例如「生存下去」),也不見得能替這個目標賦予任何清楚的「最佳化」意義。數學規劃常常被過早地打上「只關心最佳化」的標籤而被草率否定,但這其實是搞錯了重點:如果一個問題本身就涉及大量限制式,光是找到一個滿足所有限制式的解(即 feasible solution),就已經可能是相當不容易的工作——這對某些整數規劃模型尤其成立(那裡的限制式集合往往極其複雜),但偶爾對一般的線性規劃模型也一樣成立。

正因如此,就算一個情境根本沒有真正想最佳化的量,刻意替模型加上一個「拼湊出來的」(contrived)目標函數,依然有它的價值:這麼做能讓整個問題變成一個定義良好的數學規劃模型,而不只是一堆待滿足的限制式。透過對這個(或一系列)目標函數做最佳化,可以得到一些「極端」的解——這些極端解的實務意義,恰恰在於檢驗模型本身夠不夠準確:如果任何一個極端解,從實務的角度看是不可接受的,那麼就代表模型本身有問題,應該被修正。用這種方式驗證模型的價值,往往不亞於——甚至常常超過——直接拿模型的解去輔助決策的價值。這個看法,呼應了 [[mathematical-programming-overview]] 開頭談到的態度:模型的解答終究只是決策輔助之一,值得不斷質疑、拿去檢驗,而不是照單全收的答案。

## 限制式的分類

目標函數之外,限制式是 LP 模型的另一半。書裡把實務上最常見的限制式類型歸納成十一種,下表先給一個速查總覽,細節在後面逐一展開。

| 類型 | 一句話說明 |
|---|---|
| 產能限制 | 處理能力、人力等資源的供給上限 |
| 原料限制 | 生產活動用到的原物料供給上限 |
| 市場限制 | 產品可銷售量的上下限,或指定的確切需求 |
| 物料平衡(連續性)限制 | 流入的總量必須等於流出的總量 |
| 品質限制 | 混摻/調配後的成品品質須落在允許區間 |
| 硬限制與軟限制 | 絕對不能違反,對比可以付出代價違反 |
| Chance constraint | 只需以一定機率滿足的限制式 |
| 衝突限制(goal programming) | 無法同時滿足時,允許偏離並最小化偏離量 |
| 冗餘限制 | 拿掉也不影響最佳解的限制式 |
| 簡單界限與 GUB | 只涉及單一(或一組互斥)變數的界限,交給簡化的 simplex 處理 |
| 不尋常限制 | 邏輯性條件,通常要靠擴充成 IP 才能表達 |

### 產能限制

這類限制式的典型出現場合,就是 [[mathematical-programming-overview]] 提到的 product mix 範例:當生產活動要用到的資源(例如加工產能或人力)供給量有限時,這項供給與各項活動對它的耗用量之間的關係,就會產生一條產能限制。

### 原料限制

如果某些活動(例如生產某項產品)會消耗供給量有限的原物料,同樣會產生對應的限制式,形式上與產能限制非常相似,差別只在於「有限的資源」換成了原物料而不是加工產能或人力。

### 市場限制

如果一項產品的可銷售量有上限,即使其他限制式允許生產更多,實際能賣掉的數量還是受到市場限制,這種情況必須明確地建模進去,形式通常是 $x\le M$,其中 $x$ 是產量、$M$ 是市場容量上限。有時候也需要反過來設定「最低銷售限制」$x\ge L$,例如必須生產至少一定數量才能滿足某項既有的承諾;如果需求必須被精確滿足,這兩條不等式也可能改成等式限制。

### 物料平衡(連續性)限制

很多模型都需要表示「流進某個流程的總量,必須等於流出的總量」這件事——例如在調配(blending)問題裡,最終成品的重量必須恰好等於所有投入原料重量的加總。這類限制式的一般形式是

$$\sum_j x_j - \sum_k y_k = 0,$$

表示 $x_j$ 變數代表的總量(重量或體積)必須等於 $y_k$ 變數代表的總量。這種限制式看似簡單到不需要特別強調,實務上卻常常在建模時被無意間遺漏,而遺漏它就等於默許模型「憑空生產或消滅重量」,得到的解自然沒有實務意義。值得一提的是,並非所有物料平衡限制式的係數都必須是 1——如果某個製程過程本身會帶來重量或體積上的損耗或增益,對應的係數就要反映這個比例。

### 品質限制

品質限制通常出現在調配問題裡:當某些原料帶有可測量的品質指標(例如食品裡的營養成分含量、汽油的辛烷值、材料的強度),而成品的這些指標必須落在特定的允許區間內時,就會需要對應的限制式——這往往表現成一對方向相反的不等式,分別限定上界與下界。

### 硬限制與軟限制

一條形如 $\sum_j a_jx_j\le b$ 的限制式,字面上排除了任何讓左式超過 $b$ 的解,但在某些情況下,這種絕對排除並不寫實。舉例來說,如果這條限制式代表的是產能或原物料供給上限,實務上完全有可能在需要的時候,用比較高的價格額外購買產能或原料來突破這個上限——這時候原本的限制式就顯得太過剛硬。真正應該永遠不能違反的限制式,例如受限於某條管線截面積的技術性限制,才稱得上是 hard constraint(硬限制)。反過來,可以在付出某種代價之後被違反的限制式,則稱為 soft constraint(軟限制),而軟限制的建模方式,是把原本的不等式改寫成

$$\sum_j a_jx_j - u \le b,$$

並替新引入的變數 $u$ 在目標函數裡賦予一個適當的(對極小化問題為正、對極大化問題為負的)成本係數 $c$。這樣一來,如果模型判斷值得的話,$b$ 這個上限就能以每單位 $cu$ 的代價被擴增到 $b+u$——通常還會替 $u$ 設一個簡單的上界,避免這個擴增量無限增加。如果原本是 $\ge$ 限制式,可以用類似的方式引入一個 slack 變數達到同樣效果。如果原本是等式限制,則需要同時引入 slack 變數 $u$ 與 surplus 變數 $v$,寫成

$$\sum_j a_jx_j + u - v = b,$$

並在目標函數裡給 $u$、$v$ 適當的加權係數。最佳解中 $u$ 與 $v$ 必然有一個等於零——如果兩者都是正值,把兩者同時減去其中較小的那一個,一定能得到一個更好(或至少不會更差)的解,所以最佳解不可能讓兩者同時為正。另外還有一種看待軟限制的角度,是借用 fuzzy set 理論,把「違反的程度」對應成一種「隸屬度」(degree of membership);Dyson (1980) 證明了以 fuzzy set 理論表示的這類軟限制模型,其實都可以被改寫成帶有 minimax 目標的常規 LP 模型。

### Chance constraint

某些應用裡,我們希望某條限制式只需要以一定的機率被滿足即可——例如希望有 95% 的信心水準確保某條限制式成立。這種需求可以寫成

$$P\!\left[\sum_j a_jx_j\le b\right]\ge \beta,$$

其中 $\beta$ 是一個機率值。實務上,通常會希望更高的 $\beta$ 值對應到更高的成本,並把這一點反映進目標函數,但這樣一來模型會變得相當複雜。如果 $\beta$ 與成本之間並沒有已知的明確關係(這其實是很常見的情況),一個比較粗糙、但往往堪用的做法,是直接用一個 deterministic equivalent(確定性等價式)取代原本的機率式限制,寫成

$$\sum_j a_jx_j\le b',$$

其中 $b'$ 是一個比 $b$ 更大的數字,而且滿足這條確定性限制式,可以保證原本的 chance constraint 也一併被滿足。這個想法出自 Charnes and Cooper (1959)。

### 衝突限制與 goal programming

有時候一個問題裡的多條限制式,並不能同時被滿足——如果照常規做法把它們全部列為硬性限制,模型就會變成不可行。這種情況下,常見的做法是把目標改成「盡可能同時滿足所有限制式」,這正好呼應了前面「多重與衝突目標」一節裡提到、但延後到這裡處理的衝突目標問題。由此產生的模型類型稱為 goal programming(這個名稱由 Charnes and Cooper (1961b) 提出),但要注意的是,goal programming 模型本質上仍然只是一個常規的 LP 模型。

具體做法是把每一條原本的硬限制 $\sum_j a_{ij}x_j=b_i$(對每個 $i$),都當作一個「目標」(goal)——也就是希望盡量被滿足、但允許有落差的目標值,改寫成軟性版本

$$\sum_j a_{ij}x_j + u_i - v_i = b_i,$$

其中 $u_i$、$v_i$ 是代表正負偏離量的新變數。接下來要替「盡量滿足這些目標」訂出一個具體、可操作的目標函數,書裡提出兩種常見做法:第一種是把所有限制式的偏離量加總起來最小化(必要時可以給每條限制式不同的權重,反映它們的相對重要性)——Part II 的 MARKET SHARING 案例(雖然那其實是一個 IP 模型,但不影響這裡論證的邏輯)以及 CURVE FITTING 案例(這是一個貨真價實的 LP 應用)都示範了這種目標。第二種做法稍微複雜一點,但一樣可以維持在 LP 的範圍內:最小化「偏離量裡的最大值」,也就是所謂的 bottleneck problem。做法是引入一個額外變數 $z$ 代表最大偏離量,加上限制式 $z-u_i\ge 0$、$z-v_i\ge 0$(對每個 $i$),再把目標函數設為最小化 $z$——由於這幾條限制式的緣故,$z$ 的最佳值必然恰好等於所有 $u_i$、$v_i$ 裡的最大值,不多也不少。CURVE FITTING 與 MARKET SHARING 兩個案例同時示範了這種「最小化最大偏離」的用法。書裡也舉了一個放射治療的例子(Redpath and Wright (1981)):與其去最小化腫瘤各處輻射劑量的變異數(這需要用到二次規劃),不如改成最小化輻射劑量之間的最大差異,這樣一來,計算起來遠比二次規劃簡便的線性規劃就足以勝任。另外,Hooker and Williams (2012) 也示範了在一個整數規劃模型裡,如何把 minimax 目標所代表的「公平性」(equity)與另一個效益主義式(utilitarian)的目標結合在一起。

### 冗餘限制

如果一條限制式 $\sum_j a_jx_j\le b$ 在最佳解中恰好不是緊繃的(即左式嚴格小於 $b$),它對應的 shadow price 就會是零,這種限制式稱為 non-binding(非緊繃)。理論上,把一條非緊繃的限制式直接從模型裡拿掉,並不會影響最佳解,這樣的限制式就稱為 redundant constraint(冗餘限制)。即便如此,書裡列了幾個保留冗餘限制式的正當理由:第一,在真正求解模型之前,往往根本無法預先判斷哪些限制式會是冗餘的;第二,如果模型是要拿來反覆使用、資料會隨時間更新的,現在冗餘的限制式,未來換了一批新資料之後很可能就變成緊繃的,先保留下來可以省去日後重新建模的麻煩;第三,[[interpreting-lp-solutions]] 討論的 ranging(敏感度分析用的界限資訊),依賴的正是包含這些(可能冗餘的)限制式在內的完整模型。

這裡還有一個容易被忽略的細節:即使 $\sum_j a_jx_j$ 在最佳解裡恰好等於 $b$(也就是表面上「剛好卡到邊界」),這條限制式仍然可能是非緊繃的——只要拿掉這條限制式之後,基於其他理由,最佳解依然不會改變。判斷一條限制式是否真的非緊繃,要看它在最佳解裡的 shadow price 是否為零,而不是單純看左式是否等於右手邊的數值。對 $\ge$ 限制式,也有類似的對應結論。最後有一個對 IP 特別重要的但書:在整數規劃模型裡,並不能想當然爾地認為「$\sum_j a_jx_j$ 嚴格小於 $b$」就代表這條限制式是非緊繃、可以拿掉的——IP 模型裡的緊繃性判斷比 LP 更微妙,這一點會在 [[integer-programming-refinement]] 進一步說明。

### 簡單界限與 GUB

市場限制常常呈現 $x\le M$ 或 $x\ge L$ 這種只涉及單一變數的簡單形式。與其把它們當成一般的限制式列進模型,更有效率的做法,是透過修改過的 simplex algorithm,把它們當作變數的 simple bounds(簡單界限)直接處理——大多數商業套件都採用這種做法。

這個想法可以推廣成 generalized upper bounds(GUB,廣義上界):一組變數 $x_j$ 如果滿足 $\sum_j x_j = b$,就稱這組變數帶有 $b$ 這個 GUB(如果原本是不等式,加上 slack 變數即可化成等式;係數是否為 1 並不重要,透過縮放永遠可以化成這個形式)。GUB 真正關鍵的地方,在於這組變數必須構成 exclusive set(互斥集合)——也就是說,一個變數如果屬於某個 GUB 集合,就不能再屬於任何其他 GUB 集合。當一個模型裡存在大量這種 GUB 型限制式時,修改過的 simplex algorithm 一樣可以用類似處理簡單界限的方式,直接處理這些隱含的限制式,不需要把它們當作一般限制式的行列來對待。這種做法在大型模型裡能帶來相當可觀的計算效益——例如 [[lp-applications-and-networks]] 會介紹的 transportation problem(運輸問題),至少有一半的限制式都可以被歸類成 GUB 集合。要在一個大模型裡自動偵測出這類 GUB 結構,可以參考 Brearley et al. (1975) 描述的方法。

### 不尋常限制

前面幾類限制式都還能直接用線性規劃表示,但實務上偶爾會遇到一些「不尋常」的限制,乍看之下無法納入 LP 的框架。這時候,把模型擴充成整數規劃,往往就能把這類限制式表達出來。書裡舉的例子是這樣一句邏輯條件:「只有在生產產品 2、但不生產產品 3 也不生產產品 4 的前提下,才可以生產產品 1」——這種條件式的邏輯限制,單靠 LP 完全無法表示,但透過引入二元變數,IP 就能優雅地處理。這類邏輯條件與二元變數的完整處理方式,留待 [[integer-programming-fundamentals]] 詳細展開。

## 怎樣才算一個好模型

前面兩節分別講完了目標函數與限制式的分類,接下來要退一步,問一個更高層次的問題:建模者在動手建模的時候,應該追求哪些特質,才能算是一個「好」的模型?書裡歸納出三個目標——模型的**易懂**、**易於偵錯**與**易於求解**——並且坦白指出:這三者之間並非總是互相一致,有時候甚至彼此衝突。

### 易懂

要讓模型容易理解,一個常見的取捨發生在「精簡」與「顯式」之間。假設某個非負的量可以表示成另一個變數 $x$ 的函數 $f(x)$,一種做法是引入一個新變數 $y$,加上限制式

$$f(x) - y = 0,$$

讓 $y$ 明確代表這個量;另一種做法則是把 $f(x)$ 直接代入所有用得到它的地方,完全不引入 $y$,模型因此變得更精簡。精簡的模型往往更省求解時間,但代價是解讀最佳解時會遭遇更多困難與額外的計算——即使精簡的做法能省下一些求解時間,多數情況下,為了換取解讀上的方便,多花一點求解時間通常是值得的;如果模型另外搭配了報表產生工具(report writer)來自動解讀輸出,這種解讀困難可以被工具吸收掉,這時候精簡模型在計算效率上的優勢就重新變得有吸引力。除此之外,替變數與限制式取有意義的助憶名稱(mnemonic names),也能大幅降低解讀最佳解的難度——[[mathematical-programming-overview]] 提到的調配範例就示範了這種命名方式;Beale et al. (1974) 描述了一套系統化替模型變數與限制式命名的方法。

### 易於偵錯

這個目標與「易懂」緊密相關。模型裡的錯誤大致分成兩類:一類是純粹的 clerical error(謄寫錯誤,例如打錯字),另一類是 formulation error(建模邏輯本身有誤)。要避免第一類錯誤,即使模型規模很小,也值得使用 matrix generator 或建模語言來輸入,而不是手刻。第二類與第一類錯誤,常常都會導致模型求解後呈現 unbounded(無界)或 infeasible(不可行)的狀態,而這類異常狀態,往往可以透過 PRESOLVE 或 REDUCE 這類程序輕易地被揪出來。建模的過程本身,有時候也可以刻意朝著「方便日後偵錯」的方向去設計,這一點會在 [[interpreting-lp-solutions]] 具體示範。

### 易於求解

這個目標常常與「易懂」互相拉扯——如果在建模完成之後、真正送去求解之前先套用 PRESOLVE 或 REDUCE 之類的程序,反而應該避免一開始就把模型寫得太精簡,因為這類程序往往能大幅縮小模型的規模(Brearley et al. (1975) 描述了具體算法,Karwan et al. (1983) 則收錄了一系列偵測冗餘的方法);程序處理過的簡化模型拿去求解之後,再回頭產生出對應到原始模型的解。

書裡用一個具體的數值例子示範了怎麼從模型本身「看出」冗餘。考慮下面這個模型:

$$\text{Maximize}\quad 2x_1+3x_2-x_3-x_4$$
$$\text{subject to}\quad x_1+x_2+x_3-2x_4\le 4,\quad -x_1-x_2+x_3-x_4\le 1,\quad x_1+x_4\le 3,\quad x_1,x_2,x_3,x_4\ge 0.$$

因為這是一個極大化問題,而 $x_3$ 在目標函數裡的係數是負的,所以我們自然希望 $x_3$ 愈小愈好;檢視 $x_3$ 出現的兩條限制式,會發現它在兩條限制式裡的係數都是正的,而這兩條限制式又都是 $\le$ 型——也就是說,沒有任何限制式會反過來強迫 $x_3$ 必須取比較大的值。這代表 $x_3$ 可以一路降到它的下界 0,而不會讓任何限制式被違反,所以 $x_3$ 是一個 redundant variable(冗餘變數),可以直接從模型裡拿掉。把 $x_3$ 固定為 0 之後,再檢視第二條限制式,會發現它的左式(拿掉 $x_3$ 之後)變成 $-x_1-x_2-x_4$——所有係數都是負的,而所有變數又都非負,所以這個左式恆小於或等於 0,永遠不可能超過右手邊的 1,這代表第二條限制式本身也是冗餘的,同樣可以拿掉。像這樣先辨識出冗餘變數、再辨識出冗餘限制式的推理過程,對大型模型而言可能帶來相當可觀的規模縮減。infeasibility 與 unboundedness 這兩種異常狀態,同樣常常是被這類程序揪出來的,而且往往指向了建模上的錯誤。如果再進一步結合變數的簡單界限、並考慮這個模型的對偶(見 [[interpreting-lp-solutions]]),這個範例其實可以被化簡到完全消失——也就是說,光靠 PRESOLVE 就能把它徹底解完,不需要再送進 simplex algorithm。建模者不見得每次都需要親自動手做這種簡化,但一個模型「可以被這樣簡化」這件事本身,對它所代表的實務情境而言,往往帶有值得深思的意涵。除了偵測冗餘之外,善用問題本身的特殊結構(例如前面提到的 GUB)也能大幅縮短求解時間,而有些商業套件(見 Brearley, Mitra and Williams 的相關工作)甚至能自動偵測出這類結構。

### Modal formulation

在大型 LP 問題裡,如果一系列限制式只牽涉到少數幾個變數,還有另一種縮減限制式數量的手法,稱為 modal formulation:與其把這些限制式原封不動地保留在模型裡,不如直接考慮這幾個變數所構成的可行域本身。

書裡用一個小例子示範這個手法。假設 $x_A$、$x_B$ 是模型裡的兩個非負變數,只出現在以下三條限制式裡:

$$x_A+x_B\le 7,\quad 3x_A+x_B\le 15,\quad x_B\le 5.$$

這三條限制式圈出的可行域是一個多邊形,有五個頂點(對應五種「操作模式」的極端組合)。與其保留這三條限制式,可以改用五個新變數 $\lambda_0,\lambda_1,\lambda_2,\lambda_3,\lambda_4$ 分別代表這五個頂點的權重,只需要一條限制式

$$\lambda_0+\lambda_1+\lambda_2+\lambda_3+\lambda_4=1$$

就能完整表示原本三條限制式圈出的可行域。凡是模型裡其他用到 $x_A$、$x_B$ 的地方,都改用這些頂點的座標加權表示,例如 $x_A$ 換成 $2\lambda_2+4\lambda_3+5\lambda_4$、$x_B$ 換成 $5\lambda_1+5\lambda_2+3\lambda_3$——這裡每個 $\lambda$ 前面的係數,恰好就是對應頂點在 $x_A$-$x_B$ 平面上的座標。這樣一來,原本的三條限制式,就被壓縮成了一條,在變數與限制式數量都比較龐大的情境下,這種壓縮帶來的效益會相當可觀。石油工業裡的製程模型,經常出現這種 modal formulation 的應用場合;Part II 的 REFINERY OPTIMIZATION 案例示範了一種最簡單的情形——當一個製程只有單一種操作模式、輸入輸出比例固定時,與其用限制式去表示這組固定比例的輸入輸出關係,不如直接把這個製程的運作水準當作一個活動(activity)來建模,反而更簡單。至於輸入輸出關係更複雜、有多種模式的製程該怎麼一般化處理,Müller-Merbach (1987) 提出了一套完整的方法論。

### 度量單位

建模時容易被忽略、卻很實際的一點,是留意模型裡各項數量所用的度量單位。如果模型裡係數的量級差異過於懸殊,即使模型在邏輯上完全正確,也可能讓 LP 在數值上變得難解、甚至無法求解。舉例來說,如果目標函數裡的單位利潤係數動輒是幾百萬英鎊的量級,卻用「英鎊」當作利潤的計量單位,這顯然不明智;同樣地,如果產能限制式裡的數量級落在幾千噸,與其用「噸」作單位,不如直接用「千噸」。理想情況下,應該挑選度量單位,讓模型裡每個非零係數的量級都落在 0.1 到 10 之間——雖然實務上未必總能做到這麼理想。多數商業套件都內建自動 scaling(縮放)程序,會在求解前自動調整模型係數的量級,並在印出結果前把解自動還原成原本的單位,一定程度上緩解了這個問題。

## 建模語言的角色

前面四節談的都是「該怎麼想清楚一個 LP 模型」,最後這一節要處理另一個同樣重要、卻常常被低估的問題:一個想清楚的模型,該怎麼實際交給電腦去解?市面上有不少軟體工具是專門為此設計的,協助使用者 structure(組織)與 input(輸入)自己的問題,這類工具統稱為 matrix generator(MG,矩陣產生器);其中比較講究的一類,更適合被看作是專門為建模設計的高階程式語言,稱為 modelling language(建模語言)。書裡點出一個很值得記住的觀察:一個數學規劃模型能不能成功應用在實務上,真正的瓶頸往往已經不再是「怎麼算出解」,而是「使用者與電腦之間的介面」——把建模者從特定套件的具體要求裡解放出來,正是建模語言想解決的問題(Greenberg (1986) 是這方面一次企圖心很大的嘗試;Greenberg and Murphy (1992) 對各種建模系統做了完整的調查;Buchanan and McKinnon (1987) 與 Greenberg et al. (1987) 描述的系統則同時關注輸出介面,而不只是輸入介面)。

建模語言相對於手刻標準格式(例如 [[mathematical-programming-overview]] 提到的 MPS 格式)有四項具體的優點。第一,MPS 這類格式是按照電腦內部矩陣的欄位順序設計的,對使用者而言並不直覺,輸入起來既繁瑣又容易出錯,而且一點也不精簡(每兩個係數就要單獨寫一條資料陳述式)——建模語言提供的是使用者自然習慣的輸入格式,能一次解決這些問題。第二,自然的輸入格式同時也讓除錯與驗證模型變得容易得多,而模型的除錯驗證本來就是一項重要、有時候還相當耗時的工作。第三,模型往往需要定期重複使用,只做小幅修改,或者建好一次之後被實驗性地反覆調整資料——建模語言的一個重要特徵,是把「資料」和「結構」分離開來,這讓修改模型變得容易許多。第四,大型模型通常是由許多較小的模型組合、重複而成的(例如多個期間、多間工廠、多種產品的組合,見 [[structured-lp-models]]),這代表資料與結構裡會出現大量的重複——MPS 這類格式要求把每一筆重複的資料都原封不動地再寫一次,既沒效率又容易出錯;建模語言則能透過對時間期間等索引的運用,輕鬆地自動處理這種重複(Fourer (1983) 對此有相當完整的討論)。

在架構上,不同的建模語言/MG 系統採取了幾種明顯不同的取向。第一種是為每一個要建的模型分別寫一支獨立的程式,使用某種通用的高階語言——這種做法完全忽略了所有數學規劃模型之間共通的結構,而且最終仍然得產出像 MPS 這樣繁瑣的標準格式,並不划算;更合理的做法,應該是把這些共通的結構直接內建進一個專屬的語言裡。第二種是 matrix block building system(矩陣區塊建構系統):實務模型裡龐大的係數矩陣,通常呈現高度結構化的樣貌——由一些(常常彼此重複的)小型密集區塊組成,再靠單位矩陣之類的簡單矩陣把這些區塊串接起來;這類系統提供串接、轉置等操作,把小矩陣系統性地組合、複製成大矩陣,缺點是使用者依然得用矩陣係數的角度去思考問題,只是被免除了組裝矩陣的一部分機械性工作。第三種是 data structuring system(資料結構化系統):讓使用者用流程圖之類的圖形化方式去組織模型——例如描繪原物料如何流入製程、轉換成產品、再經由倉儲配送給客戶——系統再把這個圖形化的表示直接翻譯成模型,完全避開代數符號;這類系統對特定應用(例如流程工業)非常實用,缺點是使用者得先花不少功夫學會這套系統本身,才能上手。

第四種取向,也是目前最普遍、最通用的一種,是使用 mathematical language(數學語言):前面幾種取向都刻意避開傳統的數學符號(例如 $\sum$ 記號與索引集合),但傳統數學記號本身其實正是一種被廣泛理解的「語言」,能非常精簡地定義出各式各樣的模型——「數學記號對使用者而言不自然」這種說法,對已經有基礎數學訓練的使用者而言站不太住腳。大多數以數學記號為基礎的通用建模系統,彼此的核心組成都很類似:SET(集合)代表某一類線性或整數規劃變數的索引,例如用一個 root name(如 `PROD`)搭配一個從集合 $A=\{1,\dots,57\}$ 取出的索引,就能表示 57 個產品變數 `PROD1`、`PROD2`、……、`PROD57`,索引可以是數字,也可以是像城市名或月份這樣有意義的名稱;DATA(資料)是模型的係數,通常定義成陣列,或者直接從外部檔案讀入,並按照 SET 定義的索引排列;VARIABLES(變數)是模型裡實際出現的線性或整數規劃變數,同樣用 root name 加索引表示(例如 `PROD[A]`),如果變數帶有特殊性質(例如 integer、free、binary),通常也在宣告變數時一併指定;OBJECTIVE(目標)就是模型的目標函數,用 MAXIMIZE 或 MINIMIZE 宣告,並透過 sum(或 sigma,因為大多數鍵盤打不出 $\sum$ 符號)這類關鍵字,對索引集合做加總來定義;CONSTRAINTS(限制式)則是模型裡的線性限制式,同樣可以被索引。

書裡用一套名為 NEWMAGIC 的語言,具體示範了怎麼用這五個元件,把 Part II 其中一個食用油調配案例的模型完整寫出來。這個範例的價值,不只在於展示語法,更在於它幾乎把本章前面談過的每一種目標函數與限制式類型都串在了一起:模型的 OBJECTIVE 是一個典型的利潤極大化目標(呼應前面「單一目標」一節),把調配、儲存與精煉的收益、成本、庫存持有成本都算進同一個式子;CONSTRAINTS 裡處理跨期間庫存的限制式表達的是物料平衡(呼應「物料平衡(連續性)限制」一節);植物油與非植物油各自的每月精煉產能上限,呼應「產能限制」與「簡單界限與 GUB」;成品硬度必須落在允許區間的限制式,呼應「品質限制」一節。而模型後半段額外引入的一組二元變數,用來表達「一種油只要在某個月被使用,用量就必須至少達到某個下限,而且每個月最多只能用三種油,某些油之間還存在誰用了誰才能用的先後條件」——這正是前面「不尋常限制」一節提到、需要靠擴充成整數規劃才能表達的邏輯性條件。能在同一個模型檔案裡,同時看到本章分類過的絕大多數目標函數與限制式類型,也算是替這整章的分類法做了一次首尾呼應的總結。
