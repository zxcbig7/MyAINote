# MP 模型基礎：從一段文字描述到一組數學式

如果你把「建模」丟給十個有經驗的 OR（Operations Research）工作者，你大概會得到十種不同的下筆順序：有人先寫目標函數，有人先列變數，有人憑直覺抓幾條看起來重要的限制式就開始套 solver。這不是誰對誰錯的問題，而是建模這件事長期以來確實缺乏一套系統化的方法——它更接近一門靠經驗累積的手藝，而不是一套可以教、可以覆現的流程。García Sánchez 這本書要處理的正是這個缺口：給「怎麼把一個系統變成一個數學規劃模型」這件事，提供一套可以按部就班走過的方法論，而不是丟給讀者一堆案例讓他自己去悟。這一頁整理書的前兩章，也就是整套方法論的入口——Ch.1 回答「模型是什麼、為什麼要建模」，Ch.2 回答「一個 MP 模型骨架上有哪些零件、彼此怎麼咬合」。讀完這兩章，後面幾章（元素、決策活動、計算、規格）要解決什麼問題，你會有清楚的地圖感。

## 模型是什麼，為什麼建模需要方法論

先把「模型」這個詞說清楚。書裡引了幾個定義：Pidd 說模型是「人們為了理解、改變、管理、控制現實的一部分，而做出的一個明確且外顯的表徵」；Aracil 說模型是對現實某個面向的抽象表徵，其結構由「元素」和「元素之間的關係」構成。這兩個定義合起來已經點出後面整本書的骨幹——建模的核心工作，就是把「現實裡有哪些東西、它們之間怎麼互相影響」講清楚，並且用數學語言把這層關係重寫出來。

Lowry（1965）把數學模型分成三種:descriptive model 用來描述一個既有情況、prediction model 用來模擬未來事件、planning（normative）model 則是基於目標與限制去建構一個計畫，追求在一組限制之下更好地達成目標。數學規劃模型（也就是最佳化模型）屬於最後這一種：它用數學關係式（稱為 constraints）去表達一個系統的規格，系統裡的一系列活動被表示為變數，整個系統的運作則依循一個最佳化準則（objective function）去被評估、被求解。

這裡書一開始就劃了一條清楚的邊界，值得記住：**這本書講的是怎麼把系統轉成模型（formulation），不講怎麼解模型（resolution）**。這不是作者偷懶,而是刻意的範圍切割——市面上關於求解演算法（simplex、branch and bound、各種 heuristic）的教材已經很多，但「怎麼把一個含糊的業務描述,系統化地拆解成正確的變數與限制式」這一步,反而長期沒有一套明確的方法可以依循,這正是這本書要補的洞。

那為什麼在今天特別需要重視「建模」這一步、而不是把心力都放在解法上?Ch.1.6 給了一個現實理由:運算能力與最佳化函式庫這幾十年進步得非常快,現在只要模型寫對,很多問題可以直接丟給現成的 solver 求解,不再需要為每個問題手刻專屬的啟發式演算法。換句話說,「把模型寫對」正在取代「把解法寫巧」,成為工作的重心。書裡進一步指出,決定該用哪種解法策略,取決於三個因素:問題的計算複雜度(是否落在多項式時間可解的 P 類,還是 NP 類)、問題的規模、以及問題的時效性(是要在很短時間內給出答案的戰術性問題,還是可以等久一點求精確解的戰略性問題)。連續變數的線性規劃問題本身複雜度不高,幾乎都能用模型配合 exact resolution 直接解到最佳;整數變數的問題則要先判斷屬於 P 還是 NP——屬於 P 類的,一樣可以用模型精確求解;屬於 NP 類的,則要在「用模型做 exact resolution(例如 branch and bound)」與「不特別建完整模型、直接用 heuristic 做近似求解」之間做取捨。書中态度很明確:只要條件允許,作者建議永遠優先嘗試用數學模型搭配最佳化函式庫求解,把 heuristic 留給資料本身就不可靠、或問題時效性真的等不到精確解的情境。而且隨著平行運算與分散式運算越來越普及,exact resolution 這條路只會越來越可行。這也是為什麼「建模時要把後續求解放在心上,盡量寫出容易被求解器吃下去的模型」被作者當成建模者的責任之一。

## 古典的四元件,以及模型的書寫規範

在正式進入這本書自己的方法論之前,Ch.1 先幫讀者複習一遍業界既有的說法。一個 MP 模型的古典組成通常被歸納成四個元件(Castillo et al. 2002):**Data** 是模型處理的確定性數值,以參數的形式簡化表示;**Variables** 定義了問題中要決定的東西,依值的性質可以是連續、整數,而整數變數裡又有一種特別重要的子類——只能取 0/1 兩值的 binary 變數;**Constraints** 是定義系統規格與規則的等式或不等式,而變數本身的正負號限制(sign constraint)也算在內;**Objective Function** 則是最佳化準則,決定模型要極大化或極小化哪個函數。

模型也可以依幾個維度分類。依資料性質分,deterministic model 的所有資料已知且精確,stochastic model 的資料帶有隨機成分——這本書的方法論只處理 deterministic 的情況(雖然部分技巧也能挪用到隨機模型上)。依目標與限制式的數量分,可以只有限制式而沒有目標函數、可以是最常見的單目標最佳化、也可以是多目標問題,甚至存在只有目標函數、完全沒有限制式的極端情況。依函數的線性性質分,則區分成 linear programming model(所有數學式都是線性)與 non-linear programming model(限制式或目標函數中有非線性項);在線性模型內部,還可以再依變數性質細分成(continuous)linear programming model、pure integer linear programming model(全部整數變數)、mixed integer linear programming model(整數與連續變數並存)、以及 binary linear programming model(全部是二元變數)。這一套分類詞彙會在後面每一章反覆出現,是整本書的共同語言。

Ch.1.5 接著把模型的書寫格式規範化:一般寫法是 Min f(X) subject to Gᵢ(X) ≈ bᵢ,其中 X 是變數向量、f(X) 是目標函數、≈ 代表限制式的符號(可能是 ≤、=、≥)、b 是限制式右手邊的常數向量。書裡也順手交代了幾個「把模型轉成標準形式」的小工具,之後各章推導模型時會不斷用到:要把 Max 問題轉成 Min,只要把目標函數乘上 -1 再求 Min,最後再把解出來的目標值變號讀回去即可;要把 ≥ 或 = 的限制式統一轉成 ≤,可以把不等式乘上 -1 反向,或把等式拆成一個 ≤ 與一個 ≥ 再各自轉換;如果原始限制式用的是嚴格不等式(< 或 >),對整數變數可以直接用「差 1」的方式改寫成非嚴格不等式,對連續變數則要引入一個足夠小的容許誤差 ε;而如果模型裡出現非負限制之外的變數——例如變數被限定為負值,或者是完全沒有正負限制的自由變數——也都有對應的代換技巧(前者取負號代換,後者拆成兩個非負變數的差)。這些細節聽起來瑣碎,但意義在於:只要照著這套規範走,任何一個模型都可以被改寫成同一種標準形式,方便丟進求解器或跟別人溝通。

## 從文字到方程式:奶油工廠的第一次示範

理論講完,Ch.1.4 用一個刻意簡化的例子把上面的四元件實際跑一遍,目的是先讓讀者對「從系統描述到數學模型」這個轉換過程有具體的感覺。情境是這樣的:一家奶油工廠想最佳化每天甜奶油(sweet butter)與生奶油(raw butter)的產量,每公斤甜奶油利潤 $10、生奶油利潤 $15;生產要經過兩台機器——巴氏殺菌機(每天可用 3.5 小時)與打發機(每天可用 6 小時),兩種奶油在兩台機器上耗用的時間各不相同。

建模的第一步是找出 Variables:系統裡真正「需要決定值」的活動是甜奶油與生奶油各自的產量,兩者都以公斤計量,所以定義成連續變數 x₁(甜奶油產量)與 x₂(生奶油產量),並且加上不能生產負數公斤奶油的正號限制 x₁≥0、x₂≥0。第二步是 Constraints:兩台機器各自的產能就是資源的上限,只要把「該資源被兩個活動消耗掉的總量」寫成線性表達式,要求它不超過產能即可——巴氏殺菌機得到 3x₁+3x₂≤210(單位統一換算成分鐘),打發機得到 3x₁+6x₂≤360。第三步是 Objective Function:總利潤就是兩個活動各自的單位利潤乘上其產量後加總,寫成 Max 10x₁+15x₂。四個元件合起來就是完整模型。

書裡刻意用一組次佳解(x₁=20, x₂=30,利潤 $650)驗證這組限制式確實滿足,同時又指出真正的最佳解是(x₁=20, x₂=50,利潤 $950)——但作者明確提醒:怎麼從一堆可行解裡找到這個最佳解,是 resolution method 的工作,不是這本書的範圍。這個小小的提醒其實呼應了前面「建模與求解分工」的立場:formulation 寫對之後,找最佳解就交給 solver。

## 為什麼四元件不夠:系統與五元件

奶油工廠的例子雖然示範了古典四元件怎麼用,但它也暴露一個問題:當你面對的不是這麼乾淨的小例子,而是一段含糊、夾雜多種角色與規則的業務描述時,「變數」「限制式」這種詞彙太粗,沒辦法指導你一步步從文字裡把東西挖出來。這正是 Ch.2 要解決的:把模型放回它所屬的**系統(system)**——系統是最佳化問題發生的環境,擁有參與其中的元素、規格、以及引導最佳化的準則。書裡進一步把系統分成 static(元素的資訊不隨時間改變)與 dynamic 兩種,這套方法論只處理 static 系統。而「建模」這件事,說到底就是把一個系統的文字描述,轉換成優化技術可以理解的數學語言——用書裡的說法,就是「model 這個系統」。

在這個系統框架下,Ch.2.2 把古典的四元件,拆解、擴充成五個更細緻的元件,這五個詞彙會貫穿全書後面每一章:

**Elements(元素)**是系統裡所有參與其中的角色——人、工具、地點、時間等等,性質可以非常多樣。它們通常帶有相關的數值資訊(稱為 attribute),而且會參與系統中的活動、或影響系統的規格,有時候「元素」跟「活動」甚至會被合併識別。

**Decision Activities(決策活動)**是系統中需要被「決定」其值的直接行動,並且與元素相關聯。這裡有一個之後會反覆用到的判準:一個決策活動**不可以**是邏輯計算的結果、不可以是某個簡單函數的結果、也不可以是其他決策活動組合出來的結果——換句話說,它必須是真正「懸而未決」、無法從別的東西推導出來的自由選擇。決策活動決定了模型的主要變數,其值可能是二元、整數,或連續。

**Calculations(計算)**是基於決策活動、系統可能需要透過計算過程得出的額外資訊,而計算本身甚至可以建立在其他計算之上。計算在模型裡同樣被表示為變數,但書裡特別提醒了一個微妙但重要的區別:這些變數「只是為了求解過程而存在的決策變數,而不是為了描述系統實際如何運作」——換言之,它們形式上跟決策活動長得一樣(都是變數),但概念上不是自由決定的東西,而是被推導出來的。計算與其所依賴的變數之間的關係,可以透過數學函數、邏輯命題、或作為變數的界限來表達,對應到三種子類型:auxiliary calculation(由線性函數計算得出,通常是為了讓模型更清楚易讀,非強制使用,但當你需要把一個函數的值離散化——也就是整數化——時就必須用它,產生的是 auxiliary variable)、logical calculation(用來取得一個邏輯命題的結果,強制需要使用,產生的是 logical variable)、以及 lower/upper bound calculation(用來取得一組變數的上界或下界,同樣是強制需要使用的類型)。

**Specifications(規格)**是系統中必須被滿足的法規、要求或限制,它們是限制式(constraint)的來源,但規格不等於限制式——限制式是單一一條數學表達式,而規格是一個系統必須滿足的特性,這個特性有可能要靠一條、也可能要靠好幾條限制式才能完整表達出來。

**Objective Criterion(目標準則)**可以理解為系統的另一種規格,它表達了引導系統求解方向的準則。目標準則與元素身上的成本相關聯,最終形成目標函數;某些情況下,目標準則本身也需要額外的計算與專屬的限制式才能完整表達。

書裡用兩張圖把這五個元件的關係講得很清楚。第一張圖顯示:Elements 是唯一跟其他四個元件都有雙向關係的節點——它擁有系統的資訊,對 Specifications、Calculations、Objective Criterion 都有特別的影響,而這些元件也回過頭決定了元素本身的性質(也就是元素的「量化本質」,這是後面 [[quantitative-nature-of-elements]] 那一章要細講的主題);Decision Activities 參與 Specifications 與 Objective Criterion;Calculations 作為變數,同樣參與 Specifications 與 Objective Criterion,而且一個 Calculation 的定義本身也可以被表示成一種 Specification。第二張圖則把這套新詞彙對回古典四元件:Elements 對應 Data and parameters;Decision Activities 與 Calculations 都對應到 Variables;Specifications 對應到 Constraints;Objective Criterion 對應到 Objective Function。用一句話濃縮這張圖:決策活動本身就是問題的變數,計算也會生出變數、而且一定伴隨相關的限制式,規格定義限制式,目標準則定義目標函數(也可能附帶限制式)。

## 五元件如何咬合:兩個例子重新示範

Ch.2.3 把奶油工廠的例子重新走一遍,但這次改用五元件的視角。Elements 是巴氏殺菌機(容量 3.5 小時、每公斤甜奶油耗時 3 分鐘、每公斤生奶油耗時 3 分鐘)、打發機(容量 6 小時、耗時分別是 3 分鐘與 6 分鐘)、甜奶油(利潤 $10/公斤)、生奶油(利潤 $15/公斤)——書裡也順帶提到工廠本身其實也可以被當作一個元素(也就是系統本身),只是它沒有任何有意義的數值或活動與之綁定,所以列不列都不影響模型。Decision Activities 的識別過程值得留意其推理方式:面對「甜奶油產量」這個行動,先試 binary 值(不行,無法表達確切產量)、再試整數值(不行,產量以公斤計量是連續量)、最後確認連續值可行,而且這個值確實是無法被計算出來的「懸而未決」的量,因此判定為決策活動,生出變數 x₁、x₂。這裡不需要任何 Calculations。Specifications 則是這個系統裡一個非常典型的模式:當某個元素扮演「資源」的角色、擁有可用量或容量,而某些決策活動會消耗這個資源時,就會生出一條「消耗量 ≤ 容量」的限制式——巴氏殺菌與打發機各自生出一條這樣的限制式。Objective Criterion 則是把每個活動的單位利潤乘上其活動量、加總起來最大化。

第二個例子(Illustration 2.2,取材自 Meléndez 2019)則刻意設計得更貼近真實業務的含糊感,用來示範五元件框架真正解決了什麼問題。情境是一家百貨公司要清庫存:剩餘 200 件襯衫、100 件褲子,設計了兩種組合優惠——優惠 A(1 件襯衫+1 件褲子,賣 $30)與優惠 B(3 件襯衫+1 件褲子,賣 $50),而且優惠 A 至少要賣出 20 組;此外褲子也可以直接批發給一個 outlet,單價 $18,但如果批發超過 50 件就要付 $80 的手續費。目標是最大化利潤。

這個例子有三個地方特別值得記住,因為它們示範了五元件框架比古典四元件更好用在哪裡。第一,Elements 的識別可能出現數值重疊或模糊:褲子這個元素身上帶有「批發給 outlet 的單價 $18」「免手續費上限 50 件」「手續費 $80」這些屬性,但 outlet 這個元素身上也帶著幾乎一模一樣的屬性——書裡直接點出這是「同一組數值特徵可能同時關聯到不只一個元素」的情況,要等到後面 [[system-elements]] 那一章才會系統性處理這種模糊性,這裡只是先讓讀者有印象。第二,Decision Activities 的判定要靠前面提到的那個判準來過濾:「發行優惠 A/B」與「批發褲子給 outlet」都是無法從別處推導出來的自由決定,判定為整數決策活動(因為批數與批發件數都是不可分割的離散單位,binary 和 continuous 都不合適),分別生出 x_A、x_B、x_PO;但「支付手續費」不是決策活動,因為它的值完全可以從其他決策活動(也就是 x_PO 是否超過 50)推算出來——這正是判準真正發揮作用的地方;「最大化利潤」也不是決策活動,它本來就是目標函數,不是一個要被決定的行動。第三,「支付手續費」正好示範了一個 logical calculation 的典型用法:先定義一個二元計算變數 α(付費為 1、不付費為 0),再把商業規則「如果批發量超過 50 件就付 $80」寫成邏輯命題,最後轉換成一條線性限制式 x_PO≤100α。這個從「IF-THEN 描述」到「線性限制式」的轉換手法,只是在這裡先預告一下,真正完整的方法會在 [[logical-specifications-guide]] 那一章展開。至於 Specifications 與 Objective Criterion 的部分,跟奶油工廠的例子邏輯一致:優惠 A 的最低批數是一條下界限制式,襯衫與褲子的庫存量各自扮演資源角色、生出消耗量限制式,而目標函數則是把三個決策活動的收入加總、再扣掉手續費計算變數帶來的成本。

## 地圖:接下來四章要解決什麼

讀到這裡,五元件的骨架已經站穩,但每一個元件實際「怎麼從文字描述裡把它找出來」,這兩章其實只給了直覺、沒有給方法。這正是後面幾章要逐一補齊的空缺,而且書刻意按照一個循序漸進的順序安排:[[system-elements]] 先處理「怎麼判斷系統裡有哪些元素、元素之間怎麼分組成集合」；接著 [[decision-activities]] 給出一套更嚴謹的判準,教你怎麼確認一個行動究竟是不是決策活動、以及它該用二元、整數還是連續值表示;再來 [[system-calculations]] 會把 auxiliary、logical、bound 這三種計算類型的建構方法完整展開;而規格與限制式的分類、以及以命題邏輯為基礎的規格寫法,則分別留到 specification-types 與 [[logical-specifications-guide]] 兩章處理。這五章合起來,才是這本書真正要教的方法論主體——本頁只是打地基,讓讀者先把詞彙與骨架記住。
