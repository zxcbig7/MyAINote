## 模型是什麼，為什麼要建它

科學的許多應用都會用到「模型」。模型是為了某個特定目的而建的一個結構，它只保留原始對象的部分特徵——保留哪些特徵，取決於這個模型要拿來做什麼用。有些模型是具體的，例如風洞實驗用的飛機模型；但在作業研究（operational research）裡，我們關心的幾乎都是抽象模型，也就是用代數符號去鏡射被建模對象（通常是一個組織）內部關係的模型。這樣的模型稱為數學模型，它的核心特徵是：它包含一組數學關係——方程式、不等式、邏輯相依性——而這些關係對應到現實世界裡某些更接地氣的關係，例如技術上的限制、物理定律、市場條件。

值得先弄清楚一件容易被忽略的事：一個模型真正被定義的，是它裡面的**關係**，而不是它用的**資料**。同一個模型可以在不同場合套用不同的成本、技術係數、資源可用量，我們仍然會認為那是「同一個模型」——只要改變的是資料而不是關係。這個區分不是絕對的：如果資料的變動夠劇烈，通常就會被視為關係本身變了，也就是模型變了。這個看法很重要，因為它替後面要講的「建模語言」鋪了路——如果模型的本質是關係而資料只是可替換的輸入，那麼把資料和結構分離、讓資料可以獨立更新，就是一件天經地義的事。

為什麼要花力氣建模型？書中列出三個核心動機。第一，建模這個動作本身常常就會揭露出許多原本沒被注意到的關係——很多時候，理解一個系統的收穫，發生在「試著把它寫下來」的過程中，而不是在拿到答案之後。第二，模型建好之後通常可以用數學方法去分析，藉此提出原本不明顯的行動方案。第三，模型讓「實驗」變成可能，而直接拿真實對象做實驗往往不可行或不划算——在一個國家真的去實驗一套非傳統的經濟政策，政治上極度困難，失敗機率一高更是難以承受；但在數學模型上做同樣的實驗,相對而言容易被接受得多。

模型的價值也一直有爭議，而且爭議往往走向兩個極端。一種聲音全盤否定模型的價值，理由通常是許多所需資料根本無法妥善量化——例如給一項社會效益標上金錢價值,這種質疑不容易被完全反駁，但也必須指出：許多攸關不可量化概念的決策，實際上早已隱含地做了某種量化,把這個量化明白寫進數學模型裡，反而更誠實、更科學。另一種比較輕微但同樣常見的批評，是質疑模型資料的精確度——如果模型裡有十萬個係數，其中許多都不精確,答案還能信嗎？這一點必須針對每個模型個別檢視,而且，正如後面 [[building-lp-models]] 會談到的敏感度分析（sensitivity analysis）,模型結構本身有時候可以讓誤差被稀釋，不見得會直接放大成解答的誤差。

在光譜的另一端，則是對模型近乎迷信般的盲目信任，尤其是當模型跑在電腦裡的時候。模型產出答案的品質，終究取決於模型結構與資料的準確程度；毫無批判地全盤接受一個模型第一次給出的答案，本身就很危險。正確的態度是把模型當成眾多決策輔助工具之一：如果一個答案代表的操作方案讓人無法接受,就該找出原因、把它反映進一個修改過的模型；如果答案可以接受，也該把它視為眾多「選項」之一（透過設定不同的目標函數即可得到不同的選項）。透過不斷質疑答案、調整模型（或它的目標），才能逐步釐清真正可行的操作範圍，也才能對「什麼是可能的」有更深入的理解。這個「模型只是決策輔助之一、答案要拿去質疑」的態度，會貫穿整本書，也是為什麼 Part I 花這麼多篇幅在講「怎麼樣才是一個好模型」（見 [[building-lp-models]] 第 3.4 節）。

## 數學規劃模型的分類

數學規劃（mathematical programming, MP）這個詞很容易讓人誤解——它跟電腦程式設計（computer programming）幾乎沒有關係。這裡的「programming」是「規劃、排程」的意思，跟軍事或行政語境裡的用法一致。這個誤解普遍存在，也確實可惜，因為數學規劃無可避免地會牽涉到大量的資料與運算，因此在實務上總是仰賴電腦的計算能力,這讓兩件本質不同的事情在字面上混在了一起。

所有數學規劃模型共通的特徵是最佳化（optimization）：我們想要最大化某個量，或最小化某個量,這個要被最大化或最小化的量,稱為目標函數（objective function）。有一種常見的誤解是,一旦強調「最佳化一個目標」,就等於默認現實中一定存在一個清楚、單一的目標,於是很多人因為現實問題「沒有清楚目標」或「目標互相衝突」而直接否定數學規劃的適用性。這種態度其實站不住腳——正如 [[building-lp-models]] 第 3.2 節會深入說明的，就算現實中沒有單一明確的目標，最佳化某個面向仍然常常有其價值。

本書把注意力集中在幾種特殊類型的數學規劃模型：線性規劃（linear programming, LP）模型、非線性規劃（non-linear programming, NLP）模型，以及整數規劃（integer programming, IP）模型。

書裡用兩個小例子具體示範什麼是 LP 模型。第一個是「product mix」問題：一家工廠可以用研磨（grinding）和鑽孔（drilling）兩道製程，生產五種產品（PROD 1 到 PROD 5），每種產品每單位有各自的利潤貢獻，也各自佔用研磨機、鑽孔機和裝配人力的工時,問題是要決定每種產品該生產多少，才能讓總利潤貢獻最大。設 $x_1,\dots,x_5$ 為五種產品的產量，目標函數是利潤貢獻的加總

$$550x_1+600x_2+350x_3+400x_4+200x_5$$

而研磨、鑽孔、裝配這三項產能限制，各自轉成一條形如「係數乘變數加總 $\le$ 產能上限」的不等式。這個例子雖然簡單，卻已經完整示範了一個 LP 模型的三個要素：一個要被最大化或最小化的線性運算式（目標函數）,一系列同樣是線性運算式的限制式（constraints）,以及限制式右手邊的一組常數（右手邊，right-hand side）。書中也特別提醒兩個常被視為理所當然、卻值得明講的隱含假設：變數不能是負值（non-negativity，即 $x_j\ge 0$，在大多數 LP 模型裡即使沒寫出來也預設成立）；以及變數可以取分數值（divisibility）——如果變數代表的是加侖的啤酒，取 2.36 這種分數值沒有問題,但如果代表的是汽車的數量，分數值就沒有意義了。當分數解無法被接受、四捨五入又會造成明顯誤差時,就必須改用整數規劃（IP）。

第二個例子是「blending」（調配）問題：一家食品廠要把兩種植物油（VEG 1、VEG 2）與三種非植物油（OIL 1、OIL 2、OIL 3）調配成成品，每種原料有各自的採購成本與「硬度」（hardness）這項技術指標，成品的硬度必須落在 3 到 6 之間,同時植物油與非植物油分別受到每月最大精煉量的限制。這個例子比 product mix 複雜的地方在於：它同時示範了品質規格限制（硬度必須落在區間內,對應到兩條同方向但反向的不等式）,以及一條連續性限制（continuity constraint）——用來確保成品的總重量恰好等於所有原料重量的加總,即 $\sum x_j - y = 0$。這條限制式看起來瑣碎，卻是很多實務模型裡最容易被疏忽、一旦漏掉就會讓模型產生「憑空生產出重量」這種荒謬解的地方,這個主題會在 [[building-lp-models]] 第 3.3.4 節被系統性地歸類成「物料平衡限制」。

線性這個假設不見得總是成立。當目標函數或限制式裡出現非線性項（例如 $x_1^2$、$e^{x_1}$、$x_1x_2$ 這類項次），就得到一個 NLP 模型；[[nonlinear-and-separable-programming]] 會介紹如何用 separable programming 這個技巧把相當廣泛的一類非線性模型轉換成可以用線性方法逼近求解的形式。此外還有一種模型類型也值得先提一下：隨機規劃（stochastic programming）模型——當資料中有一部分是不確定的、但可以用機率分布來描述時就會產生這類模型。單純用資料的期望值來代表這種不確定性，往往並不足夠；本書會在後面談到 chance-constrained 模型（見 [[building-lp-models]] 第 3.3.7 節）和帶 recourse 的多期模型（multi-staged models with recourse，見 [[structured-lp-models]]）這兩種處理隨機性的方式，兩者都仍然可以被歸入 stochastic programming 的範疇之下。

## 怎麼解一個數學規劃模型

一套用來解決某一類問題或模型的數學規則,稱為演算法（algorithm）。演算法可以被寫成電腦程式，用來解決對應類型的模型,只要模型是用某個規定好的格式輸入電腦。對於使用頻率夠高的演算法，通常值得投入心力把它寫成非常精細、有效率的程式,把許多這類演算法收在一起,就成了一套「package」（套裝軟體）。這樣的套件由電腦廠商、顧問公司或軟體公司開發,通常代表了非常大量的人年投入。建好一個數學規劃模型之後，比起自己動手寫程式來解它,更值得善用現成的套件。

商業套件幾乎必用的三種演算法是：解 LP 模型的 revised simplex algorithm；解 separable programming 模型的、revised simplex 的延伸版本；以及解 IP 模型的 branch and bound algorithm。這三個演算法並非各自獨立——事實上，把它們放進同一套套件裡是有道理的：演算法（二）只是演算法（一）的一個修改版，可以用同一套程式在偵測到模型是 separable 的情況下自動切換執行方式;而演算法（三）則是先用演算法（一）當作第一階段,再執行第 8.3 節所描述的 tree search 程序（見 [[integer-programming-fundamentals]]）。

一套好的套裝軟體通常也提供不少額外的功能，讓使用者依情況選用：

- **Reduction**：有些套件能偵測並移除模型中的冗餘（redundancy），藉此縮小模型規模、加快求解速度,這類程序通常叫做 REDUCE、PRESOLVE 或 ANALYSE，[[building-lp-models]] 第 3.4.3 節會用具體的數值例子示範這類冗餘是怎麼被偵測出來的。
- **Starting solutions**：多數套件允許使用者為模型指定一個起始解,如果這個起始解夠接近最佳解，求解所需的時間可以大幅縮短。
- **Simple bounding constraints**：形如 $x\le U$ 或 $x\ge L$ 這種只涉及單一變數的簡單限制,不需要當成一般的限制式列出來，而是可以直接當作變數的上下界處理——revised simplex 演算法有專門處理這種「有界變數」（bounded variable）的修改版本，效率遠高於把它當成普通的一條限制式。
- **Ranged constraints**：有時候需要同時對某個線性運算式設定上界和下界,與其寫成兩條限制式，更精簡的做法是只寫第一條限制式,再額外附上一個「range」（$b_1-b_2$）,這個 range 的效果是限制該限制式所引入的 slack 變數的上界,等同於隱含了第二條限制式。
- **Generalized upper bounding constraints（GUB）**：形如 $x_1+x_2+\cdots+x_n\le M$ 這種對一組變數總和設上界的限制式在 LP 模型中很常見,如果模型中有相當比例的限制式屬於這種形式，而且每一組變數彼此互斥,用 revised simplex 的 GUB 延伸版本來處理，通常能讓求解速度大幅提升。
- **Sensitivity analysis / ranging**：模型求出最佳解之後，人們常常關心目標函數係數或右手邊係數的變動,會如何影響這個解。Ranging 就是找出這些係數可以變動的範圍，而變動仍然維持原先預測效果的方法,這在敏感度分析中非常有價值，幾乎所有商業套件都提供 range 功能，詳見 [[interpreting-lp-solutions]]。

書中也用第一章 blending 例子，示範一個模型實際上是怎麼呈現給電腦套件的。像 blending 這種規模的問題,通常會先整理成一張矩陣表——把變數當欄、限制式當列，中間填入係數,每條限制式再標上它的種類（等於、小於等於、大於等於）,這種表格化的呈現方式再進一步轉成 MPS（mathematical programming system）格式,這是絕大多數商業套件與建模語言都支援轉換的標準格式，分成 ROWS、COLUMNS、RHS 三大區塊：ROWS 區列出模型中所有的列名及其類型（N 代表非限制式列，也就是目標函數列；L / G / E 分別代表 $\le$、$\ge$、$=$ 限制式）;COLUMNS 區逐欄列出矩陣中的非零係數;RHS 區則把右手邊的常數，用跟 COLUMNS 相同的格式當成一欄處理。MPS 格式雖然通用，卻相當繁瑣、不直觀，這正是後面 [[building-lp-models]] 第 3.5 節「建模語言」要解決的痛點——那一節會說明為什麼建模語言比直接手刻 MPS 格式更適合人類使用。

## 決策支援系統與專家系統

有一些軟體會把數學規劃演算法包進去,設計來服務特定的應用場景，這樣的系統有時被稱為決策支援系統（decision support systems, DSS）。它們通常還被嵌入更大的管理資訊系統（management information systems）中，除了（可能）求解一個模型之外,還要負責存取資料庫、以「使用者友善」的方式跟管理者或決策者互動等其他大量功能。如果這類系統確實內建了數學規劃演算法，使用者在建模與演算法層面的負擔就會被移除，可以專心處理自己領域的具體應用。隨著決策支援系統越做越精細，它們開始能夠向使用者呈現多種決策選項，而不只是單純的儲存、整理、呈現資料;這類選擇背後很可能仰賴數學規劃,只是這個事實對使用者是隱藏起來的。

另一個相關的概念是專家系統（expert systems）。這類系統同樣非常重視使用者介面——它們有時被設計成可以接受「非正式的問題描述」,再透過與使用者互動,協助使用者把問題逐步精煉成一個更精確的定義（可能就是一個模型的形式）。這份資訊會結合系統過去累積的「專家」資訊,一起用來輔助決策。這類系統常用的計算程序，往往就涉及數學規劃的概念（例如 IP 中的 tree search，見 [[integer-programming-fundamentals]] 第 8.3 節）——雖然設計、撰寫這類系統本身超出本書範圍，但它們終究還是要仰賴數學規劃與建模的概念作為基礎。

## Constraint Programming：另一條路

Constraint programming（CP，有時也稱 constraint satisfaction 或 finite domain programming）是解決許多「同樣也能用 IP 解」的問題的另一種思路。CP 使用的方法，在傳統數學意義上或許不如 IP 精密，但它借助更精巧的電腦科學技術,在表達能力上有一些優勢,有時候也因此更容易求解——這是因為它能用一種更簡潔的表示法來描述問題。可以預見的是，未來會出現整合 CP 與 IP 兩種建模能力的混合系統（hybrid systems），例如 Hooker（2011）所討論、協助設計出來的 SIMPL 系統，就是這種整合思路的一個例子。

在 CP 裡，每個變數都有一個有限的可能值集合，稱為它的定義域（domain）。限制式（constraint）則用來連結、限制這些變數可以取的值組合。CP 裡的限制式比 IP 的線性限制式豐富得多（雖然線性限制式在 CP 裡也照樣可以用），通常以述詞（predicate）的形式表達——一個述詞的值必須是真或假。這些述詞也被稱為 global（或 meta）constraints，因為它們是（如果被使用的話）套用在整個模型上、被整合進所使用的 CP 系統裡。傳統的 IP 模型只使用宣告式（declarative）限制式，這使得「模型本身的陳述」和「求解過程」之間有清楚的區分——這一點恰好與 CP 系統中可能被使用者加入、用來輔助求解過程的「local」或「procedural」限制式形成對比。

書中舉了幾個 CP 系統常用、且通常會有不同名稱的 global predicate 作為說明：

| 述詞 | 意義 |
|---|---|
| $\mathrm{all\_different}(x_1,\dots,x_n)$ | 所有變數必須取相異值。用傳統 IP 也能建模，但比較笨重 |
| $\sum_j a_jx_j\neq b$ | 「不等於」限制，用 $\neq$ 述詞表達 |
| $\mathrm{card}_m(x_1,\dots,x_n\mid v)$ | 恰好 $m$ 個變數要取值 $v$（cardinality predicate） |
| $\mathrm{cumulative}((t_1,\dots,t_n),(D_1,\dots,D_n),(C_1,\dots,C_n),C)$ | $n$ 項工作分別在 $t_i$ 開始、耗時 $D_i$、佔用資源 $C_i$，任何時刻資源用量不得超過 $C$ |
| $\mathrm{circuit}(x_1,\dots,x_n)$ | $x_1,\dots,x_n$ 是 $1,\dots,n$ 的一個排列，且必須構成一個沒有子迴路的完整迴路（呼應旅行推銷員問題，見 [[special-integer-programming-structures]]） |
| $\mathrm{element}(j,(x_1,\dots,x_n),z)$ | 把 $z$ 設為變數清單中第 $j$ 個元素的值 |
| $\mathrm{lex\text{-}greater}$ | 依字典序比較兩組變數序列的大小，常用來替一群等價解排出優先順序、削減對稱性帶來的搜尋負擔 |

上面這些述詞，理論上全部都能用傳統 IP 的變數與限制式建模出來（往往還不只一種寫法），但那樣做常常很麻煩、很笨拙。多數商用 CP 系統提供的 global constraint/predicate 遠不只上面列的這幾種。

值得留意的是，用 CP 建 IP 模型也有它的實務優勢。舉例來說，在建 IP 模型（見 [[integer-programming-fundamentals]] 第 9 章）時，常常要用像 $x_{ij}=1$ 表示「$i$ 被指派給 $j$」這樣的 assignment 變數；在 CP 裡，這可以直接用一個函數 $f(i)=j$ 來表示。另一個常見的需求是要反過來——已知 $j$，找出使 $f(i)=j$ 成立的 $i$；這可以用 element predicate 的一個變化版本 $\mathrm{element}(j,f(i),i)$ 來處理，用來指定 $j$ 的反函數是否為 $i$。CP 應用的問題也經常展現高度的對稱性（symmetry）——例如 $i_1,i_2,\dots,i_n$ 可能是彼此等價、可以互換的實體,若要被指派給 $j_1,j_2,\dots,j_n$。與其窮舉所有等價解，用 lex-greater 這類述詞替解排出優先順序,可以大幅削減搜尋量。這個對稱性問題同樣也會出現在傳統 IP 模型中,並在 [[integer-programming-refinement]]（第 10 章）中被進一步討論。

CP 最有用武之地的場景，是那些要從「天文數字般多的可能性」中找出一個解的組合最佳化問題（combinatorial problems，見 [[special-integer-programming-structures]] 第 8 章），也就是要在一大堆條件中找出「大海撈針」的那根針——一個滿足複雜條件組合的可行解，可能少之又少，甚至完全不存在。相對地，CP 比較不擅長的場景，是那種存在許多可行解、要從中找出**最佳**解的問題,例如旅行推銷員問題（見 [[special-integer-programming-structures]]），或是完全沒有目標函數、只求可行解的問題。傳統 IP 使用（通常是 LP）relaxation 的概念（見 [[integer-programming-fundamentals]] 第 8.3 節）,來替最佳解提供一個界限（bound）——最大化問題得到上界、最小化問題得到下界,這個界限正是 IP 強大之處的來源。CP 雖然使用了比 IP 更精巧的分支策略（branching strategies），但它基本上是靠對限制式（述詞）施加越來越嚴格的條件，逐步逼近可行解,而不太具備「證明最佳性」的能力，除非窮舉。也因此，如何借助像 CP 中的述詞來建模 IP（再轉換成傳統 IP formulation），仍是一個持續有人研究的方向——McKinnon 與 Williams（1989）的一篇早期論文，就示範了如何用巢狀的 $\mathrm{at\_least}_m(x_1,\dots,x_n\mid v)$（意思是「$x_1,\dots,x_n$ 中至少 $m$ 個必須取值 $v$」）述詞,來表達任何 IP 模型的所有限制式。
