# 後端各種權限管理的寫法，搭配前端操作的實務範例

## 本章學習目標

學完這一章，你應該能做到：

- 一看到需求，就能同步設計：**JWT → 後端授權 → 前端 UI 行為**
- 不會出現「後端有權限但前端亂顯示」或「前端擋了但後端沒擋」
- 能將權限設計直接落地到 **ASP.NET Core Web API + 前端（React / SPA）**

## 一、三層權限模型的整體觀念

在實務系統中，權限從來不是單點設計，而是一條**責任鏈**：

```
Authentication（你是誰）
        ↓
Authorization（你能不能做）
        ↓
Frontend UI / UX（你看到什麼、能操作什麼）
```

三層的核心原則是：

- **Authentication 建立身分**
- **Authorization 是唯一可信的安全邊界**
- **Frontend 只做體驗優化，不負責安全**

## 二、貫穿三層的實際需求範例

以 RuleViewer 系統為例：

- 所有人都可以「查看規則」
- 只有 Editor 與 Admin 可以「編輯規則」
- 只有 Admin 可以「刪除規則」

這是一個**非常典型且實務真實的需求**，後續三層都會圍繞它設計。

## 三、第一層：Authentication（身分層）

### 這一層解決的問題

> 使用者是誰？
> 

### JWT 的建議結構

```json
{
  "sub": "vic",
  "role": "Editor",
  "permissions": [
    "rule.read",
    "rule.edit"
  ]
}
```

設計重點：

- `sub`：唯一身分識別
- `role`：粗粒度權限分類
- `permissions`：細粒度操作能力

---

### Pipeline 中的對應位置

```csharp
app.UseAuthentication();
```

責任只有一件事：

- 解析 Token
- 建立 `HttpContext.User`

**不做權限判斷、不擋請求**

## 四、第二層：Authorization（後端授權層）

### 這一層解決的問題

> 使用者能不能對「這個 API」做「這個動作」？
> 

這一層是**真正的安全邊界**。

---

### API 層級的權限定義（推薦）

```csharp
[HttpGet("rules")]
public IActionResult GetRules()
{
    // 公開存取
}

[Authorize(Roles = "Editor,Admin")]
[HttpPut("rules/{id}")]
public IActionResult UpdateRule(int id)
{
}

[Authorize(Roles = "Admin")]
[HttpDelete("rules/{id}")]
public IActionResult DeleteRule(int id)
{
}
```

設計原則：

- 權限寫在 API 上，而不是藏在程式邏輯裡
- Controller 本身就是「權限規格書」

---

### Pipeline 中的對應位置

```csharp
app.UseAuthorization();
```

它會：

- 讀取 `[Authorize]`
- 使用 `HttpContext.User`
- 決定是否回傳 `401 / 403`

## 五、第三層：Frontend UI / UX 行為控制

### 這一層解決的問題

> 使用者「應不應該看到」或「能不能操作」某個功能？
> 

注意：**這一層不負責安全，只負責體驗一致性。**

---

### 前端解析 JWT（一次即可）

```tsx
import jwtDecode from "jwt-decode";

const token = localStorage.getItem("access_token");
const payload = jwtDecode(token);

const role = payload.role;
const permissions = payload.permissions;
```

---

### UI 與後端權限對齊的寫法

```tsx
{permissions.includes("rule.edit") && (
  <button>編輯</button>
)}

{role === "Admin" && (
  <button>刪除</button>
)}
```

---

### 建議抽象成權限元件（中大型專案必做）

```tsx
function Can({ permission, children }) {
  if (!permissions.includes(permission)) return null;
  return children;
}
```

使用方式：

```tsx
<Can permission="rule.edit">
	<button>編輯</button>
</Can>
```

## 六、三層必須同時對齊的關鍵原則

請牢記以下三點：

- JWT 是三層共同使用的語言
- 後端永遠是最終裁判
- 前端的所有限制都假設「可能被繞過」

只要違反其中一點，系統就會開始失控。

---

## 七、套用到 RuleViewerBackend 的建議落地方案

建議你現在就採用：

- JWT：`role + permissions`
- 後端：
    - 短期：Role-based
    - 中期：Policy-based
- 前端：
    - `Can(permission)` 元件
    - 統一處理 `401 / 403`

這套結構可以直接延伸，不需要推翻重來。

---

## 本章重點整理

- 權限一定是「三層一起設計」
- Authentication、Authorization、UI 缺一不可
- 前後端權限語意必須 1:1 對齊
- RuleViewer 類系統非常適合這種模型
